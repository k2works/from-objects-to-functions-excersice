# 第 13 章 関数型アーキテクチャの設計

12 章かけて Zettai を作りました。この章では、コードをほとんど書きません。

書いたものが全体として何だったのかを、実装とテストの裏付けのある範囲で整理します。裏付けの無いことは、無いと書きます。

この版には、他の対象に無い問いが 3 つあります。執筆計画で立てたものです。

> 1. 副作用を型で追跡すると、核と殻の分離は楽になるか
> 2. Java 相互運用の境界で、型と効果の保証はどこまで届くか
> 3. 効果多相や効果ハンドラは、関数型 DI の代わりになるか

最後の節で、確かめた範囲で答えます。

### 何をシンプルと呼んだか

少ないことを、シンプルと呼びませんでした。この連載で、シンプルと呼んだのは次のことです。

| シンプルと呼んだもの | 具体例 |
| :--- | :--- |

## システム全体の設計

### 層と依存の向き

依存の向きは、次のとおりです。

```text
JdkServer ────▶ Http ──▶ Hub / CommandHub / QueryHub ──▶ Commands / Events / Projection ──▶ Domain
PostgresStore ─▶ EventStore ─────────────────────────────▶ Codec ─▶ Events
Logging ──▶ Hub / CommandHub / EventStore / Http（包むだけ）
Json ◀── Logs ◀── Logging
```

他の対象は、依存の向きを import を走査する境界テストで固定しました。Flix 版は、同じ種類のテストを書いていません。かわりに、**モジュールごとに、効果と Java への依存を数えました。**

| モジュール群 | `\ IO` の注釈 | Java の `import` |
| :--- | :--- | :--- |
| `Foundation`、`Domain`、`Errors`、`Events`、`Replay`、`Transition`、`Commands`、`Projection`、`Validate` | 無し | 無し |
| `Html`、`Http`、`Hub`、`QueryHub`、`CommandHub`、`EventStore`、`Codec`、`Logs`、`Converter`、`Profunctor`、`Lookup`、`Process`、`Logging` | 無し | 無し |
| `Json` | 無し | 1（`Character` だけ） |
| `JdkServer` | あり | 6 |
| `PostgresStore` | あり | 9 |

数えた方法は、`\ IO` を含む行と、`import java` などで始まる行を `grep` で数えただけです。**これはテストではなく、数えた結果です。** ただし、第 1 章で見たとおり、注釈の無い関数が Java を呼べば、コンパイルが拒否します。Java を呼ぶ関数は、注釈に `IO` が現れるか、後で見る例外に当たります。

### 効果の境界

副作用は、決まった場所にだけ置きました。

| 場所 | 効果 | 章 |
| :--- | :--- | :--- |
| HTTP サーバー | `IO`（Java 相互運用） | 2 |
| PostgreSQL | `IO`（Java 相互運用） | 9 |
| コマンド処理の文脈 | 効果 `EventLog`（ハンドラで与える） | 10 |
| ログ | 標準の効果 `Logger` | 12 |
| インメモリのストア | 領域の効果 `r`（外からは純粋） | 6 |

最後の領域の効果は、他と性質が違います。書き換えられる箱を使っていても、箱が領域の外に出ないので、外から見た関数は純粋です。

### 5 つの代数構造と、その確かめ方

連載で名前を付けた代数構造を、どの章のどのテストが確かめているかを数えました。

| 構造 | 章 | 対応するテスト |
| :--- | :--- | :--- |
| モノイド | 5 | `TestTransition`（結合律、単位元、畳み込みの等価）。標準の `Monoid` のインスタンス |
| ファンクタ | 7、8 | `TestResultFunctor`、`TestQueryFunctor` |
| モナド | 9 | `TestResultMonad`（左単位元、右単位元、結合律） |
| アプリカティブ | 11 | `TestApplicativeLaws`（`forA` に求める性質） |
| プロファンクタ | 12 | `TestProfunctor`（`dimap` の恒等則と合成則。束ねた `Converter` には `imap` だけ） |

アプリカティブは、則そのものを一般の形でテストしたのではなく、`forA` に求める性質を確かめました。

確かめていないことがあります。既存の 3 対象は、法則を壊して何回検出するかの率を数えています（[ADR-017](../../../adr/ADR-017-own-property-testing.md)）。Flix 版は、**検出率を数えていません。** 壊れた実装を 1 つずつ用意して、見分けられることは示しました（第 5、7、9、11、12 章）。しかし、率にはしていません。

## コードへの翻訳

### 型で表した判断

設計の判断は、型と関数の形になりました。入口は、関数値を持つレコードです。

```flix
    pub type alias ToDoListHub[ef: Eff] = {
        getList = (User, ListName) -> Result[ZettaiError, ToDoList] \ ef
    }
```

```flix
    pub type alias EventStore[ef: Eff] = {
        load = Unit -> Result[ZettaiError, Versioned] \ ef,
        append = (Int32, List[ToDoListEvent]) -> Result[ZettaiError, Unit] \ ef
    }
```

どちらも、効果を型引数に取ります。関数を 1 つずつ包めるので、ログのデコレータは、この形のおかげで足せました（第 12 章）。

### 他の対象との違い

同じ Zettai を、4 つの言語で書きました。確かめられた違いを並べます。

| 論点 | Kotlin | Kotlin FP | Flix |
| :--- | :--- | :--- | :--- |
| 失敗の型 | 自前の `Outcome` | Arrow の `Either` | 標準の `Result` |
| 文脈の持ち回り | 自前の `ContextReader` | 型引数 `Tx` と関数の引数 | 効果 `EventLog` とハンドラ |
| 複数の誤り | 自前の `Validation` | `Either.zipOrAccumulate` | 標準の `Validation` と `forA` |
| JSON | 自前の `Converter` | `JsonElement` の木と自前の `Encoder` / `Decoder` | 自前の木（標準に無い） |
| ログ | （比較していない） | decorator と filter | decorator と標準の `Logger` 効果 |

この表の Kotlin と Kotlin FP の列は、既存の記事と[横断比較](../comparison/index.md)に書かれたことに基づきます。それらのコードを、この章のために読み直して確かめたものではありません。なでしこ3 と Rust の行は、並べていません。

### 採用しなかった道具、試していない道具

| 道具 | 扱い | 理由、または比べていない旨 |
| :--- | :--- | :--- |
| Cucumber | 試していない | Flix でアノテーション付きクラスを定義する手段が、公式ドキュメントに見つからなかった（ADR-046） |
| Jackson などの JSON ライブラリ | 試していない | 載せるものを型で決める方針と合わないと判断した。比べていない（ADR-048） |
| SLF4J などのログの枠組み | 試していない | 標準の `Logger` で足りた。比べていない（ADR-048） |
| プロパティテストのライブラリ | 調べていない | 小さな範囲の全パターンを並べた（第 5 章） |
| Nix の devShell | Docker 上の Nix で確かめた | `nix develop --command` から `flix test` が動く（2026-11-02）。Linux の Nix だけで、他の OS の Nix は確かめていない |

## 最後の考察

### 扱わなかったこと

| :--- | :--- | :--- | :--- |

| 2 | CSRF 対策 | 11 | 扱っていない。名前を変える `POST` にトークンは無い |
| 3 | 読み取りモデルの永続化、スナップショット | 8、9 | 扱っていない。読むたびにイベントを畳み込む |
| 4 | 競合したときの自動の再試行 | 10 | 扱っていない。`VersionConflict` を返すところまで |
| 5 | ログの保管期間とアクセス権 | 12 | 扱っていない。利用者名とリスト名が載るので、運用で守る必要がある |
| 6 | 分散トレース、メトリクスの収集基盤、相関 ID | 12 | 扱っていない |

| 13 | Java の呼び出しの効果の分類 | 9、10、12 | 一部が `IO` にならない理由を確かめていない（下で述べる） |

1 番目が、いちばん重大です。認証が無いので、Zettai は、誰でも誰のリストでも操作できるアプリケーションです。

### 問いに答える

**問い 1: 副作用を型で追跡すると、核と殻の分離は楽になるか。**

楽になった場面があります。

- ドメインの関数に `println`、Java の呼び出し、`Logger` を足すと、コンパイルが拒否しました（第 1、2、12 章）。他の対象で import を走査するテストや規約で守っていたことを、型検査が肩代わりしました。
- 足したケースの更新漏れを、`Non-exhaustive match` が数えました（上の表）。

楽にならなかった場面もあります。

- 効果の注釈は、不足しても余っても拒否されます。純粋な関数を `IO` を期待する場所に渡せず、使っていない `IO` も宣言できません（第 2 章）。厳密な代わりに、枠に入れる補助関数 `inIO` のような書き方が要りました（第 3 章）。
- エラーメッセージは、原因の位置を指さないことがありました。レコードの一部のフィールドが純粋なままだと、レコード全体の位置で効果の不一致が報告されました（第 3 章）。

**問い 2: Java 相互運用の境界で、保証はどこまで届くか。**

届かない場所を、3 つ見つけました。

- Java が呼ぶコールバックの中身は、`start` の型から見えません。引数の効果が、起動の型に現れませんでした（第 2 章）。
  取りこぼした効果は、型検査で警告されません。`Logger` を外側で処理すると、コンパイルは通り、実行時に応答が黙って消えました（第 12 章）。
- `Logger` の処理は、サーバーのコールバックの内側に置く必要がありました（第 12 章）。
- Java の呼び出しの効果は、**一律ではありませんでした。** 公式ドキュメントの「Java とのやりとりは常に `IO`」と合わず、`Objects.isNull`、`Throwable.getMessage`、`Character.hashCode` は `IO` と判定されず、`System.currentTimeMillis()` と `getSQLState()` は `IO` でした。理由は確かめていません。**型の保証は、コンパイラの分類が正しいことに依存します。**

境界の外へ出す手段は、**例外を値にする**ことでした（第 9 章）。`SQLException` を `Result` の失敗にしたので、境界の内側では、例外が型の外に出ません。

**問い 3: 効果多相や効果ハンドラは、関数型 DI の代わりになるか。**

第 4 章で、同じ `route` を関数値のレコードと効果ハンドラの両方で書き、同じ結果を返すことを確かめました。第 10 章では、コマンド処理の文脈を、引数ではなく効果で与える `Process` を作り、156 通りのコマンド列で、引数で渡す版と同じ結果を返しました。

代わりになる、と言える場面はあります。

- 文脈（接続とトランザクション）の持ち回りは、効果ハンドラで足りました。`ContextReader` に当たる型を作らずに済みました（第 10 章）。
- ハンドラを忘れると、型検査が拒否します（第 4 章）。

一方で、連載の本流では、関数値のレコードを採りました。他の対象と形を揃えて比べられることが理由です。**代わりになるが、置き換えなければならない理由は、見つかりませんでした。**

要するに、こう言えます。副作用を型で追跡すると、**守りたいことの一部を、規約からコンパイラに移せました。** 移せなかったのは、効果の分類そのものの正しさと、境界の置き方、載せないものの決め方です。

これは、1 つの題材、1 つの実装、1 つのバージョン（Flix 0.79.0）での観察です。一般論として言える根拠は、ありません。

### 5 つの実装を並べて

連載は、5 つの実装を書きました。Kotlin、Kotlin FP、なでしこ3、Rust、Flix です。共通の問いは、**言語が与えるほど、設計は楽になるのか**でした。

Flix 版の答えは、他の版と同じ形をしています。決めることが変わります。

| 減ったこと | 減らなかったこと |
| :--- | :--- |
| 副作用の置き場所を守る規約（型検査が肩代わり） | 境界の置き方（トランザクション、競合） |
| 失敗の型・複数の誤りの型を作ること（標準にある） | 載せないものの決め方（ログ） |
| 更新漏れを人が探すこと（`match` が数える） | 何を比べて何を比べなかったかの記録 |

## 連載を終えて

13 章、25 の本番モジュール、3 件の ADR、159 件のテスト。

実装の途中で、テストが見つけた欠陥が 3 つありました。

| 章 | 欠陥 | 見つけたもの |
| :--- | :--- | :--- |
| 8 | 状態の適用が、同じ説明の項目すべてを変えていた（コマンドの判断は最初の 1 件だけを見ていた） | 同じ説明の項目が 2 つあるテスト |
| 12 | JSON の読み込みが、`Int32` の最小値を読めなかった | 境界値を入れた往復のテスト |
| 12 | コマンドの入口の `current` のログが、内側を 2 回呼んでいた | 読み出しの記録が 2 回出ることを確かめるテスト |

どれも、型検査では見つかりませんでした。型が守ってくれるものと、テストでしか守れないものがあります。

最後に、この連載で繰り返した言葉を置きます。

> 必要な強さを選ぶ。
