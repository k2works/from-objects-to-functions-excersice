# Unit 5 のふりかえり（KPT）- Zettai 連載（Kotlin FP 版）

## Keep

- 実装の前に、データモデル設計と ADR を置きました。スキーマ、`entity_id` の符号化、`payload` の形が先に決まり、実装の迷いが減りました。
- 未解決の仮定を、使い捨てのスパイクで測ってから ADR にしました。`jsonb` の正規化、`jsonb_build_object` の往復、`use` と Arrow の `Resource` の後始末、`Dispatchers.IO` のスレッドは、どれも推測ではなく実測です。
- テストが本当に効くかを、実装を壊して確かめました。`entity_id` のエスケープを外すと衝突のテストが落ち、Cucumber の PostgreSQL 経路でテーブルを空にするとその経路が落ちました。
- 境界テストが、ADR で決めた判断との食い違いを検出しました。adapter は `Dispatchers.IO` を使うのに、テストは coroutine の import 全体を禁じていました。禁じるのは `runBlocking` だけと直しました。
- 5 観点レビューと再レビューが、実装と記事の食い違いを公開前に見つけました。HTTP の 500 が「見つからない」に紛れる経路、query の型についての記事内の矛盾、強すぎる断定が該当します。
- Unit 4 のふりかえりの Try（ADR を着手前に作る、受入条件を成功側と失敗側の対にする、計画用語を記事に書かない）を計画に反映できました。

## Problem

- 受入条件を片側しか検証しない問題が、Unit 4 に続いて再発しました。`persist` の成功側を assert していない、Cucumber の HTTP 経路が 500 を見逃す、「他の集約が混ざっても」のテストが混ぜていない、が高 2 件と中 2 件になりました。対の表を計画に置いただけでは、テストを書く段階で守れませんでした。
- 1 つの module に 2 つの章を持つため、第 8 章のコードが第 9 章で変わりました。第 8 章を書く時点で、後で `Either` に変わる型を一覧していませんでした。記事の中で「query は `Either` を返す」と「失敗しない `List` を返す」が矛盾しました。
- 記事に、確かめていないことを断定する書き方が混ざりました。「必ず失敗します」「何も残りません」「再起動してもリストが残る」は、レビューで弱めました。
- Docker を前提にすることの案内が不足していました。第 8 章の実行コマンドが、実際には Docker を必要としていました。
- 計画のタスク 5-1.0（`gulp mkdocs:build` を CI と同じ判定にするか）は、Unit のクローズ時には実施せず、停止フックの指摘を受けて後から実施しました。Docker が無い環境での失敗メッセージは確認できませんでした。Testcontainers が接続方法を記憶するため、環境変数では再現できませんでした。
- `/goal` に従い自律的に進めたため、計画の停止 6 箇所で、人の判断を同期的には求めませんでした。ADR は Unit のクローズ後に人が承認しましたが、データモデルの差分は `draft` のままです。
- 一時スクリプトを、複雑な引用を含むままインラインで実行し、何度か失敗しました。ファイルに書いて実行する方が確実でした。

## Try

- 受入条件の対の表を、テストを書く前に「成功側」「失敗側」「端の経路（HTTP、adapter）」の 3 列にし、各セルにテスト名を書きます。
- 記事の断定表現（必ず、何も、すべて）は、対応するテスト名を示せるものだけに使います。
- 1 つの module に 2 つの章を持つ Unit は、前半の章を書く前に、後半で変わる型を一覧します。前半の記事に「第 N 章で変わる」を先に書きます。
- 第 10 章の着手前に、次を計画に入れます。
  - port の Left の型を広げる
  - 並行競合の再現から始める（テストを先に書く）
  - `Resource` の採否
  - 5-1.0 の判断
  - push 後の CI の確認
- 一時スクリプトは、ファイルに書いてから実行します。
- 人の判断を同期的に求める停止点は、`/goal` のような自律実行でも、データベースのスキーマと新しい ADR の 2 点は承認の記録を残します。
