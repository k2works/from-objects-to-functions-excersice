# 第 11 章 アプリカティブによるデータバリデーション

## ToDoリストの名前変更

これまで画面は読むだけでした。第 11 章で**初めて画面から書きます。**

業務の言葉で書いたシナリオはこれです。

```nako3
●(操作で)シナリオ_リスト名変更
    変更F=操作["リスト名変更"]
    経路表示=操作["経路名"]
    結果=変更F(「uberto」,「book」,「reading」)
    「{経路表示}: リスト名を変えられる」と(結果の成功判定)と真で検証
    「{経路表示}: 変更後の名前で 3 件見られる」と(結果["値"]の要素数)と3で検証
ここまで
```

もう 1 つ、断られる方も書きます。

```nako3
●(操作で)シナリオ_空名前拒否
    変更F2=操作["リスト名変更"]
    経路表示2=操作["経路名"]
    結果2=変更F2(「uberto」,「book」,「」)
    「{経路表示2}: 空の名前は断られる」と(結果2の成功判定)と偽で検証
    「{経路表示2}: 断る理由は 1 件」と(結果2["理由列"]の要素数)と1で検証
ここまで
```

**`理由列` という名前に注目してください。** 理由が 1 つではなく並びです。ここがこの章の主題です。

走らせると赤になります。

```bash
  ok ドメイン直接: 無いリストの項目は 0 件
[実行時エラー].../test/step4/ddt/scenario.nako3(31行目): TypeError: __self.__vars.get(...) is not a function
```

操作の辞書に `リスト名変更` が無いので、取り出した値が関数ではありません。**型が無い言語の Red はこういう形で出ます。** 「そのキーは辞書に無い」ではなく「関数ではないものを呼んだ」と言われます。

## 2 つのパラメータを持った検証

名前を変えるとき、確かめたいことが 2 つあります。

1. 利用者名が空でない
2. 新しいリスト名が空でなく、長すぎない

第 7 章の結果（`outcome.nako3`）でこれを書くと、こうなります。

```nako3
●(結果にFを)結果連鎖
    # F は「値を受け取って結果を返す」関数。失敗はそのまま素通しする。
```

**失敗はそのまま素通しします。** つまり利用者名が空だった時点で止まり、リスト名は見ません。画面には「利用者名が空です」だけが出て、直して送り直すと今度は「名前が空です」と言われます。

**2 往復させたくありません。**

理由が 1 つしか入らないのは、失敗の形がそうなっているからです。

```nako3
●(理由で)失敗
    {"成功":偽,"理由":理由}で戻る
ここまで
```

`理由` は 1 つです。並びにする別の形を用意します。

```nako3
●(値で)検証結果成功
    {"成功":真,"値":値}で戻る
ここまで

●(理由列で)検証結果失敗
    {"成功":偽,"理由列":理由列}で戻る
ここまで
```

**`成功` のキーは同じにしました。** 第 7 章の `成功判定` がそのまま使えます。違うのは失敗側だけです。

型が無いので、2 つの形が混ざる危険があります。**契約テストで形そのものを確かめます。**

```nako3
失敗例=["EmptyName"]で検証結果失敗
「失敗は成功判定が偽」と(失敗例の検証結果判定)と偽で検証
「失敗は理由を並びで持つ」と(失敗例["理由列"]の要素数)と1で検証
```

## バリデーションを使った検証

2 つの検査を書きます。どちらも**単独で**動きます。

```nako3
●(候補の)空名前検査
    もし、(候補の文字数)=0ならば
        (["EmptyName"]で検証結果失敗)で戻る
    ここまで
    候補で検証結果成功で戻る
ここまで

●(利用者候補の)利用者名検査
    もし、(利用者候補の文字数)=0ならば
        (["EmptyUser"]で検証結果失敗)で戻る
    ここまで
    利用者候補で検証結果成功で戻る
ここまで
```

この 2 つを**つなぐのではなく、並べて**まとめるのが結合です。

```nako3
●(利用者候補と候補で)名前変更検査
    # 2 つのパラメータを独立に確かめる。両方だめなら理由が 2 件返る。
    利用者側=利用者候補の利用者名検査
    名前側=候補のリスト名検査
    組F={関数}組作成
    結合2=利用者側と名前側に組Fを検証結果結合
    結合2で戻る
ここまで
```

**「利用者側の結果を使って名前側を決める」ということをしていません。** 2 つは互いを知りません。だから片方が失敗しても、もう片方は最後まで走ります。

結果はこうなります。

```nako3
両NG=「」と「」で名前変更検査
「2 つともだめなら理由は 2 件」と(両NG["理由列"]の要素数)と2で検証
「1 件目は利用者の理由」と両NG["理由列"][0]と「EmptyUser」で検証
「2 件目は名前の理由」と両NG["理由列"][1]と「EmptyName」で検証
```

### つまずき 1: 仮引数の名前が関数名とぶつかった

最初、仮引数を `検証` と書きました。

```bash
[文法エラー].../src/step4/validation.nako3(20行目): 関数『validation__検証結果判定』の定義で以下のエラーがありました。
[文法エラー].../src/step4/validation.nako3(21行目): 関数『helper__検証』の引数が不足しています。
```

**`検証` はテストヘルパの関数名です。** 第 10 章で `文脈` を仮引数にして同じことが起きました。2 度目なので、制約の一覧に「仮引数の名前が既存の関数名と同じだと文法エラーになる」を足しました。仮引数を `対象` に変えて通りました。

### つまずき 2: 並びどうしの `&` は連結ではない

理由列を連ねるところを、最初はこう書きました。

<!-- code-check: ignore わざと壊したコード -->

```nako3
理由列=理由列&対象A["理由列"]
```

テストの出力です。

```bash
  FAIL 両方だめなら理由は 2 件: 値が違う 実際=16 期待=2
  FAIL 1 件目は左の理由: 値が違う 実際=E 期待=EmptyName
```

**`&` が並びを文字列にしていました。** 要素数 16 は `"EmptyNameTooLong"` の文字数で、`[0]` は `"E"` です。1 件ずつ足す形に直しました。

```nako3
    # 並びどうしの `&` は文字列にしてしまうので、1 件ずつ足す（既知の制約 21）。
    理由列=[]
    もし、A可否=偽ならば
        左列=対象A["理由列"]
        もし、(左列の要素数)>0ならば
            Iを0から(左列の要素数)-1まで繰り返す
                理由列に左列[I]を配列追加
            ここまで
        ここまで
    ここまで
```

**型があれば `List<String> & List<String>` は書いた時点で止まります。** ここでは走らせて、数字が `16` だったので気づきました。

### 2 つの条件を独立に、と言いながら

リスト名の検査は「空でない」と「40 文字以内」を結合しています。

```nako3
●(候補の)リスト名検査
    # 空でないことと 40 文字以内であることを結合する。
    空側=候補の空名前検査
    長側=候補の長名前検査
```

**この 2 つが同時にだめになることはありません。** 空文字列は 40 文字以内だからです。結合しても理由は必ず 1 件です。

正直に書いておきます。**ここで結合を使う意味は、集約ではなく形を揃えることだけです。** 集約が効くのは、上の `名前変更検査` のように**別のパラメータ**を並べたときです。

## アプリカティブファンクタの結合

法則を確かめます。第 5 章（モノイド）・第 7 章（ファンクタ）・第 9 章（モナド）と同じやり方です。

```nako3
「検証の恒等則が {試行回数} 回とも成り立つ」と恒等失敗と0で検証
「検証の合成則が {試行回数} 回とも成り立つ」と合成失敗と0で検証
「成功どうしの結合が {試行回数} 回とも素直な適用と等しい」と適用失敗と0で検証
```

もう 1 つ、アプリカティブの肝そのものを性質にしました。**失敗の数が保たれること**です。

```nako3
「失敗の数が {試行回数} 回とも保たれる」と保存失敗と0で検証
```

左右のどちらが失敗しても、その理由は必ず結果に残ります。落とすことがあれば赤になります。

### 壊してから信じる

[ADR-017](../../../adr/ADR-017-own-property-testing.md) に従い、法則を壊して検出率を測ります。壊し方は「右側を見ない」です。

```bash
  ok 壊した結合は 200 回中 100 回以上で検出される
検出率（左だけを見る壊し方）: 115 / 200
```

200 回中 115 回。全部ではありません。**左が失敗していれば、右を見なくても結果は同じ**だからです。壊れているのに気づけない入力が理屈のうえで存在し、実測もそのとおりでした。

### モナドとの違いを数字で出す

この章でいちばん出したかった数字です。同じ検証を結果連鎖（モナド）で書きます。

```nako3
●(利用者候補と候補で)名前変更検査_連鎖版
    利用者側=利用者候補の利用者名検査
    変換=利用者側の検証結果変換
    名前側=候補のリスト名検査
    もし、(変換の成功判定)=偽ならば
        # 最初の失敗で止まる。名前側は見ない。
        ([変換["理由"]]で検証結果失敗)で戻る
    ここまで
```

両方だめな入力を乱数で作り、2 つの書き方で理由の件数を比べます。

```bash
  ok 両方だめな入力では連鎖が必ず見落とす
見落率（連鎖）: 69 / 69（両方だめだった回数）
```

**100% です。** 両方だめだった 69 回すべてで、連鎖版は理由を 1 件しか返しませんでした。

これはバグではありません。**連鎖は「前の結果を受けて次を決める」ものなので、前が失敗したら次を決められない**のです。できないことをしているのではなく、そもそも違うものです。

| | 結果連鎖（モナド） | 検証結果結合（アプリカティブ） |
| :--- | :--- | :--- |
| 次の処理 | 前の値に依存できる | 依存できない |
| 失敗したとき | そこで止まる | 最後まで走る |
| 理由の数 | 1 件 | だめだった数だけ |
| 向くもの | 読む → 判断 → 書く（第 10 章） | 画面の入力の検証（この章） |

**依存できないという制限の見返りが、集約です。** 第 10 章で境界を作ったときは連鎖が正しく、ここでは結合が正しい。どちらが上ということはありません。

## ユーザインタフェースの改善

画面が 2 つになりました。第 2 章から文字列の連結で作ってきましたが、限界です。

**骨組みと値を分けます。**

```nako3
●名前変更雛形
    『<html><body><h1>{{リスト名}} の名前を変える</h1>{{エラー}}<form method="post" action="{{変更URL}}"><input type="text" name="newname" value=""><button type="submit">変える</button></form></body></html>』で戻る
ここまで
```

**`『』` で書いています。** `「」` は中の `{...}` を式として展開するので、`{{リスト名}}` を書いた時点で字句解析エラーになります。

```bash
[字句解析エラー]...: 展開あり文字列で値の埋め込み{...}が対応していません。
```

制約の一覧に 23 件目として足しました。

### 埋めそこねを実行時に止める

Kotlin 版はテンプレートに渡す値をデータクラスで受けるので、渡し忘れはコンパイラが止めます。**この版には型がありません。** 渡し忘れると画面に `{{リスト名}}` がそのまま出ます。

そこで、埋め終えた後に検査します。

```nako3
    残=出力で『{{』が何文字目
    もし、残>0ならば
        # 渡し忘れ。ここで止めないと、画面に `{{...}}` がそのまま出る。
        (「TemplateNotFilled」で失敗)で戻る
    ここまで
    出力で成功で戻る
```

失敗の理由を 1 つ増やしたので、契約テストも増えます（[ADR-018](../../../adr/ADR-018-outcome-dict-port.md) の網羅の約束）。

```nako3
「失敗の理由は 6 種類」と(一覧の要素数)と6で検証
「TemplateNotFilled がある」と(一覧で「TemplateNotFilled」の出現回数)と1で検証
```

値は骨組みに入る前に無害化します。

```nako3
●(素の)HTML安全化
    # 値は骨組みに入る前に無害化する。骨組みだけがタグを持てる。
    文字=「{素}」
    文字=文字の「&」を「&amp;」に置換
    文字=文字の「<」を「&lt;」に置換
```

**穴が 1 つ残っています。** 項目の並び（`<li>...</li>`）は骨組みなので、無害化を通さず先に差し込んでいます。

```nako3
    # 項目行は骨組みなので、無害化されないよう先に埋める必要がある。
    # テンプレート適用は値を無害化するため、ここでは自前で差し込む。
```

差し込む値がドメイン由来であることに依存しています。[ADR-022](../../../adr/ADR-022-template-with-unfilled-check.md) の「解かないこと」に書きました。

### 画面から書く

`GET` はフォームを出すだけ、`POST` が実際に変えます。成功したら新しい名前の画面へ送ります（PRG）。

```nako3
    # 成功したら新しい名前の画面へ送る（PRG）。
    {"状態":302,"移動先":「/todo/{利用者}/{新名}」,"本文":""}で戻る
```

検証に落ちたら、**理由を全部並べて** 400 で返します。

```nako3
    検査=利用者と新名で名前変更検査
    もし、(検査の検証結果判定)=偽ならば
        描画=旧名とURLと検査["理由列"]で名前変更画面描画
```

### つまずき 3: 変数名が組み込み命令とぶつかった（4 度目）

エラーの一覧を組み立てる変数を `表示` と名付けました。

```bash
[文法エラー]src/step4/web.nako3(123行目): 関数『表示』に代入できません。
```

`合計`（第 4 章）、`倍`（第 7 章）、`コマンド実行`（第 10 章）に続いて 4 度目です。**制約の一覧に載せていても防げない種類**でした。`誤り欄` に変えて通りました。

### つまずき 4: POST の経路を絞っていなかった

受け入れシナリオを HTTP 経由でも走らせようとして、`curl -L` で POST しました。返ってきたのは 400 で、画面にはこう出ていました。

```bash
<h1>undefined の名前を変える</h1><ul class="errors"><li>ListAlreadyExists</li></ul>
```

2 つのことが起きていました。

1. **`curl -L` は 302 のあとに POST を送り直す**ことがある。テスト側の問題なので、ブラウザと同じく「POST して、それから送られた先を自分で読む」形にしました
2. **サーバ側が、`/rename` で終わらない POST も名前変更として処理していた。** これは実装の欠陥です

2 は経路の判定を 1 か所に切り出して直しました。

```nako3
●(パスの)名前変更判定
    # /todo/{利用者}/{リスト名}/rename だけを名前変更の経路とする。
    要素=パスのパス分解
    もし、(要素の要素数)≠4ならば
        偽で戻る
    ここまで
    ((要素[0]=「todo」)かつ(要素[3]=「rename」))で戻る
ここまで
```

**受け入れテストを 2 経路で走らせていなければ見つかりませんでした。** ドメイン直接の経路は URL を通らないので、この欠陥に触れません（[ADR-016](../../../adr/ADR-016-own-acceptance-entry.md)）。

最後に 2 経路とも緑になります。

```bash
  ok HTTP経由: リスト名を変えられる
  ok HTTP経由: 変更後の名前で 3 件見られる
  ok HTTP経由: 空の名前は断られる
  ok HTTP経由: 断る理由は 1 件
```

## まとめ

- **失敗を並びで持つ形を、結果とは別に用意しました。** `成功` のキーは揃えたので、第 7 章の `成功判定` がそのまま使えます
- **集約が効くのは、独立した別のパラメータを並べたときだけです。** 「空でない」と「40 文字以内」は同時にだめにならないので、結合しても理由は 1 件です。形を揃える以上の意味はありません
- **モナドとの違いを数字にしました。** 両方だめな入力 69 回すべてで、結果連鎖は理由を 1 件しか返しませんでした。100% の見落としです。これは欠陥ではなく、連鎖が「前の値に依存できる」ことの代償です
- 法則を壊したときの検出率は 200 回中 115 回でした。**左が失敗していれば右を見なくても同じ**なので、全部にはなりません
- **テンプレートの埋めそこねを実行時に止めました。** 型検査の代わりです。ただし項目の並びは無害化を通さず差し込んでおり、穴が 1 つ残っています
- 制約を 3 件足しました（並びの `&`・仮引数と関数名の衝突・`「」` に `{{` を書けない）。**うち 2 件は一覧を読んでも防げない種類**です
- **画面から書く経路を通して、実装の欠陥が 1 つ見つかりました。** `/rename` 以外への POST も名前変更として処理していました。2 経路で走らせていなければ通り抜けていました

次の章では監視と JSON を扱います。ここまで作ったものが**動いているかどうか**を、外から見られるようにします。
