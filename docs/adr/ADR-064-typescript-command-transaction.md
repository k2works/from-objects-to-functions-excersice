# ADR-064 TypeScript FP 版は判断の関数を保管に渡し、ストリームごとのロックで 1 つのコマンドを 1 つのトランザクションにする

日付: 2026-11-28

## ステータス

2026-11-28 推奨案を採用しました（Unit 6 のゲート ①）。**同期停止していません。** 利用者の事前の指示「執筆完了まで、判断はすべて推奨を採用する」によるもので、人が個別に確認してはいません

## コンテキスト

第 9 章では、状態の読み取りと追記が別の操作でした。間に別の更新が入れます。1 つのコマンドの「読む、判断する、追記する」を、1 つのトランザクションにします。

### 先に確かめたこと

`postgres:18-alpine` で、「読んで、無ければ作る」を 2 つ同時に実行する組を、同じリストと別々のリストで、それぞれ 20 組実行しました（行のほとんど無い小さな表）。

| 守り方 | 同じリスト | 別々のリスト | 二重に作られたリスト |
| :--- | :--- | :--- | :--- |
| 何もしない（Read Committed） | 両方が作る 20 | 両方が作る 20 | 20 |
| `SERIALIZABLE` | 片方が 40001 のエラー 20 | **片方が 40001 のエラー 20** | 0 |
| ストリームごとのアドバイザリロック | 片方が「既にある」 20 | 両方が作る 20 | 0 |

`SERIALIZABLE` の別々のリストの失敗は、この小さな表の条件での結果です。行が多い表では、割合が変わる可能性があります。確かめていません。

依存の形では、`Context.Service` にした `Transaction` を `R` に載せる形も確かめました。トランザクションの外での追記は型検査が止めます。ただし、中で取り出した service を、後から `provideService` で渡し直す書き方は、型検査を通ります。

## 決定

1. **ハブの依存の追記を、`update(streams, decide)` にする。** `decide` は、履歴から追記する出来事か失敗を返す純粋な関数。第 9 章までの `persist` は無くす
2. **PostgreSQL では、ストリームごとに `pg_advisory_xact_lock` を、名前の順に取ってから読む。** スキーマは変えない
3. **版の検査と、競合の失敗の型は足さない。** 後から来たコマンドは、前のコマンドの結果を読んで判断し、業務の規則で断られる
4. **対象でないストリームへの追記は defect にする**
5. **業務の失敗では接続を返して使い続け、defect と中断では接続を捨てる**

Unit 6 の計画の受入条件の「競合の検出」は、同時の 2 つのコマンドの片方が業務の理由で断られることで満たします。

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| `SERIALIZABLE` と再試行 | 競合していない更新が失敗した。再試行の仕組みが要る |
| 版の列と一意制約（楽観的な検査） | **試していない。** スキーマの変更が要る |
| `Transaction` を service にして `R` に載せる | 判断は純粋な関数なので、トランザクションの中で任意の処理を実行する必要が無い。判断の関数を渡す形では、ロックして読まずに追記する操作が、依存の型に存在しない |
| コールバックにトランザクションの取っ手を渡す | 取っ手を持ち出せる。判断の関数を渡す形より、守ることが多い |

## 影響

### ポジティブ

- ハブも核も、トランザクションを知らない。`handle` は変わらない
- 読まずに追記する操作が無くなった

### ネガティブ

- **判断の中で、外の情報を読めない。** 判断に別のサービスの呼び出しが要る場合は、この形を見直す
- ロックの鍵は 64 ビットのハッシュ。別のストリームが同じ鍵になると、順に待つ（誤りにはならない）
- ロックを待つ時間の上限は、設定していない
- ロックを取らずに表に書くプログラムがあれば、守られない
- 準備の出来事を入れる専用の追記は無い。テストでは、判断を持たない `update` を使う

## コンプライアンス

- 同じコマンドを同時に実行して、片方だけが受け付けられることを、2 つの保管で確かめる
- 逆の順の 2 つのストリームの更新が、行き詰まらないことを確かめる
- 業務の失敗で、接続を捨てないことを確かめる
