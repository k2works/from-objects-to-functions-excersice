    ADR-019 イベントログを 1 ファイルに追記し、状態を保存しない¶

    日付: 2026-09-28

    ステータス¶

    2026-09-28 提案されました

    コンテキスト¶

    第 9 章で永続化を入れます。Kotlin 版は PostgreSQL の 1 テーブルにイベントを追記します（ADR-008）。

    なでしこ3 の処理系（cnako3）に DB プラグインがありません。 ADR-013 の時点で「第 9 章はファイル永続化に置き換える」と決めていました。本 ADR はその形を確定します。

    加えて、Unit 5 のスパイクで制約が 1 つ分かりました。関数値ごしにファイル I/O を呼ぶと、非同期の組み込み命令が待たれず Promise がそのまま返ります（第 3 章で踏んだ制約と同じ）。Kotlin 版の EventPersister = (List<ToDoListEvent>) -> HubAction<Unit> に相当するポートを、関数値として注入できません。

    決定¶

    イベントログを 1 ファイルに追記します。状態は保存しません。

    1. 形式は 1 行 1 JSON。改行 で区切る
    2. 追記のみ。 更新も削除もしない
    3. 順序を決める唯一の根拠は行の並び。 Kotlin 版の id BIGSERIAL に相当する
    4. 無いファイルは「まだ何も起きていない」。失敗ではなく空の並びで成功を返す
    5. 入出力は src/stepN/store.nako3 1 ファイルに閉じ込める。ドメインは入出力をしない
    6. ポートは「注入される関数値」ではなく「呼び出しの順序」で表す。 読む → ドメインに渡す → 返ったイベント列を書く
    7. 失敗の理由に PersistenceError（500）を足す

    Kotlin 版 ADR-008 との対応¶

    観点 Kotlin 版 なでしこ3 版 同じか
    状態を保存するか しない しない 同じ
    追記のみか そう そう 同じ
    保存先 PostgreSQL の 1 テーブル 1 ファイル 違う
    順序の根拠 id BIGSERIAL 行の並び 形は違うが役割は同じ
    1 件の形 entity_id / event_type / payload（JSONB） 1 行 1 JSON（キーはイベントの辞書そのまま） 違う
    検索の手段 インデックス（entity_id, id） 無い。全行を走査する 違う

    判断は同じで、手段だけが違います。

    Kotlin 版 ADR-009 は不要（記録）¶

    ADR-009 は結合テストの DB を docker-compose と CI のサービスコンテナで用意する判断です。なでしこ3 版では不要です。 外部サービスに依存せず、テストは一時ファイルを作って消すだけです。

    不要であることを、ここに書き残します。 Unit 3・4 で「移植しそこねた ADR」を 2 回見つけており、「対応しない」も判断のうちだからです。

    検討した代替案¶

    案 採らなかった理由
    SQLite などの DB を npm から足す cnako3 から使う手段が確認できていない。連載の主題は永続化の手段ではなく、失敗しうる処理をどうつなぐか（モナド）
    1 ファイル 1 イベント（ディレクトリに並べる） 順序をファイル名で表すことになり、追記より複雑になる
    状態そのものを保存する イベントソーシングをやめることになる。第 5 章からの積み上げが崩れる
    ポートを関数値で注入し続ける できない。 関数値ごしに非同期の命令が待てない

    影響¶

    • 再起動してもデータが残ります。 第 9 章のデモが成立します
    • 入出力が 1 ファイルに閉じます。 ドメインは保存先を知りません。関数型の設計としてはむしろ素直な形です
    • 検索がありません。 読み出しは全行を走査します。件数が増えたときの対処は本連載で扱いません
    • テストは一時ファイルを作って消します。CI に外部サービスが要りません

    この決定が解かないこと¶

    先に書いておきます（Unit 4 のふりかえり Try 1）。

    解かないこと どうするか
    同時書き込み 読んで足して書き戻すので、2 つのプロセスが同時に書くと片方が消える。単一プロセス前提。本連載では扱わない
    途中で落ちたときの整合 書き戻しの途中で落ちるとファイルが壊れうる。トランザクションが無い。第 10 章（ADR-011 の移植判断）で扱う
    件数が増えたときの性能 追記のたびに全文を読んで書き戻す。O(n²) になる。本連載では扱わない
    形式を変えたときの後方互換 1 行 1 JSON なのでキーの追加には強いが、キーの改名や削除には弱い。改名しないという約束で守る

    コンプライアンス¶

    • ドメインのファイルが入出力の命令を使わないこと（境界検査）
    • テストが作ったファイルを残さないこと
    • イベントの辞書のキーを改名しないこと
    • 無いファイルからの読み出しが失敗ではなく空で成功すること

    再検討の条件¶

    1. 同時書き込みが必要になる（利用者が 2 人以上同時に操作する題材になる）
    2. 件数が増えて make check に影響する
    3. cnako3 から使える DB の手段が見つかる
    4. 第 10 章のトランザクションの検討で、ファイルでは表せないと分かる
