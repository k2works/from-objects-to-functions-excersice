    Unit 2 の Bolt 計画（イテレーション 2）- Zettai 連載（TypeScript FP 版）¶

    概要¶

    項目 内容
    イテレーション 2（TypeScript FP 版）
    Unit Unit 2 ウォーキングスケルトンとドメイン分離
    期間 日付は置きません。最初のコミットから完了のコミットまでをリードタイムとして記録します
    Bolt 2-1 第 2 章 / 2-2 第 3 章
    ストーリー US-002、US-003
    局面 序盤（アウトサイドイン）（開発戦略）
    テスト戦略 Standard
    人の検証負荷 13
    承認ゲート 2 箇所

    本計画は 2026-11-27 に人の承認を得ました。 新規ファイルの一覧も承認の対象です。

    上位の計画は リリース計画 です。この Unit の完了が Release v0.1.0 です。

    着手の前提¶

    Unit 1 は完了しました。 第 1 章のコードを含むコミット 7727624 の CI が成功しました。受入条件の例外が 1 件あります（Unit 1 の Bolt 終了報告）。

    承認ゲートの運用形態¶

    本 Unit のゲートは「同期停止」で運用します。

    本節は人だけが書き換えます。 AI は書き換えません。

    # ゲート ステップ 添えるもの 記録先
    ① HTTP の実装方式 2-1.1 下の「HTTP の 3 案」。本計画の承認と同時に判断できます ADR-056
    ② 受け入れテストの経路の差し替え方 2-2.1 driver を置く層の候補ごとの行数と、HTTP の経路で確かめられる範囲 ADR-057

    目標は、2 箇所とも同期停止することです。CI と実行環境の追加、データベースのスキーマ変更、永続化の形式の変更は、ゲートと別に必ず停止します。本 Unit では、どれも予定していません。

    持ち込み¶

    Unit 1 のふりかえりの Try と、Bolt 終了報告の持ち越しを反映します。

    # 持ち込み 消化するステップ
    1 承認を求める設定やスクリプトは、先にスクラッチで実行してから提示する 2-1.1、2-2.1
    2 品質ゲートは、追跡ファイルだけを取り出した場所でも確かめてから、コミットする 2-1.5、2-2.5
    3 章を書く前に、執筆規約の「対象ごとの差分」を読み、受入条件に加える 2-1.4、2-2.4
    4 バックスラッシュを含むスクリプトは、ファイル作成ツールで書く 全ステップ

    US-002: ToDo リストを HTTP で見る¶

    読者として、HTTP の縦串を動かしたい。

    # 受入条件
    1 GET /todo/{user}/{listname} が、存在するリストの項目を HTML で返す
    2 存在しないリスト、知らないパス、GET 以外のメソッドは、404 を返す
    3 壊れた URL エンコードへの応答が決まっていて、テストで固定されている
    4 日本語の名前を扱え、HTML の中の値がエスケープされる。応答の content-type に charset がある
    5 サーバーを起動しないテストと、実サーバーを起動する smoke の両方が通る
    6 domain のコードは、HTTP と effect/http、Node の module を import しない
    7 Effect の実行は、最外周とテストだけにある

    US-003: 同じ受け入れシナリオを 2 経路で実行する¶

    読者として、同じ受け入れシナリオを経路を変えて実行したい。

    # 受入条件
    1 シナリオは、業務の言葉の操作だけで書かれている
    2 同じシナリオが、domain を直接呼ぶ経路と、HTTP の経路で通る（ADR-055）
    3 HTTP の経路は、実サーバーを起動し、HTML から値を取り出す
    4 経路の選択は、テストのコードだけにある
    5 domain の依存の向きを、テストで固定している

    経路の差し替え方の比較（2026-11-27）¶

    同じ 2 つのシナリオ（自分のリストの項目が順に見える、他の利用者のリストは見えない）を、domain と HTTP の 2 経路で書きました。項目には milk & <bread> を含めました。HTTP の経路は実サーバーを起動し、HTML から項目を読み戻します。読み戻しは、200 と 404 のほかの状態と、エスケープされていない値を失敗にします（3 案で共通）。スパイクのファイルは step 2 のテストに一時的に置き、実行後に削除しました。

    案 形 経路の定義 シナリオ
    A Promise を返す driver を、高階関数 (store, use) => Promise<A> で渡す 35 行 29 行
    B driver を Context.Service にし、経路を Layer で差し替える 35 行 27 行
    C Effect を返す driver を、Scope を要求する Effect で作る 31 行 32 行

    行数は整形後の、空行とコメントを除いた数で、共通の読み戻し（page.ts・http.ts）を含みません。3 案とも型検査と lint が通り、正しい実装で 4 件が通りました。

    わざと壊した実装 失敗した経路（3 案で同じ）
    HTML が最後の項目を落とす HTTP だけ
    HTML のエスケープを忘れる HTTP だけ
    利用者を見ずにリストを返す domain と HTTP
    無いリストで 500 を返す HTTP だけ
    • HTTP の経路の driver で操作名を書き間違えると、3 案とも型検査が失敗しました
    • 検出できる範囲に、3 案の差はありませんでした。 差は書き方です
    • A は、1 つのシナリオを 1 回の起動の中で async・await で書きます。サーバーの後始末は、経路の実装の中の Effect.scoped が担います（ゲートの説明の訂正（実装の後に確認）: Effect.scoped を忘れると型検査が失敗します。型で止まらないのは、閉じないスコープを渡した場合です）
    • B と C のシナリオの補助は、操作ごとに Effect を実行するため、HTTP の経路は操作のたびにサーバーを起動します。 複数の操作を続けるシナリオは、全体を 1 つの Effect に書く必要があります
    • 確かめていないこと: 状態を変える操作を含むシナリオ（第 6 章以降）、失敗したシナリオでの後始末
