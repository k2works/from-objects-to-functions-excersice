# ADR-021 文脈を保存先の指し先として表し、組み立てない

日付: 2026-09-28

## ステータス

2026-09-28 提案されました

## コンテキスト

Kotlin 版は [ADR-011](ADR-011-transaction-boundary.md) で、トランザクションの境界をコマンド 1 つの処理に置き、文脈（`TxContext`）を**不透明な型**にしました。`ContextReader` は「文脈を受け取って値を返す計算」を値として持ち、組み立ててから最後に文脈を渡します。

なでしこ3 版には、その形をそのまま持ち込めない事情が 2 つあります。

1. **関数値ごしに非同期な組み込み命令を呼ぶと、待たれずに Promise が返る。** 第 3 章・第 7 章・第 9 章で 3 度踏んだ制約です（`README.md` の既知の制約 1）。`ContextReader` の中核は「入出力を含む計算を値として持ち回る」ことなので、この制約に正面からぶつかります
2. **ファイルにトランザクションがありません。** [ADR-019](ADR-019-file-event-log.md) は追記型のイベントログを選んでおり、`TxContext`（DB 接続）に相当するものが存在しません

「文脈と呼べるものが無い言語で、この章をどう書くか」から決める必要がありました。

## 決定

**文脈を「どこを読み書きするか」を持つだけの値とし、計算は組み立てません。**

1. 文脈は保存先の指し先（ファイルのパス）を持つ辞書とする。接続でもトランザクションでもない
2. 読み書きは文脈を通す。`文脈内読出`・`文脈内追記`・`射影問合` を `store.nako3` と `tx.nako3` に置く
3. 境界は `文脈内コマンド実行` に置く。**読む → 判断する → 書く**を 1 つの関数に閉じ込め、途中で失敗したら書かない
4. ドメイン（`domain`・`events`・`outcome`・`commands`・`projection`・`validation`・`template`）は文脈の中身を知らない。境界テストで守る

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| `ContextReader` をそのまま移植する | 関数値ごしの非同期が待たれない。3 度踏んだ制約で、回避策が無い |
| 文脈を大域変数にする | 読み書きの位置が追えなくなる。どの関数が保存先に触るかがテストで分からない |
| 文脈を使わず、各アダプタが直接ファイルを開く | 第 9 章の形に戻る。境界がどこにあるかを記事で示せない |
| 追記の前にロックを取り、原子性を確保する | この連載の主題ではない。解かないことに挙げて明示する（下表） |

## 影響

- **境界が呼び出しの順序として読めます。** `文脈内コマンド実行` を読めば、どこまでが 1 つの単位かが分かります
- **Kotlin 版との差がはっきりします。** 向こうは「計算を組み立てて最後に文脈を渡す」、こちらは「文脈を渡して順に実行する」。第 13 章の対比の材料になります
- 文脈が増えても（別のファイル、別の保存先）呼び出し側は変わりません

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| **原子性** | 書き込みの途中で落ちればファイルは壊れます。保証できるのは「判断が失敗したら 1 行も書かない」ことだけです。第 10 章の本文に明記しました |
| **同時実行** | 2 つの要求が同時に追記した場合の順序は決めていません。[ADR-019](ADR-019-file-event-log.md) で解かないことに挙げた項目のままです |
| **計算の組み立て** | 入出力を含む計算を値として持ち回ることは、この処理系ではできません。**できないことを章の主題にしました**（[第 10 章](../article/zettai/nadesiko/chapter10.md)） |

## コンプライアンス

- ドメインのファイルが文脈の中身（保存先のキー）を読まないこと（`test/stepN/boundary_test.nako3`）
- 書く経路が `文脈内コマンド実行` を通ること
