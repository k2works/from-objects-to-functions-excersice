## 検証の不確実性が HIGH だった項目の結果

計画で「検証の不確実性 HIGH の原因を数字で確かめる」としていました。

| 指標 | 計画 | 実績 |
| :--- | :--- | :--- |
| 結合テストの連続 green 回数 | 3 / 3 | **3 / 3** |
| CI の実行時間（`clean check`） | 5 分以内 | **48 秒** |
| DDT の経路数 | 3 | **3（27 ステップ）** |

**不安定さは出ませんでした。** 安定した理由は 2 つあると考えます。

1. `docker-compose.yml` と CI のサービスコンテナに**同じ `healthcheck`** を置いた。起動直後に接続を試みて落ちるのを防いだ
2. テストごとに `TRUNCATE` し、DDT の各シナリオでも `prepare()` で消した。**データ残留を最初から想定した**

結合テストを `check` に含めたまま 48 秒なので、別ジョブに分ける必要はありませんでした。

## 判断と学び（ジャーナルへ転記）

### 1. 試してから「入れない」と決めた

ADR-004 の再検討で、**ktlint を実際に導入して動かしました。** その結果、標準ルールが引数を強制的に複数行へ分割し、記事のコード例が 40 件ずれました。教材コードを縦長にする方向に働きます。

前回（Unit 2）は試さずに「入れない」と決めていました。今回は試したので、**「合わなかった」ことを具体的に書けました**。

必要だったのは行長と `import` 順の 2 点だけだったので、それを検査するスクリプト（30 行）を作りました。検出した 5 件のうち行長の 2 件は、鍵を作る関数を切り出して短くしました。**汎用ツールの整形より意味のある切り出しになりました。**

### 2. 保存した文字列がそのまま返る前提は置けない

PostgreSQL の `JSONB` は保存時に JSON を正規化します。コロンの後に空白が入ります。自作のパーサが空白を許していなかったので、結合テストが落ちました。

**結合テストが落ちた原因は、予想していた「不安定さ」ではなく「往復の前提の誤り」でした。** 検証の不確実性を HIGH と評価したのは正しく、しかし問題が起きた場所は予想と違いました。

**評価が当たることと、原因を予測できることは別です。** HIGH と評価する意味は「この領域で何か起きる」であって「何が起きるか分かる」ではありません。

### 3. 検査そのものにも漏れがある

第 9 章が `docker-compose.yml` の設定を載せたところ、記事のコード例検査が「実装に存在しない」と誤検出しました。**検査の探索先に compose ファイルが入っていなかった**だけです。

記事が正しく、検査が間違っていました。**検査を信じて記事を直そうとしかけました。** 検査が出す結果も、内容を見て判断する対象です。

### 4. 3 つめの法則も同じ形で書けた

モノイド（第 5 章）・ファンクタ（第 7・8 章）・モナド（第 9 章）を、**同じテストの形**で検証しました。`forAllRandom` も生成の考え方も変えていません。

「構造 → 性質 → 名前 → 身の回りの例」という記事の構成も 3 回目です。**同じ型を使い回せると、読者も書き手も楽になります。**

### 5. 実装より先に ER 図を作った

Unit 4 の学び（表を先に作ると判断の漏れが見える）を適用しました。ER 図とテーブル定義を実装より前に作った結果、「テーブルは 1 つでよい」「正規化を論じる必要がない」という判断が先に固まりました。

**後から変えずに済みました。** スキーマは変更コストが高いので、順序を守る価値が大きい領域です。
