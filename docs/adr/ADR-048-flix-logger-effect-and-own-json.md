# ADR-048 Flix 版のログは標準の Logger 効果を借り、JSON は自作する

日付: 2026-11-03

## ステータス

2026-11-02 承認されました

## コンテキスト

第 12 章で、ログと JSON を扱います。既製品を先に調べるのは、全章共通の手順です（[ADR-028](ADR-028-own-acceptance-trait.md)、[ADR-047](ADR-047-flix-use-standard-result.md)）。

既存の対象の手段は次のとおりです。

| 対象 | ログ | JSON |
| :--- | :--- | :--- |
| Kotlin | 自作 | 自作（[ADR-012](ADR-012-own-json-converter.md)） |
| Kotlin FP | decorator + 型付きの `LogRecord`（[ADR-045](ADR-045-logging-as-decorator-with-typed-record.md)） | JSON の木 |
| Rust | `tracing` と `serde` を採否判断のうえ選んだ | `serde` |

### 先に調べたこと

| 項目 | 結果 |
| :--- | :--- |
| 標準に `Logger` 効果があるか | **ある。** `Logger.info` などを呼び、`Logger.runWithIO` で標準出力に出せる。自前のハンドラで、出力先を差し替えられる |
| 標準に JSON があるか | **見つからなかった。** `Json.parse` と `Json.Null` は未定義だった |
| 標準に時計があるか | `Clock.currentTime` は未定義だった。時刻は、`System.currentTimeMillis()` を引数として渡す |
| 標準に文字コードを扱う関数があるか | `Char.ord` と `Char.toInt32` は未定義。`Character.hashCode` と `Character.toString` を Java から呼ぶ |

### 調べていないこと

- Maven の JSON ライブラリ（Jackson など）と、ログのライブラリ（SLF4J など）は**試していない。** 採らなかったのは、試した結果ではなく、下の理由による判断である。

## 決定

1. **ログの出力は、標準の `Logger` 効果を使う。** ログを足す操作は、デコレータとして外から包み、ドメインの関数には 1 行も足さない
2. **ログの 1 行は、自作の型 `LogRecord` で表し、JSON の 1 行として書く。** 自由な `Map` は持たない
3. **JSON は自作する。** 木（`JsonTree`）、文字列への書き出し、文字列からの読み込みを作る

### 採った理由

- **`Logger` は効果として型に現れる。** ドメインの関数に `Logger.info` を足すと、`Unexpected effect 'Logger' in {} function.` で、コンパイルが拒否する。第 2 章の `IO` と同じ守り方が、ログにも効く
- **出力先を差し替えられる。** 本番は `Logger.runWithIO`、テストは自前のハンドラで集める。テストが出力先を握れるので、「この値が行に現れない」を検査できる
- **JSON は標準に無く、Java のライブラリは効果の外にある。** 反射で型を写す Java のライブラリを使うと、ログの 1 行に載るものを、型ではなくライブラリの挙動が決める。載せないものを守る仕組み（型に置き場所が無い）が、弱くなる
- **自作の量は小さい。** 木、書き出し、読み込みで 180 行ほどである（`Json.flix`）

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| Jackson を Maven で足す | 試していない。上の理由で、載せるものを型で決める方針と相性が悪いと判断した |
| SLF4J / `java.util.logging` を呼ぶ | ログの呼び出しが `IO` になり、ドメインの関数と同じ型で扱えない。出力先の差し替えもライブラリ任せになる |
| 自作の `Logger` 効果を宣言する | 標準にあるものを作り直すことになる |
| ログを文字列の連結で作る | 値を文字列に埋め込むと、載せてはならないものを型で止められない |

## 影響

- **自作の JSON は、境界値で壊れていた。** `Int32` の最小値（-2147483648）を読めなかった。桁を先に `Int32` に読んでから符号を付けていたためで、双方向の往復のテストに境界値を入れて見つけた。符号つきで読むように直した
- ログに載るのは、`LogRecord` の 6 つの欄だけである。項目の説明、イベントの中身、失敗の理由（接続先やパスワードを含みうる）、HTTP の経路・クエリ・本文は、載せる場所が型に無い
- サーバーのコールバックは、`Logger` を処理するハンドラの外で動く。コールバックの内側で `Logger.runWithIO` を呼ぶ必要がある

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| 自作の JSON が仕様のすべてを満たすこと | 数は `Int32` の整数だけ、小数・指数・BMP 外の文字は扱わない。必要になったら足す |
| ライブラリを試して比べること | 試していない。比べた結果は、この ADR に無い |
| 時刻の型 | 時刻は `Int64` のミリ秒で渡す。標準の時刻の型は調べていない |
| ログの保管とアクセスの管理 | 運用で守る前提。利用者名とリスト名は載せるので、個人を特定しうる |

## コンプライアンス

- ドメインの関数（`Commands`、`Events`、`Projection`、`Domain`）に、`Logger` の効果を足さないこと（コンパイラが検査する）
- `LogRecord` に、自由な `Map` や文字列の欄を足さないこと
- 失敗は `Logging.category` で種類の名前だけにすること。足した失敗の種類には、`match` が全ケースを求めるので、更新漏れはコンパイルで見つかる
- JSON の往復のテストが、`Int32` の最小値と最大値を含むこと
