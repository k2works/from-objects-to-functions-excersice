## Problem（問題）

| # | Problem | 何が起きたか | 原因 |
| :--- | :--- | :--- | :--- |
| 1 | **思い込みで書いたテストが落ちた** | 「同じオブジェクトに聞いているのに答えが変わる」が、この題材では成立しなかった | **主張を先に決めて、確かめずにテストを書いた。** 得点は先頭 10 フレームで決まる |
| 2 | **ローカルで動いたものが CI に来ないと、後から気づいた** | `just` も `cargo-llvm-cov` もホストの `~/.cargo/bin` にあった | **`which` で確かめる習慣が無かった。** 動いたので満足した |
| 3 | **`$2::jsonb` をキャストだと思い込んだ** | パラメータの型が `jsonb` と推論され、`&str` を渡せなかった | SQL のキャストとドライバの型宣言を混同した |
| 4 | **計画のステップ数を数え間違えた** | 15 ステップなのに指標表に 14 と書いた | 手で足した。**機械で数えたら見つかった** |
| 5 | **タスクランナーの選定が計画に無かった** | 作業中に Make → Just の指示を受けて変更した | 計画で `Makefile` を前提にしていた。**「何で書くか」も判断だったのに、判断として扱っていなかった** |
| 6 | **devShell の外から叩くと別の rustc で動いた**（Unit を閉じたあとに発覚） | IDE から `just check` を叩いて判明。ホスト 1.97.1 対 devShell 1.91.1 | **「どこから叩かれるか」を考えていなかった。** Problem 2 と同じ根で、向きが逆だった |

Problem 1 と 2 は、どちらも「**確かめずに進んだ**」種類です。

Problem 5 は計画の抜けです。async と HTTP クレートは判断として扱ったのに、タスクランナーは 2 対象の踏襲として素通ししていました。

Problem 6 は Unit を閉じたあとに出ました。**Problem 2 で「ホストにしか無い」を直したとき、「ホストのほうが使われる」という逆向きを見ていませんでした。** どちらも「道具がどこから来るか」を確かめていなかったことが原因です。
