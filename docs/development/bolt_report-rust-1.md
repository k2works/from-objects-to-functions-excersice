## 判断と学び

### 1. 承認ゲートが 3 / 3 で同期停止した

**2 対象は 41 箇所計画して 1 回でした。この Unit は 3 箇所計画して 3 回です。**

違いは計画の書き方です。Unit 1 の計画では、**ゲートごとに「添えるもの」を事前に確定**させていました。

| ゲート | 添えたもの | 人の判断 |
| :--- | :--- | :--- |
| async の採否 | 同期クレートで第 9〜10 章の題材が書けるかの実測、選択肢 3 つ、それぞれで第 2〜8 章がどう変わるか | **採らない** |
| HTTP クレートの選定 | 候補 3 つの tokio 必須の有無・依存クレート数・行数・ビルド時間 | **`tiny_http`** |
| `just check` の構成 | 各段が何を守るか、それぞれの秒数、カバレッジの導入に必要な変更 | **カバレッジを入れる** |

**共通しているのは「選択肢」と「数字」です。** なでしこ3 版 Unit 7 で 1 度だけ止まったときと同じ形でした。

あわせて、**「記事の全文検証」をゲートから外しました。** 2 対象で 14 箇所計画して 1 度も止まっていないためで、DoD のチェック項目に移しました。**止まらないものを並べるのをやめたことが、止まる率に効いています。**

### 2. 2 対象の学びが着手前に効いた

持ち込み 9 件のうち 7 件を本 Unit で消化しました。

| 学び | どう効いたか |
| :--- | :--- |
| **既知の制約の一覧を Unit 1 から置く** | 器を作った日のうちに 1 件記録した（`$2::jsonb` がキャストにならない） |
| **段を入れる前に何を守るか数える** | 4 段とも守るものが違うことを先に確認した。なでしこ3 版は重複に Unit 7 まで気づかなかった |
| **共有する書き込み先はテストごとに分ける** | 第 1 章のうちに `unique_path` を用意した。依存クレート 0 で書けた |
| **測れない指標を置かない** | 「人が検証に使った時間」を最初から置かず、「人が修正を入れた箇所数」を使った |
| **変更依頼数の定義を先に決める** | 1-1.0 で定義した。なでしこ3 版は 7 Unit かけて定義できなかった |

**2 件は送りました。** しきい値の分布計算（性質テストが無いので Unit 3 へ）と、段階を切る手順（段階が 1 つなので Unit 2 へ）です。**計画に送り先を書いてあったので、取りこぼしになりませんでした。**

### 3. ローカルで動いたことは、CI で動くことを意味しない

`just` も `cargo-llvm-cov` も、最初はローカルで動きました。**ホストの `~/.cargo/bin` に入っていたためです。**

```text
/Users/k2works/.cargo/bin/just
/Users/k2works/.cargo/bin/cargo-llvm-cov
```

**CI は Nix の devShell しか使いません。** そのままなら Unit 2 で CI を作った瞬間に落ちていました。`ops/nix/environments/rust/shell.nix` に両方足しました。

足したあとも `cargo-llvm-cov` が落ちました。rustup の `llvm-tools-preview` を探すためです。**rustc の LLVM（21.1.7）と devShell の `llvmPackages.bintools` の版が一致していた**ので、`LLVM_COV` / `LLVM_PROFDATA` を `shellHook` で指して解決しました。

### 4. 思い込みで書いたテストが落ちた

第 1 章の「状態を持つと何が起きるか」で、**「同じオブジェクトに聞いているのに答えが変わる」**というテストを書きました。落ちました。

得点は先頭 10 フレームで決まるので、12 投したあとに何を足しても答えは変わりません。**主張そのものが間違っていました。**

実際に示せたのは「**いつ聞いてよいかが型に現れない**」ことでした。記事にはこの経緯も書きました。

### 5. タスクランナーを作業中に変えた

計画では `Makefile` でした。作業中に人から「Just にして」と指示があり、変更しました。

**指標「人が修正を入れた箇所数」の 1 件目です。** 変更依頼（ゲートでのやり直し）ではないので、定義どおり分けて数えました。

`just --list` がタスク一覧になるので、2 対象で `Makefile` に書いていた `grep` + `awk` のヘルパが要らなくなりました。

### 6. Unit を閉じたあとに 1 件直した（2026-09-29）

IDE から `just check` を叩いたところ、**devShell の外ではホストの rustc 1.97.1 が使われる**ことが分かりました。devShell は 1.91.1 を固定しています。`LLVM_COV` も未設定で `just cov` が落ちます。

**「ローカルでは通ったが CI で落ちる」が起きる形**です。判断と学び 3（`just` と `cargo-llvm-cov` がホストにしか無かった）と同じ根で、今度は逆向きでした。あちらは「ホストにしか無い」、こちらは「ホストのほうが使われる」です。

2 対象がこの問題を持たないのは、**道具をリポジトリに取り込んでいる**からでした。

| 対象 | 道具の在り処 |
| :--- | :--- |
| Kotlin | `./gradlew` |
| なでしこ3 | `./node_modules/.bin/cnako3` |
| **Rust** | **PATH**（rustc も `cargo-llvm-cov` も取り込めない） |

`justfile` が `IN_NIX_SHELL` を見て `nix develop` に入り直す形にしました（[ADR-026](../adr/ADR-026-just-and-coverage.md) に追記）。**再入は 1 回だけで、外から叩いても 4〜8 秒**です。`check` を依存指定から 1 行に変えたのはこのためです。

**指標「人が修正を入れた箇所数」の 2 件目**にはしません。人の指摘ではなく、IDE の実行で見つかった実装の欠陥だからです。

### 7. スパイクのコードを捨てずに残した

計画に「書いた 3 つは捨てずにスパイクの記録として残す」と書いていました。`apps/rust/zettai/spikes/` に置き、**workspace の `exclude` に入れて検査の対象外**にしています。

理由は 2 つです。`sync-postgres` は DB が要り、HTTP の 3 つは同じポートを使うので並列に走らせられません。

**記事検査（`check_article_code.py`）はこれを見ます。** 第 1 章がスパイクのコードを引用できるのは、実物がここにあるからです。
