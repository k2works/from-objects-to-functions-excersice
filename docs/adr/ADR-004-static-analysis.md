# ADR-004 静的解析を check に組み込まず記事のコード例検査を優先する

日付: 2026-09-26

## ステータス

2026-09-26 提案されました

## コンテキスト

[開発戦略](../development/development_strategy.md) は「静的解析（ktlint / detekt）を `check` に組み込むかは Unit 1 の Gradle 雛形作成時に決めて ADR に記録する」としていましたが、**Unit 1 では決めずに積み残しました**。Unit 2 の開始準備の検証（`validating-design` 軸 A）でこの積み残しが検出され、本 Unit で消化することになりました。

判断の材料は次のとおりです。

- 本プロジェクトの成果物は**記事とサンプル実装の対**であり、コードは読者に読まれることを前提に書く
- 記事のコードは説明のために意図的に単純化する箇所がある。ボウリングの得点計算の定数、短い関数名、`when` の分岐の並びなど
- 開発者は 1 名で、複数人の書き方のブレという問題が発生していない
- Unit 1 で実際に起きた品質問題は **1 件**で、それは「記事に載せたコードの実装が存在しなかった」ことだった。静的解析では検出できない種類の問題である

## 決定

**静的解析（ktlint / detekt）を `check` に組み込みません。** 代わりに、記事のコード例が実装に存在することを検査するスクリプトを CI に入れます。

1. `check` に集約するのはコンパイル・テスト・カバレッジ検証（Kover、ドメイン層 80%）とする
2. 記事のコード例検査（`ops/scripts/article/check_article_code.py`）を CI の独立したジョブとして実行する
3. 逐語の転記でない抜粋は、記事側に `<!-- code-check: ignore 理由 -->` を置いて除外する
4. **再検討は Unit 5（第 9 章）**。永続化が入りコード量が増える時点で、書き方のブレが実際に問題になっているかを見て判断する

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| detekt を入れる | 複雑度・マジックナンバー・命名のルールが、説明のために単純化した教材コードと衝突する。抑制コメント（`@Suppress`）が記事のコードに写り込むと、説明していない要素が増えて記事が読みにくくなる |
| ktlint（整形のみ）を入れる | 衝突は detekt より少ないが、1 名体制で整形のブレが問題になっていない。`check` にゲートを増やすと、得られるものより CI 時間とビルドの複雑さが増す |
| 両方入れて記事用に緩い設定を作る | 設定の維持が新しい仕事になる。連載を書き切ることが目的であり、ビルド設定の作り込みはその手段にすぎない |

## 影響

- **書き方のブレは人のレビューで吸収する。** 記事の全文検証（承認ゲート）でコードも読むため、極端なブレはそこで止まる
- **記事と実装の乖離は機械的に止まる。** Unit 1 で実際に起きた問題に対して、直接効く検査を入れた
- CI のジョブは 2 つ（`check` と記事のコード例検査）にとどまり、実行時間が短い
- Unit 5 で再検討する。そこで必要と判断すれば、静的解析を後から足せる。**逆に、入れたものを外すほうが難しい**

## コンプライアンス

- 第 1 章以降のすべての章で、検査が違反 0 件であること
- Unit 5 の Bolt 計画に、静的解析の再検討をステップとして入れること
