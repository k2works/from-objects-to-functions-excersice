# ADR-020 受け入れシナリオに永続化を通す 3 経路目を足す

日付: 2026-09-28

## ステータス

2026-09-28 提案されました

## コンテキスト

第 3 章で、同じシナリオを 2 経路（ドメイン直接・HTTP 経由）で走らせる形を作りました（[ADR-016](ADR-016-own-acceptance-entry.md)）。**片方だけ落ちたら、そこに業務ロジックが漏れている**という検査です。

第 9 章で永続化が入ります。ファイルに書いて読み戻す経路が増え、**そこにも業務ロジックが漏れうる**ようになりました。たとえば、読み戻したイベントの順序が入れ替われば、状態が変わります。

Kotlin 版も第 9 章で 3 経路目を足しています（節「3経路目」）。

## 決定

**受け入れシナリオに永続化を通す 3 経路目を足します。**

1. `test/stepN/ddt/actions_store.nako3` を置く。ファイルに書いてから読み戻し、射影に畳み込む
2. シナリオは 3 経路とも**同じもの**を使う。シナリオ側は経路を知らない
3. 3 経路とも green であることを、永続化がドメインに漏れていない証拠とする
4. テストは一時ファイルを作り、前後で消す

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| 永続化は単体テストだけで確かめる | 「読み書きができる」ことしか分からない。**業務の振る舞いが同じかどうか**が分からない |
| HTTP 経由の経路を永続化経由に置き換える | HTTP を通さない経路が減る。テストが遅くなり、落ちたときの切り分けも難しくなる |
| 経路を増やさず、永続化を HTTP 経由の中に含める | 永続化だけが原因の失敗と、HTTP が原因の失敗を区別できない |

## 影響

- **永続化の欠陥が業務の言葉で見つかります。** 「3 件見られるはずが 2 件だった」という形で出ます
- シナリオを 1 つ足すと、確かめる箇所が 3 倍になります。**シナリオを増やすときの重みが上がりました**
- テストの実行時間が伸びます。Unit 5 の時点では影響は小さい（読み書きが速い）

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| **書く側の経路** | 3 経路目は読む側だけを通す。書く側（コマンド → イベント → 保存）は単体テストで確かめている。HTTP から書く口が無いため（第 6 章で見送った） |
| **落ちたときの切り分け** | 3 経路すべてが落ちた場合、原因がシナリオ側かドメイン側かは分からない。経路が増えても切り分けの手間は減らない |
| **経路の組み合わせ** | HTTP 経由かつ永続化経由、という組み合わせは試さない。組み合わせ爆発を避ける |

## コンプライアンス

- 3 経路が同じシナリオを使うこと（シナリオを経路ごとに書き分けない）
- 3 経路とも green であること
- テストが作ったファイルを残さないこと

## 再検討の条件

1. 書く側の口（POST）ができ、3 経路目で書く側も通せるようになる
2. 経路が 4 つ以上になり、実行時間が問題になる
3. 3 経路が同じ結果になることが、一度も欠陥を見つけないまま 3 Unit 続く
