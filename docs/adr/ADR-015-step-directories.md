# ADR-015 章の段階ごとにディレクトリを切り、過去の章のコードを残す

日付: 2026-09-28

## ステータス

2026-09-28 提案されました

## コンテキスト

連載の記事は、各章の時点のコードを載せます。[執筆計画](../article/outline.md) の規約は「記事のコード例は必ず動作確認済み実装から転記する」とし、`check_article_code.py` がそれを機械的に検査します。

**Unit 3 で、この規約と構造が衝突しました。** 第 5 章で `保管庫作成` をイベントの畳み込みに置き換えたところ、**第 2〜4 章のコード例 7 箇所が「実装に存在しない」と落ちました**。章が進んで実装が変わると、過去の章のコード例が実装から消えるためです。

Kotlin 版はこの問題を構造で解いていました。[ADR-007](ADR-007-module-per-unit.md) でモジュールを Unit の境界（= 2 章）で切っており、`zettai-step1-http` には第 1〜3 章のコードが残ります。**なでしこ3 版は `src/` が 1 つで、この判断を移植していませんでした。** Unit 4 の [Kotlin 版 ADR の棚卸し](../development/iteration_plan-nadesiko-4.md) で漏れとして特定されました。

暫定として `code-check: ignore 第 N 章時点の実装` を 7 箇所に付けましたが、**章が進むほど増え、検査の意味が薄まります**。残り 8 章あります。

## 決定

**サンプル実装を章の段階ごとのディレクトリに分けます。**

```text
apps/nadesiko/zettai/
├── src/step1/      第 1〜3 章（Unit 1〜2）
├── src/step2/      第 4〜7 章（Unit 3〜4）
├── test/step1/     step1 のテスト
├── test/step2/     step2 のテスト
├── doctest/step1/  step1 の受け入れシナリオ
└── doctest/step2/  step2 の受け入れシナリオ
```

1. 段階の区切りは **Kotlin 版のモジュールと同じ**にする（[ADR-007](ADR-007-module-per-unit.md) の表に従う）。対象間で「同じ章が同じ段階にある」状態を保つ
2. **過去の段階は凍結する。** バグの修正も、その段階の記事が説明している内容に影響しない限り行わない
3. `make check` は**全段階**を対象にする。過去の段階も動き続けることを確かめる
4. `make check STEP=step1` で 1 段階だけを扱える
5. `make run` は最新の段階を起動する

### 適用した結果

| 項目 | 前 | 後 |
| :--- | :--- | :--- |
| `code-check: ignore` の件数 | 7 | **3**（残りは「わざと壊したコード」で本来の用途）。Unit 4 の第 7 章で **8 件**に増えた。理由は後述 |
| 検証（ok）の数 | 55 | **76** |
| `make check` の実行時間 | 約 15 秒 | **約 25 秒** |

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| 検査に「章時点」の概念を入れる（git の履歴からその章の時点のコードを引く） | 検査が git の履歴に依存する。章と commit の対応を別に持つ必要があり、壊れやすい。**検査を複雑にして構造を単純に保つのは、順序が逆** |
| `ignore` を許容して上限を決める | 章が進むほど増える。上限に達したときに何をするかを決められない。**検査の目的（記事と実装の一致）が達成できなくなる** |
| 記事から古いコードを消し、常に最新の形だけを載せる | 連載の価値は「設計が変わっていく過程」にある。各章の時点の形を見せられないなら、連載として成立しない |

## 影響

- **記事のコード例が実装から消えません。** 第 2〜3 章のコードは `src/step1/` にあり、動きます
- **重複が生まれます。** `step2` は `step1` からの派生で、変わっていない部分を含みます。Kotlin 版も同じ形（5 モジュール）なので、対象間の対称性は保たれます
- **実行時間が伸びます。** 段階が 5 つになると `make check` が 30 秒を超える見込みです。超えた時点で、過去の段階の受け入れシナリオを CI だけで回すなど、対処を決めます
- 記事の「この章で書いたコード」のパスに段階が入ります（`src/step1/domain.nako3`）
- **ADR-007 を移植しそこねていた**ことが、`check_article_code.py` によって見つかりました。検査が設計の穴を見つけた例として第 6 章に書きます

## 段階の中のドリフト（2026-09-28 追記）

**この決定は段階「の間」のドリフトしか解きません。** 段階の区切りは Unit の境界（= 2 Unit = 4 章）なので、**段階の中でも章が進めばコードは変わります。**

Unit 4 で実際に起きました。第 7 章で失敗の表し方を結果辞書に変えたところ、同じ `step2` にある第 6 章のコード例 2 箇所が実装から消えました。第 6 章は「拒否をイベント 0 件で表す」暫定を説明しており、その形は第 7 章で置き換わるからです。

対処は 2 通りあり、**章によって使い分けます。**

| 状況 | 対処 |
| :--- | :--- |
| 変更が小さく、章の主題に影響しない（引数名、取り出し方） | **記事を最終形に直し**、段階の中で育つことを注記する（第 4・5 章） |
| その形であること自体が章の主題（第 6 章の「イベント 0 件で拒否」） | **`ignore` を付け、どの章で置き換わるかを書く** |

したがって `ignore` の許容理由に 3 つ目を加えます。

1. わざと壊したコード
2. 比較のために引いた他言語のコード、説明のための素朴な書き方
3. **同じ段階の後の章で置き換わる、その章の時点の形**（置き換わる章を理由に書くこと）

**段階に属さないファイルもあります。** `Makefile`・`package.json`・CI のワークフローは 1 つで、全段階が共有します。これらは章をまたいで育つので、引用した章の時点の形は理由 3 と同じ扱いにします（理由に「Makefile は段階をまたぐ 1 ファイル」と書く）。段階を細かく切っても解けません。

段階をもっと細かく（1 章 = 1 段階）切れば 3 は消えますが、13 段階になり重複が大きくなります。**Kotlin 版と段階の区切りを揃えることを優先します。**

## コンプライアンス

- `code-check: ignore` の理由が、上の 3 つのいずれかであること（現在 8 件。内訳は 1・2 が 6 件、3 が 2 件）
- 理由 3 の ignore には、**置き換わる章**が書かれていること
- `make check` が全段階を対象に green であること
- 新しい段階を切るときは、Kotlin 版のモジュールの区切りと一致させること

## 再検討の条件

時期では区切りません。次のいずれかが起きたら再検討します。

1. ~~`make check` が 30 秒を超える（段階が 4 つ以上になったとき）~~ → **段階 3 つで起きた（2026-09-28）。** 下の「実行時間の扱い（追記）」で対処済み。次は**全段階が 35 秒を超えたとき**
2. 過去の段階に修正が必要な欠陥が見つかり、**凍結の方針が守れなくなる**
3. 重複が原因で、同じ修正を複数の段階に入れる場面が実際に起きる
4. 理由 3（段階の中のドリフト）の `ignore` が、1 つの段階で 4 件を超える

## 実行時間の扱い（2026-09-28 追記）

段階が 3 つになった時点で、全段階の `make check` が **33.4 秒**になりました。予想（4 つ以上）より早く超えています。

原因は**ファイル 1 つごとに cnako3 のプロセスを起こすこと**です。段階が増えるとファイル数が比例して増えます。Unit 4 で lint を並列化しましたが、それでも足りませんでした。

対処として、テストも並列化し、サーバの起動待ちを固定の `sleep` から到達確認に変えました。**それでも全段階は 27 秒で、段階が 5 つになれば再び超えます。**

そこで **NFR の立て方を変えました。**

| 対象 | 上限 | 理由 |
| :--- | :--- | :--- |
| 作業中の段階（`make check STEP=stepN`） | **15 秒** | これが書いている間の待ち時間。ここが速ければ TDD は回る |
| 全段階（`make check`） | **35 秒** | 段階をまたぐ回帰の確認。毎回は回さない。**CI が push のたびに回す** |

**速さが要るのは書いている間で、全段階は CI の仕事です。** 段階を増やす構造を選んだ以上、全段階の実行が伸びるのは避けられません。避けるのではなく、どこを速く保つかを決めました。
