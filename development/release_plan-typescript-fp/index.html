    リリース計画 - Zettai 連載（TypeScript FP 版）¶

    概要¶

    本計画は リリース・イテレーション計画ガイド（AI-DLC 版） に準拠する Level 1 計画 です。章の焦点、技術方針、執筆規約の一次情報は 執筆計画 の「TypeScript FP 追加執筆計画」、進行と進捗の一次情報は本計画です。食い違いが生じた場合は両方を同じコミットで直します。

    本計画は 2026-11-27 に人の承認を得ました。 検証負荷、エントロピー評価、承認ゲートの位置、リリースの区切りは AI の提案を承認したもので、実績による裏づけはまだありません。

    プロジェクト情報¶

    項目 内容

    主なライブラリ Effect v4（基準は 4.1.6）。テスト、HTTP、永続化の道具は Unit 1 以降のスパイクで決める

    リリース 3 回（v0.1.0 / v0.2.0 / v1.0.0。他の対象とは独立に採番）

    満足条件¶

    Intent¶

    型が実行時に消え、型付けが構造的な言語で、副作用・エラー・依存を Effect<A, E, R> の型に載せると、設計のどこが型で守られ、どこが規約とテストに残るのか。 同じ 13 章を動く Zettai の実装で辿り、読者が手元で再現できる形で答える。

    ビジネス価値と測定基準¶

    # 価値 測定基準
    1 エラーと依存まで型に持つ方式を、Scala 版（IO）・Kotlin FP 版（Arrow）と比べられる comparison/ に TypeScript FP の節があり、第 13 章が冒頭の問いに答える
    2 TypeScript の型が守る範囲と守らない範囲が分かる 全 13 章に「型で守れたこと・守れなかったこと」がある
    3 Effect に置き換える抽象と自作で残す抽象の判断が残る 全 13 章にその記録があり、採否は ADR で追える
    4 Effect v4 で動くコード例が残る 記事のコードがテスト済みの実装と一致し、版が固定されている

    スコープ¶

    # 含むもの
    1 index.md と全 13 章の記事
    2 動作するサンプル実装（apps/typescript-fp/zettai/）
    3 単一の品質ゲート npm run check と CI（.github/workflows/typescript-fp-zettai.yml）
    4 記事の検査スクリプトの TypeScript 対応
    5 ADR（ADR-053 から）。採らなかった判断も残す
    6 シリーズ索引、章構成の読み替え、サイトナビゲーション、横断比較の同期
    7 既知の制約の一覧（apps/typescript-fp/zettai/README.md。Unit 1 から置く）

    スコープ外¶

    # 含まないもの 理由
    1 認証・認可、本番デプロイ 他の対象と同じく連載の範囲外
    2 Effect を使わない TypeScript 版、fp-ts 版 対象を増やすと比較の軸がぼやける
    3 TypeScript と Effect の入門解説 つまずいた箇所と、章の設計判断に必要な用語だけを書く
    4 要件が無い Fiber・Stream・並行化 道具を見せるための抽象は増やさない

    Unit 分解¶

    各章を 1 Bolt、2 章を 1 Unit とします。Unit 1 だけは前提整備と第 1 章です。

    Unit 名前 章 ストーリー 検証負荷 Bolt
    1 土台と第 1 章 前提整備・1 US-000, US-001 13 1-1 / 1-2
    2 ウォーキングスケルトンとドメイン分離 2〜3 US-002, US-003 13 2-1 / 2-2
    3 依存の注入とイベント 4〜5 US-004, US-005 11 3-1 / 3-2
    4 コマンドと型付きエラー 6〜7 US-006, US-007 10 4-1 / 4-2
    5 射影と永続化 8〜9 US-008, US-009 13 5-1 / 5-2
    6 文脈と検証の蓄積 10〜11 US-010, US-011 11 6-1 / 6-2
    7 監視と総括 12〜13 US-012, US-013 8 7-1 / 7-2
    合計 13 章 14 ストーリー 79 14

    検証負荷は、人が検証にどれだけ向き合う必要があるかの相対値です。時間ではありません。Kotlin 版の値を起点に、次の理由で調整しました。実績による裏づけはありません。

    • Unit 1（13）: 参考実装のコードを流用できず、Effect v4 の確認と技術の選定が集まります
    • Unit 2（13）: unstable な HTTP を使うかの判断が加わります
    • Unit 3（11）: 依存の渡し方を 3 通り比べます
    • Unit 5・6（13・11）: unstable な SQL、transaction の後始末、エラー蓄積の方式を扱います

    依存 DAG¶

    US-000 → US-001 → US-002 → US-003 → US-004 → US-005 → US-006
→ US-007 → US-008 → US-009 → US-010 → US-011 → US-012 → US-013

    章の物語が設計の到達順序を固定するため、並行できる Unit はありません。

    DAG に現れない前倒しの判断が 2 つあります。

    • unstable モジュールの扱い（Unit 1 で方針）: 第 2 章の HTTP と第 9 章の SQL に効きます
    • codec と decode（第 9 章の前）: 本来の主題は第 12 章ですが、DB の行の decode が先に必要になります

    ストーリーと受入条件¶

    共通のアクターは、手元で再現しながら読む読者です。全ストーリーに、後述の「全 Bolt 共通の完了条件」を適用します。受入条件の詳細は、各 Unit の Bolt 計画で確定します。

    ID ストーリー 受入条件の要点
    US-000 読者として、同じ版の環境を再現したい。記事のコードを手元で動かすためだ 版と lock が固定される。npm run check と CI が通る。テストの型エラーと生成物の除外を、壊して確認している
    US-001 読者として、純粋関数と Effect の違いをテストで確かめたい Promise と Effect の実行の違いがテストで分かる。第 1 章が公開される
    US-002 読者として、HTTP の縦串を動かしたい プロセス内のテストと実サーバーの smoke が通る
    US-003 読者として、同じ受け入れシナリオを経路を変えて実行したい domain と HTTP の 2 経路で通る
    US-004 読者として、依存を差し替えられる形を理解したい 3 通りの比較が記録され、取り違えと提供漏れが型のテストで固定される
    US-005 読者として、状態をイベントの畳み込みで表したい 畳み込みが通り、結合律と単位元を性質テストで確かめる
    US-006 読者として、コマンドを純粋な状態遷移で扱いたい 全遷移と拒否理由が通る。分岐を足すと tsc が落ちる
    US-007 読者として、失敗を型で扱いたい ファンクタ則とエラーの HTTP への対応が通る。失敗と defect の線引きが記録される
    US-008 読者として、読み取り側を射影で分離したい command と query の経路が分かれ、射影の性質テストが通る
    US-009 読者として、イベントを PostgreSQL に安全に保存したい Testcontainers の結合テスト（追記順、原子性、3 経路目）とモナド則が通る
    US-010 読者として、1 コマンドを 1 transaction で処理したい commit、失敗・defect・中断での rollback、接続の返却、競合の検出が通る
    US-011 読者として、入力の誤りをまとめて知りたい 全エラーが入力順に返る。蓄積の性質テストと rename のフォームが通る
    US-012 読者として、機密を出さずに動きを観測したい ログに機密が含まれないこと、往復と dimap 則が通る
    US-013 読者として、型が守る範囲を総括で知りたい 第 13 章が冒頭の問いに答え、comparison/ に反映される

    非機能要件¶

    項目 要件 確認する時期
    再現性 依存の版を固定し、lock をコミットする。ローカルと CI は同じコマンドを使う Unit 1 から毎 Unit
    検査の実行時間 Unit 1 で npm run check の基準値を測る。上限は実測を見てから決める Unit 1、以後は各 Unit の冒頭
    テストの実行条件 結合テストは Docker を必要とし、無い場合は skip せず失敗させて診断を出す Unit 1、Unit 5
    テストの独立 テストは他のテストの終了状態に依存しない 全 Unit
    機密の保護 ログと記事に、認証情報や利用者の入力値をそのまま出さない Unit 5、Unit 7

    • 既知の制約の一覧を更新した

    Unit ごとの Bolt 計画概要¶

    各 Unit の詳しい Bolt 計画は、着手時に opening-iteration で iteration_plan-typescript-fp-N.md として作成します。作成済みは Unit 1 の Bolt 計画（承認済み）と Unit 2 の Bolt 計画（承認済み）です。

    Unit ゴール 確認したい仮説
    1 環境・品質ゲート・CI・検査スクリプトを整え、第 1 章を公開する Effect v4 で、型検査・テスト・Node での実行が一つのゲートにまとまる
    2 HTTP の縦串と 2 経路の受け入れテストを通す（第 2〜3 章、v0.1.0） Effect を使っても、縦串は薄く保てる
    3 依存の注入とイベントの畳み込みを書く（第 4〜5 章） R に依存を載せると、差し替えの漏れが型で分かる
    4 状態遷移と型付きエラーを書く（第 6〜7 章） 純粋な核は Effect に依存せずに書ける
    5 CQRS と PostgreSQL の永続化に到達する（第 8〜9 章、v0.2.0） 接続の寿命を Scope と Layer で表せる
    6 transaction の文脈とエラー蓄積を書く（第 10〜11 章） 失敗・defect・中断のすべてで後始末が保証できる
    7 監視と総括を書き、比較を同期する（第 12〜13 章、v1.0.0） 型が守る範囲を、各章の記録からまとめられる

    仮説は確認の対象であり、結論ではありません。成り立たなかった場合は、その事実を章に書き、残りの Unit の計画を直します。
