# ADR-026 タスクランナーに Just を使い、カバレッジを検査に入れる

日付: 2026-09-28

## ステータス

2026-09-28 提案されました

## コンテキスト

検査をまとめるコマンドが要ります。2 対象は `Makefile` を使いました。

**なでしこ3 版でここに失敗があります。** `lint` が `test` と完全に重複していたのに Unit 7 まで気づかず、検査時間の半分（全段階 41 秒のうち 21 秒）を食っていました。原因は「**段を入れるときに、それが何を守るかを数えなかった**」ことです。

その学びを先に適用します。**段を入れる前に、何を守るかを書き出しました。**

| 段 | 何を守るか | `test` と重複するか |
| :--- | :--- | :--- |
| `fmt` | 体裁。差分を読みやすく保つ | **しない**（`test` は体裁を見ない） |
| `clippy` | 言語の慣用から外れた書き方 | **しない**（コンパイルは通るが指摘される書き方がある） |
| `test` | 振る舞い。あわせて型・所有権も（コンパイルするため） | — |
| `cov` | **テストが見ていないコード** | **しない**（`test` は「通ったか」しか見ない） |

**4 段とも守るものが違うので、4 段とも入れます。**

## 決定

### 1. タスクランナーは Just

`justfile` に置きます。

### 2. 検査を 2 段構えにする

| コマンド | 内容 | 用途 | 実測 |
| :--- | :--- | :--- | :--- |
| `just check` | `fmt` + `lint` + `test` | **書いている間** | **2〜3 秒** |
| `just check-all` | 上 + `cov` | リリース前と CI | **5〜8 秒**（冷えた状態で 11 秒） |

なでしこ3 版の [ADR-015](ADR-015-step-directories.md) と同じ考え方です。**速さが要るのは書いている間で、全部は CI の仕事**です。

### 3. カバレッジは `cargo-llvm-cov`、下限はドメイン層 80%

Kotlin 版の kover と同じ下限にします。`justfile` の変数 `cov_min` に置き、`--fail-under-lines` で落とします。

### 4. devShell の外から呼ばれたら入り直す（2026-09-29 追記）

**IDE から `just check` を叩いて気づきました。** この版の道具は devShell から来るので、外から叩くとホストの道具が使われます。

| 項目 | devShell 内 | ホスト |
| :--- | :--- | :--- |
| rustc | 1.91.1 | **1.97.1** |
| `cargo-llvm-cov` | 0.6.20 | 0.8.7 |
| `LLVM_COV` / `LLVM_PROFDATA` | 設定済み | **未設定 → `cov` が落ちる** |

**別のコンパイラで通って CI で落ちます。** 2 対象は道具をリポジトリに取り込んでいる（`./gradlew`・`./node_modules/.bin/cnako3`）ので起きませんが、rustc は取り込めません。

`justfile` が `IN_NIX_SHELL` を見て、外なら `nix develop` に入り直します。中にいれば何も挟みません。

再入は 1 回だけにしました。`check` を依存指定から 1 行に変えたのはこのためです（依存のままだと `fmt`・`lint`・`test` がそれぞれ入り直して 3 回になる）。**外から叩いても 3〜4 秒のままです。**

### 5. devShell に `just` と `cargo-llvm-cov` を足す

どちらもホストの `~/.cargo/bin` に入っていましたが、**CI には来ません**。`ops/nix/environments/rust/shell.nix` に足しました。

**`cargo-llvm-cov` は rustup の `llvm-tools-preview` を探しに行きますが、Nix にはありません。** rustc の LLVM 版（21.1.7）と `llvmPackages.bintools` の LLVM 版が一致していたので、`LLVM_COV` と `LLVM_PROFDATA` を `shellHook` で指すようにしました。

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| `Makefile`（2 対象と同じ） | 動くが、`just --list` に相当するものを自前で書くことになる（2 対象では `grep` + `awk` で書いた）。**Just はタスクランナーとして作られており、その部分を書かなくてよい** |
| `cargo-make` | 設定が TOML で冗長になる。この規模では過剰 |
| カバレッジを入れない | 「入れない」も選べたが、**Kotlin 版と同じ定量ゲートを持てるなら持つ**ほうが 3 対象の比較がしやすい。なでしこ3 版だけが計測手段を持たない、という形になる |
| `just check` にカバレッジも入れる | 書いている間の待ち時間が倍以上になる。**速さが要るのは書いている間**（なでしこ3 版 Unit 7 の学び） |
| `tarpaulin` | macOS のサポートが弱い。`cargo-llvm-cov` は rustc の LLVM をそのまま使う |

## 影響

- **段を入れる基準ができました。** 「何を守るか」を書けない段は入れません
- `just --list` がタスク一覧になります。説明はレシピ直前のコメント 1 行です
- CI とローカルが同じ devShell を使うので、**「ローカルでは動くが CI で落ちる」が減ります**
- **3 対象で初めて、なでしこ3 版が持てなかったカバレッジの定量ゲートを持ちます**

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| **カバレッジの下限が意味を持つか** | 第 1 章の時点でコードが 30 行弱しかなく、80% に意味はありません。**Unit 3（ドメインが育つ）で見直します** |
| **`clippy` の指摘の仕分け** | `-D warnings` は設計判断に混ざります。押された箇所を `README.md` に記録し、**第 13 章で「設計の改善」と「clippy の好み」に仕分けます** |
| **`just` のバージョン差** | devShell の 1.45.0 に固定されます。ホストに別の版があっても devShell が優先されます。ただし **`justfile` を最初に解析するのはホストの `just`** です（1.43.0 で確認）。`env()` と `/` 演算子はどちらの版にもあります |
| **Nix が無い環境** | 再入が失敗します。**CI に Nix を入れるか、外側で `nix develop` を回すかを Unit 2 で決めます**（`.github/workflows/rust-zettai.yml` は未作成） |
| **IDE 側の `PATH` の引用** | IntelliJ が `PATH` を引用せずに渡して `export` が壊れることがあります。リポジトリからは直せません。**実行構成の環境変数から `PATH` の上書きを外すのが対処**で、この `justfile` は PATH に依存しないので上書きする理由がありません |
| **段が増えたときの時間** | 段階（workspace のメンバー）が増えれば伸びます。**増やす前に見積もり、直後に測ります**（なでしこ3 版 Unit 5 Try 2） |

## コンプライアンス

- `justfile` の各レシピに「何を守るか」が書かれていること
- `just check` が 20 秒以内であること
- `just check-all` が CI で回ること
