## ユーザーストーリー

### US-010: 1 コマンドを 1 transaction で処理する

| # | 受入条件 |
| :--- | :--- |
| 1 | コマンドの読み取り、判断、追記が、1 つのトランザクションになる |
| 2 | 業務の失敗、defect、中断のどれでも、何も追記せず、接続を返す |
| 3 | 同じリストを作る 2 つのコマンドを同時に実行すると、片方だけが受け付けられる |
| 4 | 同じ契約を、メモリと PostgreSQL の保管で確かめる |

リリース計画の受入条件の「競合の検出」は、3 で満たします。版の検査と、競合の専用の失敗は足しません（[ADR-064](../adr/ADR-064-typescript-command-transaction.md)）。

### US-011: 入力の誤りをまとめて知る

| # | 受入条件 |
| :--- | :--- |
| 1 | リスト名の検証は、空でないこと、40 文字以内、使えない文字を含まないことを独立に確かめ、すべての誤りを順に返す |
| 2 | 利用者名と新しいリスト名の誤りを、まとめて返す |
| 3 | 蓄積の合成が、結合律と、成功の場合の値の保存を満たすことを性質テストで確かめる。逐次の合成は最初の失敗で止まることを、テストで固定する |
| 4 | `GET`・`POST /todo/{user}/{listname}/rename` で、画面から名前を変えられる。成功は 302、検証の失敗は 400 で理由を並べた同じ画面、業務の規則の失敗は理由に応じた状態になる |
| 5 | 名前の変更は、2 つのストリームを 1 回の更新で扱う |
| 6 | 画面は、埋め忘れとエスケープ漏れを防ぐ仕組みで組み立てる |
| 7 | 受け入れシナリオに名前の変更を加え、3 経路で通る |
