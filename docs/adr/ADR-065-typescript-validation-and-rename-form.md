# ADR-065 TypeScript FP 版は検証の問題を自作の合成で蓄積し、画面はタグ付きテンプレートで組み立てる

日付: 2026-11-28

## ステータス

2026-11-28 推奨案を採用しました（Unit 6 のゲート ②）。**同期停止していません。** 利用者の事前の指示「執筆完了まで、判断はすべて推奨を採用する」によるもので、人が個別に確認してはいません

## コンテキスト

第 11 章で、画面からリストの名前を変えます。入力の誤りは、まとめて利用者に返します。蓄積の方式と、フォームを含む画面の組み立て方を決めます。

### 先に確かめたこと

Effect 4.1.6 で確かめました（2026-11-28）。

| API | 結果 |
| :--- | :--- |
| `Result.all` に 2 つの失敗を渡す | 最初の失敗だけを返す |
| `Effect.validate` | 配列の要素ごとの失敗を集める。結果は `Effect` |
| `Schema` の `errors: "all"` | 項目をまたいで問題を集める。返る値は `SchemaError` |

## 決定

1. **検証の結果を `Result<A, ReadonlyArray<E>>` にし、2 つを合わせる `zipWith` を自作する**
2. **40 文字の制限は、新しい名前の入力（`validateNewListName`）にだけ掛ける。** 保存済みの行は、空でないことと保存できる文字であることだけを確かめる
3. **名前の変更は、古いストリームの `ListRenamed` と、新しいストリームの `ListCreated`・`ItemAdded` にする。** 2 つのストリームを 1 回の `update` で扱う（[ドメインモデル設計](../design/domain-model.md)）
4. **画面は、文字列を必ずエスケープするタグ付きテンプレート `markup` で組み立てる。** タグの名前を `html` にしない
5. **フォームの送信は、成功で 302、入力の問題で 400 の同じ画面、業務の失敗は理由に応じた状態と固定の本文にする**（[UI 設計](../design/ui_design.md)）
6. **HTTP の接続は POST と `content-type` を渡し、本文は 10,000 バイトまでにする**

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| `Effect.validate` | 検証は実行を伴わない。核は `Effect` の型を読み込まないと決めている |
| `Schema` の `errors: "all"` | 返る問題を、業務の言葉の型に直す処理が要る |
| 40 文字の制限を、すべての名前の生成に掛ける | 過去に保存した長い名前が、読めなくなる |
| 既製のテンプレートエンジン | **比べていない。** タグ付きテンプレートで、渡し忘れとエスケープの要件を満たせた |

## 影響

### ポジティブ

- 問題が、業務の型の配列になる。画面の文言は `Record` で、足し忘れを型が止める
- テンプレートの値は TypeScript の式なので、無いかもしれない値は型検査が止める

### ネガティブ

- **CSRF の対策がありません。** 別のサイトからの送信で名前が変わることを確かめました。この版には認証もありません。開発機の `127.0.0.1` で動かす見本であり、公開の環境で使ってはいけません
- 利用者名は URL の値をそのまま使います。その利用者であることは確かめません
- 名前を変えると、状態の変更の履歴は新しいストリームに引き継がれません。一覧では末尾に移ります
- 項目の説明の文字の制約は、まだありません
- テンプレートは HTML の文脈（属性、URL、スクリプト）を区別しません。URL は、組み立てる側で符号化します

## コンプライアンス

- 蓄積の順序と結合の性質テストがある
- 長い保存済みの名前を読めることを、保管の契約で確かめる
- 名前の変更を、3 経路の受け入れシナリオで確かめる
