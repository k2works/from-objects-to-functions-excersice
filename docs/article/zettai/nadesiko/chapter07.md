# 第 7 章 関数型手法によるエラーハンドリング

## より適切なエラー処理

ここまで、失敗を 2 通りで表してきました。

| 章 | 失敗の表し方 | 分からないこと |
| :--- | :--- | :--- |
| 2 | リストが見つからないとき `空` を返す | 利用者が無いのか、リストが無いのか |
| 6 | コマンドが拒否されたときイベント 0 件を返す | 同名のリストがあったのか、リストが無かったのか、遷移が許されなかったのか |

**どちらも「失敗した」しか言っていません。**

`空` はさらに厄介です。なでしこ3 の `空` は空文字列で、次の 3 つを同じ形で表します。

- 値が無い
- 空文字列そのもの
- まだ調べていない

そして第 2 章で踏んだとおり、**辞書に無いキーを引くと `undefined` が返り、これは `空` とも違います。**

### 何を返すべきか

欲しいのは「成功したか失敗したか」と「失敗ならその理由」です。値にします。

```nako3
●(値で)成功
    {"成功":真,"値":値}で戻る
ここまで

●(理由で)失敗
    {"成功":偽,"理由":理由}で戻る
ここまで
```

Kotlin 版は `Outcome<E, T>` という型で、`Success<T>` と `Failure<E>` の 2 つだけを取ります。`sealed` なので**これで全部**だとコンパイラが知っています。

なでしこ3 では辞書です。`成功` キーの真偽で区別します。**「これで全部」という保証はありません。** `{"成功":真}` だけの辞書を作っても、誰も止めません。

### 失敗の理由

4 種類です。列挙型が無いので、第 4 章の状態と同じやり方をします。

```nako3
●失敗理由一覧
    ["ListNotFound","ItemNotFound","ListAlreadyExists","InvalidTransition"]で戻る
ここまで
```

そして契約テストが 4 種類の網羅を守ります。

## ファンクタと圏を学ぶ

結果を作れるようになりました。次は**使う**側です。

リストを取得して、その項目の数を数えたいとします。素直に書くとこうなります。

<!-- code-check: ignore 説明のための素朴な書き方。実装には入れていない -->

```nako3
取得=状態で利用者とリスト名の状態内リスト取得
もし、(取得の成功判定)=偽ならば
    取得で戻る
ここまで
数=取得["値"]["項目"]の要素数
数で成功で戻る
```

**5 行のうち、やりたいことは 1 行です。** 残りは「失敗だったらそのまま返す」という定型です。そしてこの定型は、結果を使うたびに現れます。

まとめられます。

```nako3
●(結果にFを)結果マップ
    # 成功なら中の値に F を適用する。失敗はそのまま素通しする。
    # これがファンクタ。恒等則と合成則を性質テストで確かめる。
    もし、結果["成功"]=偽ならば
        結果で戻る
    ここまで
    新値=F(結果["値"])
    新値で成功で戻る
ここまで
```

これで、さっきの 5 行が 1 行になります。

### 何が起きたのか

`結果マップ` がしていることを、形だけ取り出します。

- **箱がある**（結果）
- **箱の中身に関数を適用する手段がある**（`結果マップ`）
- **箱の外側は変わらない**（成功は成功のまま、失敗は失敗のまま）

これを満たす箱を**ファンクタ**と呼びます。第 5 章のモノイドと同じで、**構造があって、性質が確かめられて、それから名前が付きます。**

性質は 2 つです。

| 名前 | 言っていること |
| :--- | :--- |
| 恒等則 | 「そのまま返す関数」を `map` しても、何も変わらない |
| 合成則 | `map(f)` してから `map(g)` は、`map(f と g をつないだ関数)` と同じ |

恒等則は「`map` が余計なことをしない」ことを言っています。合成則は「`map` を何回に分けても結果が同じ」ことを言っています。**この 2 つが成り立つから、安心して `map` を並べられます。**

「圏」という言葉もありますが、ここでは踏み込みません。**必要なのは、この 2 つの性質が成り立つかどうかだけ**です。

## ファンクタを使ったエラーハンドリング

### 性質を確かめる

第 5 章と同じやり方です。乱数で入力を作り、法則を確かめます。

```nako3
●乱結果作成
    # 成功と失敗を混ぜる。成功だけで試すと素通しの側を確かめられない。
    種=0から1までの乱整数
```

成功だけで試してはいけません。**`結果マップ` の半分（失敗を素通しする側）を一度も通らない**からです。

```bash
  ok 恒等則が 200 回とも成り立つ
  ok 合成則が 200 回とも成り立つ
```

### 壊して確かめる

通ったことは確かめたことになりません。

| 壊し方 | 恒等則 | 合成則 |
| :--- | :--- | :--- |
| 失敗も `map` してしまう（素通しをやめる） | **104 / 200** | 0 |
| `map` が値を 1 足す | **96 / 200** | **94 / 200** |

どちらも落ちました。

**第 5 章のモノイドと比べてみます。** 結合律を非結合的な合成で壊したとき、検出は 200 回中 13 件でした。ファンクタ則は 100 件前後です。**法則によってテストの感度がまるで違います。**

理由ははっきりしています。ファンクタ則は**すべての入力について**成り立つべきもので、壊せばほぼ毎回ずれます。結合律は、ランダムに選んだ変換の多くが互いに干渉しないので、順番を変えても結果が変わりません。

**検出率の低い法則ほど、入力の多様性に気を配る必要があります。**

1 つだけ、落ちなかった組み合わせがあります。「失敗も `map` してしまう」壊し方で、合成則は 0 件でした。合成則は `map` を 2 回するか 1 回するかの違いを見るので、**両方が同じように壊れていれば差が出ません。** 法則は 1 つでは足りない、ということです。

## Outcomeを使って実装する

### 契約テストを先に変える

ポートの契約を変えます。`状態内リスト取得` が `空` ではなく結果を返すようにします。

**Kotlin 版ならここで型を変えます。** `ToDoListFetcher = (User, ListName) -> ToDoList?` を `-> Outcome<ZettaiError, ToDoList>` にすれば、**使っている場所が全部コンパイルエラーになります。** どこを直せばいいかが一度に分かります。

なでしこ3 では何も起きません。呼び出し側は `undefined` を読んで、動き続けます。

そこで**実装より先にテストを変えました。**

```bash
$ make test STEP=step2
  FAIL 作成コマンドは成功する: 型が違う 実際=undefined 期待=boolean
  FAIL 見つかれば成功: 型が違う 実際=undefined 期待=boolean
  FAIL ハブ経由でコマンドが成功する: 型が違う 実際=undefined 期待=boolean
テスト 8 本成功 / 3 本失敗
```

**落ちた 3 件が波及の一覧です。** これが型検査の代わりになります。

### 波及は 5 箇所あった

実装を直して走らせると、**さらに 2 箇所落ちました。**

```bash
[実行時エラー]test/step2/ddt/actions_domain.nako3(19行目): TypeError: Cannot read properties of undefined (reading '0')
[実行時エラー]src/step2/web.nako3(47行目): TypeError: Cannot read properties of undefined (reading '0')
```

| 段階 | 見つかった箇所 |
| :--- | :--- |
| 契約テストを先に変えた時点 | 3 件（`events_test`・`commands_test`・`hub_test`） |
| 実装を変えて実行した後 | **2 件**（`web.nako3`・`ddt/actions_domain.nako3`） |

**合計 5 箇所です。型があれば 5 件すべてが一度に分かります。**

契約テストは型検査の代わりになりますが、限界があります。**テストが無い場所は教えてくれません。** `web.nako3` の該当行には直接のテストがなく、受け入れテストを走らせて初めて落ちました。もし受け入れテストも無ければ、ブラウザで開くまで気づきません。

**「契約テストを書く」という規律は、型の代わりというより、型を持たないことの授業料です。** 判断は [ADR-018](../../../adr/ADR-018-outcome-dict-port.md) に記録しました。

### 拒否に理由を付ける

第 6 章でイベント 0 件だった拒否を、理由のある失敗にします。

```nako3
    もし、種別=「CreateToDoList」ならば
        もし、有無=真ならば
            重複=「ListAlreadyExists」で失敗
            重複で戻る
        ここまで
```

リストが無いときは、取得の失敗をそのまま返します。

```nako3
        もし、有無=偽ならば
            既存で戻る
        ここまで
```

**理由を作り直していません。** `状態内リスト取得` が返した `ListNotFound` をそのまま流します。失敗が値なので、持ち回せます。

### HTTP に届ける

失敗の理由は 4 種類、ステータスコードは 404 と 400 です。対応表を持ちます。

```nako3
●(理由の)失敗状態コード
    # HTTP の層はこの対応表だけを見る。ドメインは HTTP を知らない。
    表={"ListNotFound":404,"ItemNotFound":404,"ListAlreadyExists":400,"InvalidTransition":400}
```

この対応表を**ドメインの側**に置きました。HTTP のことを知っているように見えますが、知っているのは「数値」だけです。`404` が HTTP のステータスコードであることは、使う側が決めます。

HTTP の層はこうなります。

```nako3
    取得=ハブで要素[1]と要素[2]のハブリスト取得
    もし、(取得の成功判定)=偽ならば
        # 失敗の理由からステータスコードを決める。
        # ドメインは HTTP を知らず、対応表だけが両者をつなぐ。
        番号=取得["理由"]の失敗状態コード
        {"状態":番号,"本文":「<h1>{番号}</h1><p>{取得["理由"]}</p>」}で戻る
    ここまで
```

ブラウザで確かめます。

```bash
$ curl -s http://localhost:8080/todo/uberto/none
<h1>404</h1><p>ListNotFound</p>
```

**「404」ではなく「ListNotFound だから 404」と言えるようになりました。**

### つまずき: 関数値を式の中に書くと呼び出しになる

`結果マップ` に関数を渡すテストを、最初こう書いて落ちました。

<!-- code-check: ignore わざと壊した書き方。直した形は下に載せている -->

```nako3
写=成に({関数}倍)を結果マップ
```

```bash
[文法エラー]: 関数『倍』で引数が指定されていません。2個の引数を指定してください。
```

2 つのことが同時に起きています。**`倍` が組み込み命令と衝突している**ことと、**`{関数}` を式の中に書くと呼び出しとして解釈される**ことです。

```nako3
# 関数値は一度変数に受けてから渡す。式の中に {関数} を書くと呼び出しになる。
倍F={関数}値二倍
写=成に倍Fを結果マップ
```

第 4 章で「関数値を引数に渡すときはカッコで包む」と書きました。**カッコで包むのは定義済みの関数名を渡すときで、`{関数}` から作るときは変数に受けます。** 規則が 2 つあるのは覚えにくいところです。

## まとめ

- `空` は「値が無い」「空文字列」「まだ調べていない」を区別しません。**イベント 0 件も「なぜ」を持ちません**
- 失敗を**理由を持つ値**にしました。成功も失敗も同じ形（結果辞書）で運べます
- 「箱の中身に関数を適用し、外側は変えない」という形が**ファンクタ**です。恒等則と合成則が成り立つから、安心して `map` を並べられます
- 法則によって**テストの感度がまるで違います**。ファンクタ則は 100 / 200 前後で壊れを検出し、第 5 章の結合律は 13 / 200 でした
- **法則は 1 つでは足りません。** 「失敗も map してしまう」壊し方は、恒等則では 104 件、合成則では 0 件でした
- 契約を変えたとき、**先にテストを変えて 3 件、実装を変えて 2 件**、合わせて 5 箇所が波及しました。型があれば一度に分かります
- **契約テストは型の代わりというより、型を持たないことの授業料です。** テストの無い場所は教えてくれません

次の章では、表示のためのモデルを本体から切り離します。イベントを畳み込む先が「今の状態」だけでなく「画面に出したい形」にもなります。そこにも `map` が現れ、同じファンクタの形が繰り返されます。
