# ADR-005 プロパティベーステストを自前で書き kotest-property を導入しない

日付: 2026-09-27

## ステータス

2026-09-27 提案されました

## コンテキスト

第 5 章で、状態変換の合成がモノイドであることを示す必要が出ました。モノイド則（結合律・単位元）は「例をいくつか挙げても成り立つとは言えない」種類の性質で、ランダムな入力を多数試す**プロパティベーステスト**が適しています。

これ以降も、第 7〜8 章でファンクタ則、第 9 章でモナド則を扱うため、同じ道具を繰り返し使います。

Kotlin で使える主なライブラリは [kotest-property](https://kotest.io/docs/proptest/property-based-testing.html) で、最新安定版は 5.9.1 です（6.0.0 はマイルストーン）。

## 決定

**kotest-property を導入せず、自前のジェネレータと繰り返しで書きます。**

```kotlin
private fun repeatWithRandomEvents(
    check: (List<ToDoListEvent>, List<ToDoListEvent>, List<ToDoListEvent>) -> Unit
) {
    repeat(trials) { seed ->
        val random = Random(seed)
        check(/* ランダムな出来事の列を 3 つ */)
    }
}
```

生成器はドメインごとに `EventGenerator` として持ちます。

### 採らなかった理由

1. **ドメイン固有の生成器はどちらにせよ自前で書く。** `List<ToDoListEvent>` をランダムに作るには、kotest でも `Arb.bind` や `Arb.of` を組み合わせて自作することになります。ライブラリを入れても、書く量はあまり減りません
2. **説明コストが増える。** `checkAll` は suspend 関数なので `runBlocking` が要ります。記事で「なぜここに `runBlocking` があるのか」を説明する必要が出て、モノイドの説明から読者の注意が逸れます
3. **依存を増やさない方針と整合する。** [ADR-004](ADR-004-static-analysis.md) と同じ考え方です。このプロジェクトで実際に起きる問題に効くかどうかで判断します
4. **`repeat` + シード固定の 20 行で足ります。** 失敗の再現も、シードが整数なので容易です

### 失うもの

kotest-property が持つ次の機能は得られません。

| 機能 | 影響 |
| :--- | :--- |
| シュリンキング（失敗する最小の入力を探す） | 失敗時の原因特定が手作業になる。ただし入力が小さい（列の長さ 0〜5）ので実用上の差は小さい |
| 統計情報（生成された値の分布） | 生成器の偏りに気づきにくい。生成器を自分で書いているので、偏りは読めば分かる |
| エッジケースの自動投入（空・境界値） | 生成器で明示的に含める必要がある。現在は列の長さ 0 を含めている |

シュリンキングが効いてくるのは、入力が大きく構造が複雑なときです。本連載の対象では、そこまでの規模になりません。

## 影響

- 第 5・7・8・9 章で同じ形のプロパティベーステストを書きます。`EventGenerator` のようなドメイン固有の生成器が章ごとに増えます
- 記事では「なぜ例示テストでは足りないのか」を説明でき、ライブラリの使い方の説明に紙面を使わずに済みます
- 失敗したときは、シードを固定して再現し、手で入力を縮めます

## 再検討の条件

次のいずれかに当たったら、kotest-property の導入を検討します。

1. プロパティベーステストが 3 つ以上のドメインに広がり、生成器の重複が目立つようになった
2. 失敗の再現と原因特定に時間を取られるようになった（シュリンキングが欲しくなった）
3. 生成器の偏りが原因で、あるはずの反例を見逃したことが判明した

**再検討は Unit 5（第 9 章、モナド則）を目安にします。** そこまでで 3 種類の法則を書くことになり、重複の有無が判断できます。

## コンプライアンス

- 法則を確かめるテストが、ランダムな入力を一定回数（現在 200 回）試していること
- 失敗時に再現できるよう、乱数のシードが固定されていること
