# 対象言語の横断比較

Zettai を複数の言語で書くと、同じ設計が言語ごとに違う形で現れます。ここでは章を閉じるたびに、その章で見えた違いを 1 つずつ足していきます。

当初の比較軸は 1 つでした。**Kotlin 版は「型で保証する」、なでしこ3 版は「約束とテストで保証する」。**

**Rust 版で軸が広がりました。** 「型があるか」ではなく「**言語がどこまで与えるか**」です。

| 対象 | 型 | 関数型の道具 | `Outcome` 相当 | 代数的データ型 |
| :--- | :--- | :--- | :--- | :--- |
| Kotlin | あり | あり | **自前で作る** | `sealed interface` |
| なでしこ3 | なし | なし | **辞書で作る** | 無い |
| Rust | あり | あり | **`Result` が言語にある** | `enum` |

- [Kotlin 版](../kotlin/index.md)（完結・13 / 13 章）
- [なでしこ3 版](../nadesiko/index.md)（完結・13 / 13 章）
- [Rust 版](../rust/index.md)（進行中・3 / 13 章）

## Phase 1（第 1〜3 章）で見えた違い

> **Rust 版の列を 2026-09-29 に足しました。** 以下の表は当初 2 対象で書いたもので、Rust 版の行を追記しています。

### テストの土台

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| テストフレームワーク | JUnit 5 + Strikt | **無い。** 検証関数とランナーを自作（[ADR-014](../../../adr/ADR-014-own-test-framework.md)） |
| 失敗の判定 | 例外と終了コード | **終了コードが常に 0。** `プロセス終` で明示し、出力のエラー表示も併せて見る |
| 型の取り違え | コンパイルが通らない | **`=` が型を区別しない。** 値を比べる前に `変数型確認` 同士を比べる |
| カバレッジ | Kover（ドメイン層 80%） | **計測できない。** 受け入れシナリオ数で代替する |

Kotlin 版は第 1 章の大半を「テストを関数型に書く」ことに使えました。なでしこ3 版は**その前に「テストを書く道具を作る」段階**が入ります。

**Rust 版は逆の極でした。**

| 観点 | Rust |
| :--- | :--- |
| テストフレームワーク | **言語にある**（`#[test]` と `assert_eq!`）。自作は 0 行 |
| 失敗の判定 | `cargo test` の終了コード |
| 型の取り違え | コンパイルが通らない |
| カバレッジ | `cargo-llvm-cov`（ドメイン層 80%） |

**第 1 章で自作したものがありません。** 代わりに**後戻りの効かない判断**（async の採否・HTTP クレートの選定）を実測してから決める章になりました（[ADR-024](../../../adr/ADR-024-no-async.md)・[ADR-025](../../../adr/ADR-025-tiny-http.md)）。

3 対象で第 1 章の中身が違います。**Kotlin は書き方、なでしこ3 は道具づくり、Rust は判断**でした。

### ドメインの表し方

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| ドメインの型 | `data class ToDoItem(val description: String)` | 辞書 `{"説明":説明}` |
| 契約の保証 | コンパイラ | **契約テスト**（キーの有無と値の型） |
| 契約の置き場所 | 型定義の 1 箇所 | 実装とテストの 2 箇所 |
| 契約を破ったとき | コンパイルが通らない | **`undefined` が返るだけ。** テストが無ければ気づけない |

**同じ設計に到達しています。** 違うのは、契約が「1 箇所に書けば守られる」か「2 箇所に書いて片方が片方を見張る」かです。

Rust は Kotlin と同じ側です。`struct` のフィールドをコンパイラが見ます。**違いは型の数**で、`String` と `&str` が別物なので、テストの期待値を揃える 1 行が要りました（第 3 章）。

### 境界の引き方

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| 境界の定義 | `zettai.domain` パッケージがフレームワークを import しない | `src/domain.nako3` がプラグインを取り込まない |
| 表現手段 | パッケージ | **ファイルだけ。** 公開範囲の制御は無い |
| 検査 | `DomainBoundaryTest`（import を機械的に検査） | `boundary_test.nako3`（ファイルの中身の文字列を数える） |

**どちらも「不在」を検査しています。** 手段は違っても、境界の守り方は同じ形になりました。

**Rust だけが検査を書きませんでした。**

| 観点 | Rust |
| :--- | :--- |
| 境界の定義 | `zettai-stepN-domain` と `zettai-stepN-http` を別クレートにする |
| 表現手段 | **クレート**。`Cargo.toml` の `dependencies` が依存の一覧そのもの |
| 検査 | **無し。** 書いていない相手を呼ぶとコンパイルが止まる（[ADR-027](../../../adr/ADR-027-crate-boundary.md)） |

実測しました。同一クレート内でドメインから HTTP を呼ぶと**エラー 0 件**、クレートを分けると `error[E0433]` で止まります。**ビルド時間は変わりませんでした。**

なでしこ3 版は章が進むごとに検査の項目が増え（第 2 章 1 項目 → 第 12 章 5 項目 × 7 ファイル）、第 4 章では一覧への足し忘れが起きかけました。**Rust では `Cargo.toml` が一覧なので、足し忘れようがありません。**

### 受け入れテストの入口

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| 枠組み | Pesticide（ライブラリ） | **無い。** 操作の辞書と関数値で自作 |
| 経路の差し替え | `DdtActions` の実装を差し替える | 関数値を詰めた辞書を差し替える |
| HTTP 経由の経路 | テストの中からサーバを起動できる | **できない。** `Makefile` が起動と停止を持つ |
| 経路の関数 | 入出力をしてよい | **入出力をできない。** 関数値ごしに非同期を待てないため、応答を先に記録する |

なでしこ3 版は制約に押されて、**シナリオに渡す関数が両経路とも純粋になりました。** 関数型の設計としてはむしろ望ましい形です。**制約が設計を良い方向に押すことがあります。**

**Rust では「寄せる先があるのに寄せない」判断をしました。**

| 観点 | Rust |
| :--- | :--- |
| 枠組み | **トレイト 1 つ**（自作。[ADR-028](../../../adr/ADR-028-own-acceptance-trait.md)） |
| 既製品 | `cucumber` はある。**依存 6 → 127、ビルド +92 秒**で `just check` の上限 20 秒を単独で超える |
| HTTP 経由の経路 | **サーバを起こさない。** ハンドラが HTTP の型を返さないので関数として呼べる |

第 3 章第 5 節（Kotlin 版では「DDT を Pesticide に変換する」）で、**3 対象の結論が 3 つとも違いました。**

| 対象 | この節でしたこと |
| :--- | :--- |
| Kotlin | 自作 → ライブラリ（Pesticide）に寄せた |
| なでしこ3 | 自作のまま（寄せる先が無い） |
| Rust | **調べて、寄せないと決めた** |

**言語が何を与えるかで、同じ判断の答えが変わります。**

### 型検査があっても止まらないもの

なでしこ3 版の Unit 2 で、`繰り返す` が開始より終了が小さいときに逆向きに回ることが分かり、空の配列を回すコードが 5 箇所すべて潜在バグでした。

**これは型システムがあっても止まりません。** 「型で保証する」対「約束とテストで保証する」という軸の外側に、**言語の癖という第 3 の要素**があります。どちらの版でも、踏んでからガードや検査にするしかありません。

## Phase 2（第 4〜9 章）で見えた違い

### 依存の注入

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| ポートの宣言 | `typealias ToDoListFetcher = (User, ListName) -> ToDoList?` | 関数の名前と助詞 |
| 注入 | 関数の値を渡す | 関数値を辞書に詰める（`{"リスト参照":…}`） |
| **注入できるもの** | すべての関数 | **純粋な関数だけ。** 入出力をする関数は注入できない |

最後の行がこの版の設計をほぼ決めています。**関数値ごしに呼ぶと、中の非同期な組み込み命令が待たれず Promise が返ります。** 連載を通して **5 度**踏みました（第 3・7・9・10・12 章）。

そのたびに**副作用を関数の外へ押し出して**います。5 回とも、関数型の設計としては素直な方向でした。

### イベントと畳み込み

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| イベントの型 | `sealed interface ToDoListEvent` | `種別` キーの文字列。**「これで全部」の保証は無い** |
| 網羅の保証 | `when` がコンパイル時に網羅を要求 | 一覧に集め、契約テストが網羅を守る |
| 畳み込み | `fold` | **再帰で書けない。** 配列を削りながら自分を呼ぶ形はパーサが解決できず、ループで書いた |
| 不変性 | `data class` | **言語サポート無し。** 変換のたびに `辞書写し` と `配列複製` をする |

**外から見た振る舞いは同じです。** 畳み込みがループで書かれていても、状態を書き換えなければ畳み込みです。

### 失敗の表し方

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| 型 | `Outcome<E, T>`（`sealed`） | 辞書 `{"成功":真偽,"値"/"理由":…}` |
| 失敗の種類 | `sealed` なので足すと扱い漏れがコンパイルエラー | 一覧 `失敗理由一覧` と契約テスト |
| 契約を変えたときの波及 | コンパイラが全箇所を示す | **静かに通る。** 第 7 章で数えたら 5 箇所で、うち 2 箇所は実行するまで分からなかった |

**型が無いと波及が静かです。** 契約テストの無い場所は教えてくれません。

### 永続化

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| 保存先 | PostgreSQL（1 テーブル） | **追記型のファイル**（[ADR-019](../../../adr/ADR-019-file-event-log.md)）。DB プラグインが無い |
| 追記 | `INSERT` | **追記の命令が無い。** 読んで足して書き戻す |
| トランザクション | ある | **無い。** 原子性は保証しない |
| ポート | `EventPersister`（注入する） | **注入しない。** 呼び出しの順序で表す（上記の制約） |

イベントソーシングとファイル追記は相性がよく、**題材としてはむしろ素直**でした。失ったのは原子性と同時実行の安全だけです。

## Phase 3（第 10〜13 章）で見えた違い

### 文脈の持ち回り

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| 文脈 | `TxContext`（DB 接続。不透明な型） | **接続が無い。** 「どこを読み書きするか」を文脈とした（[ADR-021](../../../adr/ADR-021-context-as-path.md)） |
| 組み立て | `ContextReader` を組み立て、最後に文脈を渡す | **組み立てられない。** 入出力を含む計算を値にできない |
| 境界の表し方 | 計算の合成 | **呼び出しの順序** |
| 保証すること | トランザクションの原子性 | 「判断が失敗したら 1 行も書かない」だけ |

**「できないこと」を章の主題にしました。** 中身の無い文脈を形だけ真似ることはしていません。

文脈を「接続」ではなく「どこを読み書きするか」と定義したおかげで、第 12 章で記録の行き先を足すときに定義を広げずに済みました。

### 複数のエラーを集める

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| 型 | `Validation<T>`（`Valid` / `Invalid`） | 辞書 `{"成功":真偽,"理由列":配列}` |
| 結果との使い分け | 型が違うので取り違えない | **`成功` のキーを揃えた。** 失敗側だけが違う |
| 並びの連結 | `+` | **`&` は文字列にしてしまう。** 1 件ずつ足す |

**モナドとアプリカティブの違いを数字にできました。** 両方だめな入力 69 回すべてで、結果連鎖は理由を 1 件しか返しませんでした（100%）。

### JSON と双方向変換

| 観点 | Kotlin | なでしこ3 |
| :--- | :--- | :--- |
| JSON の生成 | 手書き → 自前の `Converter` に発展（Kondor は入れない） | **組み込みの `JSONエンコード` がある。** 捨てない（[ADR-023](../../../adr/ADR-023-builtin-json-with-converter.md)） |
| 解いた問題 | 書き出しと読み込みが別々で片方だけ直せる | **同じ問題が残っていた。** 手書きかどうかは関係なかった |
| 壊れた入力 | `Outcome` で返る | **例外が飛ぶ。** 境界 1 か所で捕まえて結果に変える |

**「自前で書く」を惰性で続けませんでした。** 足りていたのは JSON の生成で、足りなかったのは「対であること」だけでした。

### 代数構造の確かめ方

7 つの構造を両版で扱いました。Kotlin 版は型が構造を表し、なでしこ3 版は**性質テストだけ**が表します。

| 構造 | 章 | なでしこ3 版で検出率が 0 になった壊し方 |
| :--- | :--- | :--- |
| モノイド | 5 | 恒等変換が状態を変える → 結合律が 0 |
| ファンクタ（結果） | 7 | 失敗も `map` する → 合成則が 0 |
| ファンクタ（射影） | 8 | `F` を 2 回適用する → 恒等則が 0 |
| モナド | 9 | 失敗も連鎖する → 左単位元と結合律が 0 |
| アプリカティブ | 11 | （0 は無し。最小 115 / 200） |
| プロファンクタ | 12 | 出力側の合成順を入れ替える → 0 / 200 |

**法則が複数あるのは飾りではありません。** そして**どの構造にも、法則が捕まえない壊し方があります。**

同じ 13 章を辿った結果、支えているものはこうなりました。

最終段階（Kotlin 版 `zettai-step5-monitoring` / なでしこ3 版 `src/step5`）で数えます。

| | Kotlin 版 | なでしこ3 版 |
| :--- | :--- | :--- |
| 型定義 | **57**（`data class` 36・`typealias` 9・`sealed interface` 7・ほか 5） | **0** |
| テストファイル | 32 | 25（+ 受け入れの部品 4） |
| うち性質テスト | 9 | 6 |
| 契約テスト | 補助的 | **16 ファイル。** 型検査の代わり |
| 境界検査 | import の検査 1 本 | ドメイン 7 ファイル × 5 項目 |
| 受け入れシナリオ | 2 経路 | **3 経路**（ドメイン直接・HTTP 経由・保管経由） |
| 誤りが分かるまで | コンパイル | `make check`（**7〜11 秒**） |

**差は 7〜11 秒です。** 書いている間の体験は違いますが、本番に届く前に止まるという点では同じところに来ています。

止まらないものもあります。**テストの無い場所**です。型は書いた全部を見ますが、テストは書いた分しか見ません。

## 第 3 の要素: 言語の癖

**「型で保証する」対「約束とテストで保証する」という軸の外側に、もう 1 つあります。**

なでしこ3 版の Unit 2 で、`繰り返す` が開始より終了が小さいときに逆向きに回ることが分かり、空の配列を回すコードが 5 箇所すべて潜在バグでした。**これは型システムがあっても止まりません。**

連載を通して、こうした癖を **25 件**集めました（`apps/nadesiko/zettai/README.md`）。

**そして一覧を作ったら、設計の間違いが止まりました。** 第 10 章は設計を 1 回も間違えていません。一覧を作るのに 30 分もかかっていません。**3 回踏んでから作ったのが遅すぎたのです。**

ただし一覧で防げないものもあります。

| 種類 | 例 | 一覧で防げるか |
| :--- | :--- | :--- |
| 設計に関わる制約 | 関数値ごしに入出力を呼べない | **防げる**（読めば設計を変えられる） |
| 名前の衝突 | `合計`・`倍`・`コマンド実行`・`検証`・`表示` | **防げない**（踏んでから直す。エラーが教える） |
| 既存の関数への追加で壊れるもの | 記録を足したら関数値ごしに呼べなくなった | **防げなかった**（制約は知っていたが、この形で現れるとは思わなかった） |

## Rust 版で増える比較

Rust 版は進行中です（3 / 13 章）。章を閉じるたびに足します。

| 章 | 比較の焦点 |
| :--- | :--- |
| 4〜5 | **所有権のもとでの関数型 DI とクロージャの合成。** 3 対象で最も重い Unit と見込んでいる |
| 6〜7 | **`enum` と `Result` が言語にある。** Kotlin 版が自前で作ったものを使う側 |
| 8〜9 | 射影と PostgreSQL 永続化。**同期のまま通す**（[ADR-024](../../../adr/ADR-024-no-async.md)） |
| 10〜11 | 境界とライフタイム。アプリカティブは自前 |
| 12〜13 | serde と tracing の採否。**3 言語の総括** |
