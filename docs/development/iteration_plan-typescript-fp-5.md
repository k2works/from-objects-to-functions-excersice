## ゴール

> 読み取り側を射影で分け、出来事を PostgreSQL に保存する。**確認したい仮説**: 接続の寿命を `Scope` と `Layer` で表せる。

### Unit 完了時の達成状態

- 利用者ごとのリストの一覧が、項目数と完了数つきで見える
- command の経路と query の経路が分かれている
- 出来事が PostgreSQL に追記され、停止と再起動をしても残る
- 受け入れシナリオが、domain・HTTP・DB の 3 経路で通る

## ユーザーストーリー

### US-008: 読み取り側を射影で分離する

| # | 受入条件 |
| :--- | :--- |
| 1 | 出来事の列から、利用者のリストの行（名前、項目数、完了数）を作る射影が、純粋な関数である。行は作成順に並び、ほかの利用者の出来事は含まない |
| 2 | 生成した出来事の列で、射影の行が、状態を畳み込んで数えた行と一致する |
| 3 | `GET /todo/{user}` が行の一覧を返す。値はエスケープする。リストの無い利用者は、行の無い一覧になる |
| 4 | ハブの query は、command の状態を経由せずに、出来事から射影する。command は、対象のリストの出来事だけを読む |
| 5 | `map` の恒等則と合成則を、`Effect` と配列を重ねた形で性質テストにする |
| 6 | 受け入れシナリオに「自分のリストの一覧を、項目数と完了数つきで見られる」を加え、2 経路で通る |

### US-009: イベントを PostgreSQL に安全に保存する

| # | 受入条件 |
| :--- | :--- |
| 1 | 出来事は追記だけで保存し、追記順に読み戻せる。読み戻した出来事は、保存した出来事と一致する |
| 2 | 1 回の保存は、すべて残るか、何も残らないかのどちらかになる |
| 3 | 壊れた行（未知の種類、必須の値の欠落、不正な値）は、読み出しで失敗にし、黙って捨てない |
| 4 | 接続は、成功、失敗、中断のどの場合も返す |
| 5 | データベースの失敗は、理由を応答に出さずに 500 になる |
| 6 | `Effect.flatMap` の左右の単位元と結合律を、結果と実行の記録で確かめる |
| 7 | 同じ受け入れシナリオを、DB を使う 3 経路目でも実行する。Docker が無い場合は skip せずに失敗する |
