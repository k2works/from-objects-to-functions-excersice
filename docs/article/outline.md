# 執筆計画：関数型プログラミングで作る変更を楽に安全にできるソフトウェア

本シリーズは、Uberto Barbini 著『From Objects to Functions』を下敷きに、ToDo リストアプリケーション **Zettai** を TDD で一から作りながら、オブジェクト指向から関数型へ設計を移していく連載です。

- 章・節構成の一次情報は [章構成マインドマップ](draft.md) です。記事の節見出しはこれに一致させます。
- 原著のコンパニオンコードは `references/fotf/` に読み取り専用の参照元として置いています。**記事に載せるコードは参照元からの転載ではなく、`apps/{lang}/zettai/` の自作実装から転記します。**
- シリーズの索引は [Zettai シリーズ索引](zettai/index.md) です。
- 本計画を AI-DLC の Intent・Unit・Bolt に落としたものが対象ごとのリリース計画（Level 1 計画）です。[Kotlin 版](../development/release_plan.md)（完結）、[なでしこ3 版](../development/release_plan-nadesiko.md)（計画中）。本ファイルは章構成と執筆規約の一次情報、リリース計画は進行と進捗の一次情報とし、章の割り当てが変わったときは両方を揃えます。
- 各章は 1 つの **Bolt**（時間〜日単位の作業単位）に対応し、2 章で 1 つの **Unit**（独立して公開できる単位）を構成します。局面別の TDD アプローチと承認ゲートの密度は [開発戦略](../development/development_strategy.md) にあります。

**Rust 版で 3 点目が入ります。** 軸は「型の有無」ではなく「**言語がどこまで与えるか**」に広がります。

| 対象 | 型 | 関数型の道具 | `Outcome` 相当 | 代数的データ型 |
| :--- | :--- | :--- | :--- | :--- |
| Kotlin | あり | あり | **自前で作る** | `sealed interface` |
| なでしこ3 | なし | なし | **辞書で作る** | 無い（`種別` キーの約束） |
| Rust | あり | あり | **`Result` が言語にある** | `enum` |

3 点を並べると、**「言語が与えるほど、設計は楽になるのか」**という問いが立ちます。Rust 版はこの問いに答える対象です。

## なでしこ3 追加執筆計画

2 言語目として、日本語プログラミング言語 **なでしこ3** で同じ 13 章を書き起こします。Kotlin 版で「型で保証していたもの」を、型のない言語でどう保証するかを示すのがこの対象の狙いです。TDD の進め方と実装基盤の組み方は、既存の連載 `references/getting-started-tdd/docs/article/nadesiko/`（全 12 章）と `references/getting-started-tdd/apps/nadesiko/` を手本にします。

### 採用理由と処理系の選定

| 項目 | 内容 |
| :--- | :--- |
| 採用理由 | 型システム・ユーザー定義型・代数的データ型・モナド記法のいずれも持たない言語で同じ設計に到達させることで、Kotlin 版の各章が「言語機能の説明」ではなく「設計の説明」であったことを確かめられる |
| 処理系 | **cnako3**（npm パッケージ `nadesiko3` 3.8.7、Node 実装）を採用する |
| 選定の根拠 | cnako3 には簡易 HTTP サーバのプラグインがあり、『簡易HTTPサーバ起動時』『簡易HTTPサーバ受信時』『簡易HTTPサーバ出力』『簡易HTTPサーバヘッダ出力』『簡易HTTPサーバ移動』と `HTTPメソッド`・`GETデータ`・`POSTデータ` でルーティングとフォーム POST が書ける。Zettai の題材（HTTP の ToDo Web アプリ）がそのまま成立する |
| gonako を採らない理由 | 参考連載が使う Go 実装の CLI（`gonako`）には、記事群・実装ともネットワーク機能の記述がない。第 2 章以降を CLI 題材に全面再編することになり、Kotlin 版との章の対称性が崩れる |

#### 実行環境の方針

- テストフレームワークが存在しないため、組み込みの `【A】と【B】がASSERT等` を土台に検証関数とテストランナーを自作します。値を比べる前に `変数型確認` 同士を比べ、`=` が型を区別しないことによる見逃しを防ぎます。**cnako3 は実行時エラーでも終了コードが 0 を返す**ので、`テスト結果報告` が失敗時に `1でプロセス終` を呼び、ランナー側は出力に `[エラー]` が含まれるかも併せて見ます（Unit 1 で判明）。
- 受け入れテストは `doctest/` に期待出力を書く形式で置き、`make check` から実行します。
- 第 9 章の永続化は、PostgreSQL ではなく**追記型イベントログのファイル保存**とします。イベントソーシングとは相性がよく、`docker-compose.yml` への追加も不要です。

## Rust 追加執筆計画

3 言語目として **Rust** で同じ 13 章を書き起こします。

なでしこ3 版は「型も関数型の道具も無い」側の極でした。Rust 版は反対側の極です。**Kotlin 版が自前で作ったもの（`Outcome`・代数的データ型）が、言語に最初からあります。** 同時に、Kotlin 版にもなでしこ3 版にも無かった制約（所有権・借用・ライフタイム）が入ります。

### 採用理由

| 項目 | 内容 |
| :--- | :--- |
| 採用理由 | Kotlin 版が第 7 章で自前実装した `Outcome` が、Rust には `Result` として言語にある。**言語が与えるものが増えたとき、章の主題がどう変わるか**を見る。あわせて、なでしこ3 版で「制約が設計を押した」現象が、型の側の制約（所有権）でも起きるかを確かめる |
| 処理系 | **rustc 1.91.1 / cargo 1.91.0**（Nix devShell `rust`。clippy 0.1.91・rustfmt 1.8.0 も同梱） |
| 環境が既にある | `ops/nix/environments/rust/shell.nix` と `flake.nix` の `devShells.rust` は導入済み。**前提整備の負荷が 3 対象で最も軽い** |
| 3 言語目にこれを選ぶ理由 | 「型なし + 関数型あり」（Clojure など）は象限としては新しいが、**連載で最も使った道具（`Outcome`）に直接当たらない**。Rust は `Result` と `enum` でそこに当たる |

### 章の読み替え

章の番号・タイトル・焦点は Kotlin 版と一致させ、実現手段だけを差し替えます。**節名の読み替えは現時点で 0 件の見込み**です（データベースを使うため、なでしこ3 版で読み替えた 5 件はそのまま使えます）。

| 章 | テーマ（Kotlin 版と共通） | Rust での実現手段 | 到達点 |
| :--- | :--- | :--- | :--- |
| 1 | 新しいアプリケーションを準備する | cargo・**組み込みの `#[test]`**・clippy・rustfmt | `cargo test` が 1 本通る。**自作するものが無い**（なでしこ3 版と正反対） |
| 2 | 関数を使って HTTP を扱う | HTTP クレートを 1 つ選ぶ（Unit 1 のスパイクで決定） | 縦串。**所有権との初遭遇** |
| 3 | ドメインの定義とテスト | 受け入れテストをトレイトまたはクロージャで抽象化 | ドメインとアダプタをモジュールで分離 |
| 4 | ドメインとアダプタのモデリング | 関数型 DI を `impl Fn` / `Box<dyn Fn>` / ジェネリクスのどれで表すか | **所有権が設計を押す最初の章** |
| 5 | イベントで状態を変更する | `fold` と、状態変換のクロージャ合成 | モノイド。**クロージャの所有とライフタイム** |
| 6 | コマンドを実行してイベントを生成する | **`enum` + `match`。網羅はコンパイラが保証する** | 関数型ステートマシン。Kotlin 版とほぼ同じ形になる見込み |
| 7 | 関数型手法によるエラーハンドリング | **`Result<T, E>` が言語にある。`?` 演算子もある** | ファンクタ。**主題が「作る」から「使う／作らない判断」に変わる** |
| 8 | ファンクタを使ってイベントを射影する | 射影は自前。`map` は言語にある | CQRS |
| 9 | モナドによる安全なデータ永続化 | PostgreSQL。**同期クレートか async かを選ぶ**（async は全体に伝播する） | モナド則。Kotlin 版と同じ題材が使える |
| 10 | コンテキストを読み込み、コマンドを処理する | `ContextReader` 相当を借用で書くか、所有で書くか | **ライフタイムが境界の設計に直接効く** |
| 11 | アプリカティブによるデータバリデーション | `Result` は短絡するので、集約する型を自前で作る | 最初の失敗で止めない。**ここは自前になる** |
| 12 | 監視と関数型 JSON | serde と tracing。**どちらも既製品がある** | プロファンクタ。**「自前で書くか」をなでしこ3 版と同じ手順で判断する** |
| 13 | 関数型アーキテクチャの設計 | 総括と **3 言語の対比** | 「言語が与えるほど設計は楽になるのか」に答える |

### この対象で新しく問われること

| 問い | 章 | なぜ新しいか |
| :--- | :--- | :--- |
| **言語が与えるものを使うか、作るか** | 7・11・12 | Kotlin 版は `Outcome` を自前で作り、なでしこ3 版は辞書で作った。Rust は `Result` がある。**使う判断も記録に値する** |
| **型が設計を押すことはあるか** | 4・5・10 | なでしこ3 版は「制約が設計を押した」が 5 回あった。所有権でも同じことが起きるなら、**制約の出どころが型でも型の不在でも同じ**という話になる |

| **測れない指標は、指標が無いより悪い** | 「人が検証に使った時間」を最初から置かない。「人が修正を入れた箇所数」を使う |
| **しきい値には分布の計算を添える** | 性質テストの検出率のしきい値は、期待値と標準偏差を出してから置く |
| **段階を切る手順を書く** | cargo workspace のメンバー追加手順を、最初の段階を切るときに ADR へ書く |
| **共有する書き込み先は最初からテストごとに分ける** | 永続化とログを入れる章で、テストごとに接続先・出力先を分ける |
| **変更依頼数の定義が曖昧だった** | Unit 1 の計画で定義を決めてから使う |

### 進め方

1. Unit 1 で cargo workspace と `just check` を整え、**同期で最後まで行けるか**と **HTTP クレートの選定**をスパイクで確かめ、第 1 章を書く
2. 以降は 2 対象と同じく「実装 → 記事執筆 → サイト反映 → コミット」を 1 Bolt として、章 2 本で 1 Unit を閉じる
3. Phase 1 の完了時に `comparison/` に Rust の列を足す

## 執筆規約

- 見出しは階層を飛ばさない。章内の節は [draft.md](draft.md) のマインドマップに一致させる
- コードブロックには言語を明示する。差分を示すときは変更箇所が分かる粒度で切る
- **記事のコード例は必ず対象言語のサンプル実装（`apps/kotlin/zettai/`・`apps/nadesiko/zettai/`・`apps/rust/zettai/`）の動作確認済み実装から転記する。** 憶測で書いたコードを載せない
- 長い完成コードは `<details>` に入れ、本文には差分だけを載せる
- 日本語と半角英数字の間に半角スペース。文体はですます調。技術用語は英語のまま
- 読者が実行するコマンドは、プロンプト記号を混ぜず、コピーしてそのまま動く形で書く
- 原著のコードや文章をそのまま転載しない。参照した箇所は出典として示す
- 章を追加したら `mkdocs.yml` の nav、[シリーズ索引](zettai/index.md) の全章構成表と進捗管理表、本ファイルの対象一覧を必ず揃える
- なでしこ3 版では、コードブロックの言語タグを `nako3` とし、識別子にひらがなを使わない（助詞として分割されるため）。Red の直後には実際のエラー出力を `bash` ブロックで貼る
- 同じ章を複数の対象で書くときも、章の番号・タイトル・焦点は変えない。変えるのは実現手段だけとし、言語固有の制約は章内の「つまずき」節にまとめる
- **節名が特定の対象に固有の語（ライブラリ名・言語名・製品名）を含む場合は、対象言語での対応物に読み替える。** マインドマップ本体は 1 言語目の記事が参照しているため変えず、[draft.md](draft.md) の「言語別の読み替え」表に登録してから記事を書く。節の位置と役割は変えない（規則は Unit 5 で「ライブラリ名」から「対象に固有の語」に広げた。第 9 章に `PostgreSQL`・`Kotlin` が入っていたため）
- 章の割り当て・検証負荷・Unit / Bolt の構成を変えたら、本ファイルの章別計画と対象のリリース計画（[Kotlin 版](../development/release_plan.md) / [なでしこ3 版](../development/release_plan-nadesiko.md)）の Unit 分解・ストーリー一覧・進捗状況を同じコミットで揃える
