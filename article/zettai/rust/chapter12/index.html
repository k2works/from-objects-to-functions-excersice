    第 12 章 監視と関数型 JSON¶

    11 章かけて Zettai を作りました。動いていることは分かりますが、何が起きているかは分かりません。

    この章で記録を出します。そしてもう 1 つ、第 9 章で残した宿題を片づけます。

    アプリケーションを監視する¶

    記録の契約をドメインに置きます。手段は知りません。

    pub struct Record {
    /// 何が起きたか。業務の言葉で書く。
    pub what: String,
    /// 付帯する値。**キーと値の並び。**
    pub fields: Vec<(String, String)>,
}

    文字列 1 本にしません。 後から絞り込めるようにするためです。

    3 対象で共通の方針です（ADR-021）。違うのは守り方です。

    対象 ドメインが記録の手段を知らないことを、何が守るか
    Kotlin DomainBoundaryTest（import の検査）
    なでしこ3 boundary_test.nako3（文字列の検査。第 12 章で項目が 5 つ目になった）
    Rust Cargo.toml。ドメインは依存 0 なので、記録の実体を書けない

    第 3 章から続いている構図です。 2 対象は検査を足し、Rust は何も足していません。

    構造化されたロギング¶

    既製品を調べた — そして要求を満たしていた¶

    tracing を測りました。要求（構造を持つ記録・差し替えられる出力先）を既定で満たします。

    tracing: {"timestamp":"...","fields":{"message":"追記した","user":"uberto","appended":2},...}

    出力先の差し替えもテストで確かめました。満たしています。

    それでも入れませんでした。

    自前 tracing + subscriber
    依存クレート +0 +18
    ビルド 0 秒 15.23 秒

    just check の余裕が 4 秒弱しかありません。 第 11 章で tera（+3・18.42 秒）を入れたときとは、払う額が違います。

    「要求を満たすか」だけでは決まりませんでした。 第 11 章では自作する理由が消えたので入れました。ここでは入れる余地がありません。

    つまずき 1: 記録を足す場所が、境界を入れたことで変わっていた¶

    EventStore の append と events_of に記録を足しました。1 件も出ませんでした。

    第 10 章で境界を入れてから、実際の読み書きは単位の中の口（TxEventStore の実装）を通ります。PgTx に持たせる必要がありました。

    境界を入れると、通り道が変わります。 記録のような「後から足すもの」は、通り道の上に置かないと効きません。

    JSON を関数型にする¶

    第 9 章の宿題です。ADR-032 にこう書きました。

    1 件の代償では判断が決まりません。 第 12 章でログの JSON が要るとき、もう一度測ります。自前のパーサが 3 か所に増えていたら判断を変えます

    数えた。そして条件の書き方が曖昧だったことが分かった¶

    自前で文字列を解く箇所は 3 種類ありました。

    # 何を解くか 足した章
    1 JSON 9
    2 フォーム 11
    3 HTML（テスト用） 3・11

    「自前のパーサ」が JSON だけを指すなら 1 か所です。 条件を書いたときに、数え方を決めていませんでした。

    条件を書くことと、条件が判定できることは別です。

    serde も要求を満たしていた¶

    serde: {"ItemAdded":{"item":"読む 本&\"<x>\""}}

    derive は 1 つの宣言から両方向を作ります。 綴りがずれようがありません。これは第 9 章で解けなかった問題そのものです。

    それでも入れませんでした。理由が tracing とは違います。

    属性を書く先の ToDoListEvent はドメインのクレートにあります。第 3 章から依存 0 を守ってきました。 それは境界検査を 1 行も書かずに済んだ根拠です。

    鏡の型を HTTP 側に置く手はありますが、ドメインとの写しを手で書くことになり、対であることの利点がそこで失われます。

    12 章通しで守ったものを、最終 Unit で崩すことになります。

    プロファンクタとの出会い¶

    自前で書きます。書き出しと読み込みを 1 つにします。

    pub struct Converter<A, B> {
    write: Write<A, B>,
    read: Read<A, B>,
}

    第 9 章は to_json と from_json が別々でした。片方だけ直せます。 そして実際に片方だけ直しています。jsonb の正規化に対応したとき、読み側だけを直しました。

    対にすると、片方だけ直す形がそもそも書けません。

    入力側と出力側で向きが逆¶

        pub fn contramap<A2: 'static>(
        self,
        to: impl Fn(&A2) -> A + 'static,
        from: impl Fn(A) -> A2 + 'static,
    ) -> Converter<A2, B> {
        Converter {
            write: Box::new(move |a2| (self.write)(&to(a2))),
            read: Box::new(move |b| (self.read)(b).map(&from)),
        }
    }

    to と from の両方が要ります。 書くときは A2 → A、読むときは A → A2 です。向きが逆だから、写す関数も 2 つ要ります。

    ファンクタ（第 7・8 章）は map が 1 つで足りました。出力側しか無かったからです。

    構造 写せる向き 要る関数
    ファンクタ 出力側だけ 1 つ
    プロファンクタ 入力側と出力側 2 つ（向きが逆）

    検出率¶

    「片方だけ直した対」を作って測りました。 第 9 章で実際にやったことです。

    片方だけ直した対の検出 188 / 200

    3 桁の数のときだけ、書くときに空白を足します。読み側は直っていません。

    p = 900 / 1000 = 0.9
期待値 = 200 × 0.9 = 180、σ = √(200 × 0.9 × 0.1) = 4.24

    実測 188 は +1.9σ です。しきい値は期待値から 4σ 下（163）に置いています。

    第 8 章で 1.8σ のずれを見たとき、生成器を疑って数え直しました。 今回も同じくらいずれていますが、壊し方が決定的（3 桁なら必ず落ちる）なので、ずれは生成する数の偏りだけから来ます。

    つまずき 2: clippy に 3 回目の type_complexity¶

    pub type Write<A, B> = Box<dyn Fn(&A) -> B>;
pub type Read<A, B> = Box<dyn Fn(&B) -> Result<A, ZettaiError>>;

    第 4 章（ハブ）・第 7 章（保管のハブ）に続いて 3 回目です。Box<dyn Fn> を構造体のフィールドに置くたびに止まります。

    名前を付けると、書く側と読む側で型の形が違うことが目に入るようになりました。読む側だけ Result です。失敗しうるのは読むときだけだからです。

    データベース呼び出しのロギング¶

    保管の読み書きを記録します。

    {"what":"イベントを追記した","user":"uberto","list":"book","count":"1"}

    ドメインは記録の手段を知りません。 行き先を差し替えても、呼ぶ側は変わりません。

    記録の JSON も自前です。第 9 章と同じ判断で、ここでも serde_json を入れていません。

    まとめ¶

    • 記録の契約をドメインに置きました。 手段は知りません。クレートの境界が守ります
    • tracing も serde も、要求を既定で満たしていました。 それでも入れていません
    • 理由が 2 つとも違います。 tracing は数字が合わない（+18・15.23 秒）、serde はADR-027 が壊れる
    • 第 11 章で tera を入れたのと、判断の形が違います。 あちらは自作する理由が消えました。ここは入れる余地がありません
    • 条件の書き方が曖昧でした。 「自前のパーサが 3 か所」の数え方を決めていません。条件を書くことと、条件が判定できることは別です
    • 書き出しと読み込みを 1 つにしました。 第 9 章で片方だけ直した形が、書けなくなりました
    • プロファンクタは写す関数が 2 つ要ります。 入力側と出力側で向きが逆だからです
    • 記録を足す場所が、境界を入れたことで変わっていました。 EventStore に足して 1 件も出ませんでした
    • clippy の type_complexity に 3 回目に止められました。 名前を付けたら、読む側だけ Result であることが目に入りました

    次が最終章です。3 言語を並べます。
