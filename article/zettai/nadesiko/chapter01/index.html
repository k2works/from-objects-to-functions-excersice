    第 1 章 新しいアプリケーションを準備する¶

    サンプルアプリケーションを定義する¶

    この連載では、ToDo リストアプリケーションを一から作ります。作りながら、オブジェクト指向で書いた設計を関数型へ移していきます。

    ただし、この版には制約が 1 つあります。使う言語になでしこ3 を選びました。日本語プログラミング言語で、型システムがありません。

    型がないのに関数型の設計を扱うのは、遠回りに見えるかもしれません。しかしこれは、設計の話と言語機能の話を切り分けるための選択です。Kotlin 版 で sealed class や型パラメータを使って表していたものが、型のない言語では何になるのか。同じ設計に到達できるのか。到達できるとしたら、何がその設計を支えているのか。

    答えを先に書きます。支えるのはテストです。 Kotlin 版でコンパイラが担っていた保証を、この版ではテストが肩代わりします。だから第 1 章の大半は、テストを書く準備に費やします。

    Zettai: イノベーティブな ToDo リストアプリケーション¶

    作るアプリケーションの名前は Zettai です。

    やることは単純です。ユーザーごとに ToDo リストがあり、リストには項目が並びます。項目には名前と期限があり、まだ終わっていないか、進行中か、終わったかという状態を持ちます。ブラウザから見られて、項目を足せます。

    イノベーティブな点はありません。それでいいのです。題材が珍しいと、設計の話が題材の説明に埋もれます。 ToDo リストなら、何を作っているかの説明は 1 段落で済みます。残りの紙幅をすべて設計に使えます。

    一方で、ToDo リストには設計の題材として必要なものが揃っています。

    • 状態が変わる（項目を足す、終わったことにする）
    • 不正な操作がある（存在しないリストに足す、終わった項目をもう一度終わらせる）
    • 見せ方が複数ある（リストの一覧、1 つのリストの中身）
    • 保存が要る（アプリケーションを再起動しても消えない）

    この 4 つが、それぞれイベント・エラーハンドリング・射影・永続化の章になります。

    テストに開発をガイドさせる¶

    コードを書く前にテストを書きます。理由は、テストが最初の利用者だからです。

    まだ実装のない関数を呼ぶテストを書くと、その関数に何を渡して何が返ってほしいかを、実装の都合を知らない立場で決めることになります。あとから書くテストは、すでにある実装の形に引きずられます。

    なでしこ3 でこれをやろうとすると、いきなり壁にぶつかります。

    なでしこ3 にはテストフレームワークがありません。 JUnit も RSpec も pytest も、それに相当するものがありません。テストを書き始める前に、テストを書く道具から作る必要があります。

    材料は 2 つあります。組み込みの表明命令と、値の型を実行時に調べる命令です。

    「3」の変数型確認と「string」がASSERT等

    【A】と【B】がASSERT等 は、A と B が等しくなければ実行時エラーを出します。変数型確認 は、値の型を "number" や "string" といった文字列で返します。

    この 2 つを土台に、検証関数とテストランナーを自作します。

    プロジェクトをセットアップする¶

    実行環境¶

    処理系には cnako3 を使います。なでしこ3 の Node 実装で、npm パッケージ nadesiko3 に入っています。

    なでしこ3 には Go 実装の gonako もありますが、そちらを採りませんでした。Zettai は Web アプリケーションで、第 2 章で HTTP サーバを書きます。 cnako3 には簡易 HTTP サーバのプラグインがあり、gonako にはネットワーク機能が見当たりませんでした。判断の経緯は ADR-013 に記録しています。

    バージョンは package.json の 1 箇所で固定します。

      "dependencies": {
    "nadesiko3": "3.8.7"
  }

    Node は 22 以上が必要です。nadesiko3 の engines がそう要求します。

    検証関数を書く¶

    まず、まだ存在しない検証関数を呼ぶテストを書きます。

    !「./helper.nako3」を取り込む

    実行すると、期待どおり失敗します。

    $ make test
[エラー]NakoError: [取り込みエラー]test/bowling_test.nako3(1行目): ファイル .../test/helper.nako3 が存在しません。

    失敗を確認してから、test/helper.nako3 を書きます。

    検証数=0
失敗数=0

●(名前と実際と期待で)検証
    検証数=検証数+1
    実際型=実際の変数型確認
    期待型=期待の変数型確認
    もし、実際型≠期待型ならば
        失敗数=失敗数+1
        「  FAIL {名前}: 型が違う 実際={実際型} 期待={期待型}」と表示
        戻る
    ここまで
    もし、実際≠期待ならば
        失敗数=失敗数+1
        「  FAIL {名前}: 値が違う 実際={実際} 期待={期待}」と表示
        戻る
    ここまで
    「  ok {名前}」と表示
ここまで

    なでしこ3 ならではの点をいくつか。

    • ●(名前と実際と期待で)検証 — 行頭の ● が関数定義の合図です。カッコの中は引数で、名前と・実際と・期待で のように助詞まで含めて書きます。呼ぶときは 「テスト名」と5と5で検証 となり、日本語の語順のまま読めます
    • 実際の変数型確認 — 値の型を文字列で返します
    • {名前} — 文字列の中で {} に囲んだ変数が展開されます

    この関数の要は、値を比べる前に型を比べていることです。 理由は次の節で説明します。

    検証関数自身をテストする¶

    自作した道具は、自分でテストします。これが壊れていると、以降のすべてのテストが嘘をつくからです。

    この層だけは、検証関数ではなく組み込みの ASSERT等 を直に使います。検証関数を検証関数でテストすると、壊れ方によっては両方が同時に黙ってしまいます。

    3の変数型確認と「number」がASSERT等
「3」の変数型確認と「string」がASSERT等

    つまずき 1: = が型を区別しない¶

    なでしこ3 の = は型を区別しません。組み込みの ASSERT等 も同じです。

    $ cnako3 -e '3と「3」がASSERT等
「通ってしまった」と表示'
通ってしまった

    数値の 3 と文字列の 「3」 が等しいと判定されます。型システムのある言語なら、この 2 つを比べようとした時点でコンパイルが通りません。

    これを放置すると、「数値を返すはずの関数が文字列を返している」という誤りをテストが見逃します。型の無い言語でこれを見逃すと、間違いが見つかるのは本番で計算が狂ったときになります。

    だから検証関数は、値を比べる前に 変数型確認 同士を比べます。

        もし、実際型≠期待型ならば

    これが、この連載でコンパイラの代わりを務める最初の仕掛けです。

    つまずき 2: 失敗しても終了コードが 0¶

    テストランナーを書こうとして、2 つ目の壁にぶつかります。

    cnako3 は、実行時エラーでも文法エラーでも終了コードが 0 です。

    $ cnako3 -e '3と4がASSERT等'
[実行時エラー]: AssertionError: Expected values to be strictly equal:
3 !== 4
$ echo $?
0

    エラーメッセージは出ているのに、シェルから見ると成功しています。このまま CI に載せると、テストが落ちているのにビルドが緑になります。

    回避策があります。プロセス終 で終了コードを明示できます。

    ●テスト結果報告
    「  {検証数} 件中 {失敗数} 件失敗」と表示
    もし、失敗数>0ならば
        1でプロセス終
    ここまで
ここまで

    各テストファイルの最後で テスト結果報告 を呼びます。失敗が 1 件でもあれば、そこで終了コード 1 を返します。これでテストランナーが合否を判定できます。

    ただしこれだけでは足りません。文法エラーや取り込みエラーで落ちた場合は、テスト結果報告 にたどり着かないので終了コードが 0 のままです。 そこで判定を 2 つ重ねます。

          out=$$($(CNAKO) "$$t" 2>&1); code=$$?; \
      echo "$$out"; \
      if [ $$code -ne 0 ] || echo "$$out" | grep -qE 'エラー\]'; then \
        fail=$$((fail+1)); echo "  -> FAILED"; \
      else pass=$$((pass+1)); fi; \

    終了コードと、出力にエラーの表示が含まれるかどうか。この 2 つで見ます。この 2 つ目の条件は、第 2 章で一度書き直すことになります。 最初は [エラー] という表示だけを探していて、[実行時エラー] を取りこぼしました。

    文法検査も同じ発想です。cnako3 には lint サブコマンドがありませんが、-A（構文解析だけして AST を出す）を使うと、文法エラーが標準エラー出力に出ます。標準エラー出力が空でなければ文法エラーと判定します。

    テスト基盤を自作する判断と、静的解析を文法検査だけにとどめる判断は ADR-014 に記録しています。

    nix develop .#nadesiko

    make check は文法検査とテストをまとめて実行します。

    ユニットテストを関数型にする¶

    道具が揃ったので、テストを 1 本書きます。題材は Zettai ではなく、ボウリングの得点計算にします。仕様が閉じていて、関数型とオブジェクト指向の違いだけを見られるからです。

    オブジェクト指向でよくある形¶

    なでしこ3 にはクラス構文がありません。それでも、オブジェクト指向でよく書かれる形は再現できます。状態を辞書に持たせて、それを書き換える関数を並べます。

    ●ゲーム作成
    新ゲーム={"投球列":[]}
    新ゲームで戻る
ここまで

●(ゲームにPINSを)投球
    ゲーム["投球列"]にPINSを配列追加
ここまで

    テストはこうなります。

    ゲーム=ゲーム作成
ゲームに5を投球
ゲームに5を投球
ゲームに3を投球
ゲームに0を17で連続投球
「オブジェクト指向版もスペアを加算する」と(ゲームの得点取得)と16で検証

    このテストには、確かめたいこと以外のものが混ざっています。

    • ゲーム という変数があり、テストの行をまたいで持ち回されます。3 行目の結果は 2 行目に依存しています
    • 投球 は値を返さず、ゲーム を書き換えます。何を渡すと何が返るかが関数の形から読み取れません
    • 「5 と 5 と 3 を投げた」という 1 つの入力が、4 行に散らばっています

    なでしこ3 では、この最後の点がとくに効いてきます。ゲーム["投球列"] は参照で、配列追加 は元の配列を書き換えます。辞書を渡した先で中身が変わることを、言語は何も警告しません。

    関数型で書く¶

    同じことを、入力から出力への関数として書きます。

    まずテストです。実装はまだありません。

    # 入力（投球の配列）と出力（得点）だけが見える。準備も後始末も無い。
「ガターゲームは0点」と(([]に0を20で同値連結)の得点計算)と0で検証
「スペアは次の1投を加算する」と(([5,5,3]に0を17で同値連結)の得点計算)と16で検証
「ストライクは次の2投を加算する」と(([10,3,4]に0を16で同値連結)の得点計算)と24で検証

    3 行が独立しています。どの行も、前の行が何をしたかを知りません。入力は [5,5,3] と「0 を 17 回」という 1 つの式にまとまり、出力は 16 です。

    同値連結 は、配列に同じ値を N 個つないだ新しい配列を返します。

    ●(配列にPINSをNで)同値連結
    結果=配列を配列複製
    Kを1からNまで繰り返す
        結果にPINSを配列追加
    ここまで
    結果で戻る
ここまで

    1 行目の 配列複製 が要です。なでしこ3 の配列は参照で、配列追加 は破壊的です。複製してから足さないと、呼び出し元が渡した配列が書き換わります。不変性を言語が守ってくれないので、自分で守ります。

    実装はこうなりました。

    ●(投球列の)得点計算
    得点合計=0
    I=0
    Fを1から10まで繰り返す
        もし、投球列[I]=10ならば
            得点合計=得点合計+10+投球列[I+1]+投球列[I+2]
            I=I+1
        違えば
            フレーム=投球列[I]+投球列[I+1]
            もし、フレーム=10ならば
                得点合計=得点合計+10+投球列[I+2]
            違えば
                得点合計=得点合計+フレーム
            ここまで
            I=I+2
        ここまで
    ここまで
    得点合計で戻る
ここまで

    中では変数を書き換えています。それでいいのです。 関数の外から見れば、投球列を渡すと得点が返るだけです。関数型に書くというのは、中で一切代入しないことではなく、境界の外に状態を漏らさないことです。

    つまずき 3: 組み込み命令名は変数名に使えない¶

    この実装は、最初こう書いて失敗しました。

    $ make test
[文法エラー]src/bowling.nako3(14行目): 関数『合計』に代入できません。

    得点合計 は最初 合計 という名前でした。ところが 合計 はなでしこ3 の組み込み命令です。変数名として使うと、代入の時点で文法エラーになります。

    似た問題がもう一つあります。識別子にひらがなを使うと、助詞として切られます。 変換して装飾 のような名前は「して」の位置で分割され、意味の分からないエラーになります。

    この言語で名前を付けるときの規則は 2 つです。

    1. 組み込み命令と同じ名前を避ける（合計・表示・実行 など）
    2. 識別子は漢字・カタカナ・英数字で組み、ひらがなを混ぜない

    Kotlin 版では考えなくてよかったことです。一方で、名前を短くしたいという圧力が減るので、得点合計 のように意味の分かる名前に落ち着きやすいという副作用もありました。

    まとめ¶

    • 題材は ToDo リストアプリケーション Zettai。珍しくない題材を選ぶことで、紙幅を設計に使える
    • テストを先に書くのは、テストが実装の最初の利用者だから
    • なでしこ3 にはテストフレームワークが無い。検証関数とテストランナーを自作するところから始まる
    • = は型を区別しない。だから検証関数は、値を比べる前に 変数型確認 同士を比べる
    • cnako3 は失敗しても終了コードが 0。プロセス終と出力の検査を重ねて、合否を判定する
    • 関数型に書くとは、中で一切代入しないことではなく、境界の外に状態を漏らさないこと

    第 2 章では、簡易 HTTP サーバとハンドラ関数の合成で、ブラウザから ToDo リストが見えるところまでを一気に通します。動く縦串を最初に通すと、以降の 11 章はその内側を作り込む作業になります。
