## 満足条件

### Intent

> **副作用が型の一部になる言語で、同じ 13 章を辿ったとき、設計は楽になるのか。** 他の対象は、純粋な核と副作用の殻の分離を、設計の規律（Kotlin FP 版）や所有権（Rust 版）で守った。Flix は、効果として型に載せる。

3 つの問いに分けて立てました（[執筆計画](../article/outline.md)）。

1. 副作用を型で追跡すると、核と殻の分離は楽になるか
2. Java 相互運用の境界で、型と効果の保証はどこまで届くか
3. 効果多相や効果ハンドラは、関数型 DI の代わりになるか

答えは [第 13 章](../article/zettai/flix/chapter13.md) にあります。

## リスクと、実際に起きたこと

| 計画で挙げたリスク | 実際 |
| :--- | :--- |
| 言語・標準ライブラリの変更が速い | Flix 0.79.0 に固定し、CI でも同じ版を使った。上げたときの影響は、確かめていない |
| Nix に Flix の定義が無い可能性 | JDK のみ提供し、`flix.jar` を取得するラッパー方式にした。Docker 上の Nix で動かした（2026-11-02）。最初のラッパーは、シェル関数で非対話の使い方ができず、`flix.jar` の保存先もカレントディレクトリ依存だったため、実行可能なスクリプトとキャッシュ置き場に直した |
| Cucumber を使えない可能性 | 試さずに、関数値のレコードを採った（ADR-046） |
| Java 相互運用の注釈が冗長 | 境界を薄い層（`JdkServer`、`PostgresStore`）に閉じ込めた |
| Java 側の副作用が型で保証されない | 切れる場所を各章で記録した。Java の呼び出しの効果が一律でないことも観察した |

計画に無かったが起きたことは、[リリース完了報告書](release_report-flix-1.0.0.md) にあります。
