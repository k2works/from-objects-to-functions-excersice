# 2026-09-27 Unit 5 — 試してから入れないと決める

Unit 5（第 8〜9 章）を完了させた。射影と CQRS、そして PostgreSQL への永続化。Phase 2 が終わり、Release v0.2.0 の条件を満たした。

不確実性が Unit 1 以来もっとも高い Unit で、ゲートを 4 箇所から 8 箇所に戻した。

## 試してから「入れない」と決めた

Unit 2 で「静的解析を入れない」と決めたとき、**試していなかった**。ADR-004 に「Unit 5 で再検討する」と書いておいたので、今回戻ってきた。

まず条件を確かめた。「書き方のブレが実際に問題になっているか」。**なっていた。** 行長 120 超が 2 件、import の並びが崩れたファイルが 3 件。行長は記事のコードブロックが折り返す原因で、この連載固有のリスクに直結する。

そこで ktlint を実際に入れて動かした。結果、標準ルールが引数を強制的に複数行へ分割し、`if (x) a else b` をブロックに展開し、式の本体を必ず改行した。**記事のコード例が 40 件ずれた。**

つまり ktlint の整形は、この連載のコードを「記事に載せにくい形」に変える方向に働く。目的（行長と import 順の 2 点）に対して副作用が大きすぎる。

整形を取り消して、必要な 2 点だけを検査する 30 行のスクリプトを書いた。検出した 5 件のうち行長の 2 件は、鍵を作る関数（`ToDoListEvent.key()`）を切り出して短くした。**汎用ツールの整形より意味のある切り出しになった。**

前回は試さずに「入れない」と決めた。今回は試したので、**「合わなかった」ことを具体的に書けた**。結論は同じでも、根拠の強さが違う。

## 評価が当たることと、原因を予測できることは別

結合テストの「検証の不確実性」を HIGH と評価した。予想していたのは不安定さ（Docker の起動待ち、ポートの衝突、データ残留）だった。

**不安定さは出なかった。** 3 回連続 green。`healthcheck` を compose と CI の両方に置き、テストごとに `TRUNCATE` したのが効いた。

代わりに別の理由で落ちた。**PostgreSQL の `JSONB` は保存時に JSON を正規化する。** コロンの後に空白が入る。自作の JSON パーサが空白を許していなかった。

```text
書き込み: {"user":"uberto","listName":"book"}
読み出し: {"user": "uberto", "listName": "book"}
```

`JSONB` を選ぶなら、保存した文字列がそのまま返る前提は置けない。文字列として厳密に往復させたいなら `TEXT` にする。

学びはこうだ。**HIGH と評価する意味は「この領域で何か起きる」であって「何が起きるか分かる」ではない。** 評価は当たったが、原因は予想と違った。予測できないから HIGH なのだと言ったほうが正確だ。

## 検査そのものにも漏れがある

第 9 章に `docker-compose.yml` の設定を載せたら、記事のコード例検査が「実装に存在しない」と 7 行を報告した。

**記事が正しく、検査が間違っていた。** 検査の探索先に compose ファイルが入っていなかっただけだ。

危なかったのは、**一瞬「記事を直そう」と考えた**ことだ。検査が緑にならないと気持ちが悪いので、記事側を曲げようとする。検査が出す結果も、内容を見て判断する対象だった。

Unit 2 でこの検査を作ったとき「人が見ていた判断を機械に移した」と書いた。移したあとも、機械の言うことを鵜呑みにはできない。

## 3 つめの法則も同じ形で書けた

モノイド（第 5 章）・ファンクタ（第 7・8 章）・モナド（第 9 章）を、同じテストの形で検証した。`forAllRandom` も生成の考え方も変えていない。

記事の構成も 3 回目だ。**構造 → 性質 → 名前 → 身の回りの例。**

- モノイド: 整数の足し算、文字列の連結
- ファンクタ: `List.map`
- モナド: `List.flatMap`

3 回とも「知っていたことに名前が付いた」形に着地できた。**同じ型を使い回せると、読者も書き手も楽になる。**

第 11 章のアプリカティブも同じ順序で書く。

## 実装より先に ER 図を作った

Unit 4 の学び（表を先に作ると判断の漏れが見える）をスキーマに適用した。ER 図とテーブル定義を実装の前に作った。

先に作ったことで、「テーブルは 1 つでよい」「正規化を論じる必要がない」という判断が固まった。**追記だけで UPDATE も DELETE もしないので、正規化が解決する問題が起きない。**

コードから書き始めていたら、たぶん `todo_list` と `todo_item` のテーブルを作っていた。**普通の設計の型に引きずられる。**

スキーマは変更コストが高いので、順序を守る価値が大きい領域だった。

## 密に戻した判断

変更依頼 0 件だった。Unit 3・4（疎）も 0 件だったので、数字だけ見ると「密にする必要はなかった」と読める。

そうは思わない。8 箇所のゲートのうち 3 つで、実際に判断が必要になった。

- ADR の再検討 → **ktlint を試して採用しない**という結論
- スパイク → ORM を使わない判断
- スキーマ設計 → テーブルを 1 つにする判断

**ゲートで止まって判断したから、手戻りが起きなかった**と解釈する。ゲートが不要だったのではない。

Unit 3・4 との違いは「新しく現れる判断が機械に移せているか」だった。この基準は 3 Unit 通して機能している。

## 次回に活かすこと

- **Unit 6 は疎に戻す。** 終盤（アウトサイドイン）に移り、法則のテストは 3 回書いた形が使える。ただしテンプレートエンジンは新規ライブラリなのでゲートを 1 つ置く
