    第 5 章 イベントで状態を変更する¶

    ToDoリストの作成の表示¶

    第 4 章までで、リストを表示できて、取得元を差し替えられるようになりました。次は変更です。

    ただし、その前に決めることがあります。変更を何として保存するかです。

    素直に考えれば、今の状態を持っておいて、変更のたびに書き換えます。項目を追加したら配列に足す。終わったことにしたら状態を書き換える。

    この章ではそうしません。 保存するのは「何が起きたか」です。

    • uberto が book というリストを作った
    • uberto の book に write chapter が追加された

    これを順に並べたものが、保存する内容のすべてです。今の状態はそこから計算します。

    なぜそうするのか¶

    理由は 1 つです。起きたことの並びからは今の状態を導けますが、今の状態からは何が起きたかを導けません。

    情報量が違います。状態だけを持つと、「なぜこうなったか」が消えます。並びを持てば、いつでも状態を作り直せるし、途中の状態も再現できます。

    まずは、作っただけで項目が 0 件のリストを表示できるようにします。これが「リストを作った」というイベントが効いていることの、一番小さな証拠です。

    状態変更の保存¶

    イベントを定義する¶

    イベントは辞書です。過去形で名付けます。 すでに起きたことなので取り消せません。

    ●(利用者とリスト名で)リスト作成イベント
    {"種別":"ListCreated","利用者":利用者,"リスト名":リスト名}で戻る
ここまで

●(利用者とリスト名と項目で)項目追加イベント
    {"種別":"ItemAdded","利用者":利用者,"リスト名":リスト名,"項目":項目}で戻る
ここまで

    Kotlin 版は sealed interface ToDoListEvent で、2 つのイベントがその実装です。sealed なので、イベントを 1 種類足すと扱い忘れている場所がコンパイルエラーになります。

    なでしこ3 に直和型はありません。種別 というキーの文字列で区別します。「これで全部」という保証はありません。 イベントを足したときに分岐を書き忘れても、何も起きません。

    全体の状態¶

    状態も辞書です。

    ●空状態
    {"リスト表":{}}で戻る
ここまで

    リスト表 の鍵は 利用者/リスト名 です。利用者ごとに入れ子にする手もありますが、平たくしました。取り出すときの分岐が 1 段で済みます。

    再帰の力を解き放つ¶

    イベントの並びから状態を作る操作を畳み込みと呼びます。教科書的には再帰で書きます。

    空の並びなら初期状態。そうでなければ、先頭を適用してから、残りを畳み込む。

    なでしこ3 で再帰は書けます。

    $ cnako3 -e '●(Nの)階乗
    もし、N<=1ならば
        1で戻る
    ここまで
    前=(N-1)の階乗
    N*前で戻る
ここまで
「{5の階乗}」と表示'
120

    ところが、畳み込みの形では書けませんでした。

    [文法エラー]: 関数『合計再帰』の定義で以下のエラーがありました。
[文法エラー]: 『ここまで』がありません。関数定義の末尾に必要です。『=』の前に『ここまで』を記述してください。

    配列を削りながら自分を呼ぶ形にすると、パーサが関数の終わりを見失います。引数を 2 つにしても、ループを別の関数に追い出しても、カッコで包んでも、同じでした。単純な数値の再帰は通り、この形は通りません。

    書けないときどうするか¶

    節の題は「再帰の力を解き放つ」です。力を解き放てませんでした。

    ここで選べる道は 3 つあります。

    道 判断
    処理系を変える 第 2 章以降のすべてをやり直すことになる。合わない
    回避策を探し続ける 見つかるかもしれないが、見つかる保証がない。連載が止まる
    ループで書き、外から見た振る舞いを畳み込みに保つ 採る

    3 つ目を採りました。

    ●(イベント列を)畳込
    # 再帰で書きたかったが、配列を削りながら自分を呼ぶ形は
    # パーサが自己参照を解決できない（単純な数値の再帰は書ける）。
    # ここはループで書き、外から見た振る舞いを畳み込みに保つ。
    # 状態は書き換えず、変換のたびに新しい状態を作る。
    状態=空状態
    もし、(イベント列の要素数)=0ならば
        状態で戻る
    ここまで
    Iを0から(イベント列の要素数)-1まで繰り返す
        変換=イベント列[I]の状態変換作成
        状態=変換(状態)
    ここまで
    状態で戻る
ここまで

    中では変数を書き換えています。それでいいのです。 第 1 章で書いたとおり、関数型に書くというのは中で一切代入しないことではなく、境界の外に状態を漏らさないことです。

    畳込 は、イベントの並びを渡すと状態が返るだけの関数です。中が再帰でもループでも、呼ぶ側には関係ありません。再帰は畳み込みを表す 1 つの書き方であって、畳み込みそのものではありません。

    失ったものもあります。再帰で書けば「空なら初期状態、そうでなければ先頭を適用して残りを畳み込む」という定義がそのままコードになります。ループはそれを手続きに翻訳した形です。定義とコードの距離が開きました。

    イベントを畳み込む¶

    1 件のイベントを関数にする¶

    畳み込みの中心は、イベント 1 件を「状態から状態への関数」に変えるところです。

    ●(イベントの)状態変換作成
    種別=イベント["種別"]
    もし、種別=「ListCreated」ならば
        変換=関数(状態)
            鍵=「{イベント["利用者"]}/{イベント["リスト名"]}」
            新表=状態["リスト表"]の辞書写し
            新表[鍵]=イベント["リスト名"]と[]でToDoリスト作成
            {"リスト表":新表}で戻る
        ここまで
        変換で戻る
    ここまで

    返しているのは関数です。イベントを渡すと、状態を受け取って新しい状態を返す関数が返ります。

    無名関数が外側の イベント を捕まえています。クロージャです。なでしこ3 でも、関数を作って返せます。

    つまずき 1: 辞書を複製する命令が無い¶

    辞書写し という自作の関数が出てきました。

    ●(辞書の)辞書写し
    # 辞書複製に相当する命令が無いのでキーを写す。
    # 元の辞書を書き換えないために、変換のたびに写す。
    新辞書={}
    鍵列=辞書の辞書キー列挙
    もし、(鍵列の要素数)=0ならば
        新辞書で戻る
    ここまで
    Iを0から(鍵列の要素数)-1まで繰り返す
        新辞書[鍵列[I]]=辞書[鍵列[I]]
    ここまで
    新辞書で戻る
ここまで

    配列には 配列複製 がありますが、辞書に相当する命令がありません。 自分で書きます。

    写さないとどうなるか。状態変換が元の状態を書き換えてしまい、畳み込みの途中の状態が全部同じものを指すことになります。 Kotlin 版の data class は不変なので、この問題自体が起きません。

    だからテストで確かめます。

    # 元の状態を書き換えていないこと
リスト1再=(一件で「uberto」と「book」の状態内リスト取得)["値"]
「畳み込みは元の状態を書き換えない」と(リスト1再["項目"]の要素数)と0で検証

    不変性は言語ではなく約束が守ります。 約束はテストに書きます。

    動かす¶

    二件=[作成,項目追加]を畳込
リスト2=(二件で「uberto」と「book」の状態内リスト取得)["値"]
「追加すると項目が 1 件」と(リスト2["項目"]の要素数)と1で検証

    初期データも、イベントの並びから作るようにしました。

    ●初期イベント列
    # 第 5 章から、初期データは「起きたこと」の並びで表す。
    # shopping は作っただけのリスト。項目が 0 件でも表示できる。

    作っただけの shopping が表示できます。

    $ curl -s http://localhost:8080/todo/uberto/shopping
<html><body><h1>shopping</h1><ul></ul></body></html>

    「リストを作った」というイベントだけで、画面に出ました。 状態を直接書いた場所はどこにもありません。

    モノイドの発見¶

    変換は合成できる¶

    状態変換作成 が返すのは関数です。関数なら、つなげられます。

    ●(FとGで)変換合成
    # F を適用してから G を適用する変換を作る。
    合成後=関数(状態)
        中間=F(状態)
        G(中間)で戻る
    ここまで
    合成後で戻る
ここまで

    そして「何もしない変換」があります。

    ●恒等変換
    # 合成の単位元。何もしない変換。
    変換=関数(状態)
        状態で戻る
    ここまで
    変換で戻る
ここまで

    この 2 つがあると、畳み込みを別の形で書けます。状態を畳み込むのではなく、変換を畳み込むのです。

    ●(イベント列を)変換畳込
    # イベント列を「1 つの状態変換」に畳み込む。
    # 合成の単位元から始めて、変換を次々と合成していく。
    積=恒等変換

    イベントの並びが、1 つの変換になります。

    構造に気づく¶

    ここまでで、3 つのものが揃いました。

    1. 集まり: 状態変換（状態を受け取って状態を返す関数）
    2. つなげる操作: 変換合成
    3. 何もしないもの: 恒等変換

    そして、次の 2 つが成り立ちそうです。

    • 結合律: どこから括ってもつなげた結果は同じ。(f と g) と h == f と (g と h)
    • 単位元: 何もしないものをつなげても変わらない。恒等 と f == f == f と 恒等

    この 3 点セットを、数学ではモノイドと呼びます。

    名前を先に出しませんでした。順番が逆だからです。構造があって、性質が確かめられて、それから名前が付きます。 名前から始めると、なぜそれが要るのかが分からなくなります。

    身の回りにもあります。文字列の連結（空文字列が単位元）、数の足し算（0 が単位元）、配列の連結（空配列が単位元）。同じ形をしたものに同じ名前を付けておくと、次に会ったときにすぐ分かります。

    性質をどう確かめるか¶

    Kotlin 版は型パラメータで StateTransition を表し、プロパティベーステストで法則を確かめます。

    なでしこ3 には型パラメータがありません。確かめる手段はテストしかありません。 そして例示のテストでは足りません。f・g・h を 1 組だけ試して通っても、法則が成り立つとは言えません。

    乱数で入力を作ります。

    ●(下限から上限までの)乱整数
    # 性質テストの土台。Nの乱数 は 0 以上 N 未満の整数を返す。
    幅=上限-下限+1
    値=幅の乱数
    値+下限で戻る

    状態どうしを比べる手段も要ります。辞書を直接比べられないので、JSON にします。

    ●(値の)比較用文字列
    # 辞書どうしを比べる手段が無いので JSON にして比べる。
    値をJSONエンコードで戻る

    そして結合律を確かめます。

        左=FとGで変換合成
    左合成=左とHで変換合成
    右=GとHで変換合成
    右合成=Fと右で変換合成
    左結果=左合成(状態)
    右結果=右合成(状態)

    適用する状態も乱数で作ります。空状態だけで試すと、法則が成り立って見えることがあるからです。

    # 適用する状態も乱数で作る（空状態だけで試すと、法則が成り立って見えることがある）

      ok 結合律が 200 回とも成り立つ
  ok 単位元が 200 回とも成り立つ

    つまずき 2: 通ったことは確かめたことにならない¶

    ここで止まってはいけません。 200 回通ったのは、法則が成り立つからかもしれないし、テストが何も確かめていないからかもしれません。

    確かめます。合成を非結合的に壊してみます。

      FAIL 結合律が 200 回とも成り立つ: 値が違う 実際=13 期待=0
  FAIL 単位元が 200 回とも成り立つ: 値が違う 実際=8 期待=0

    落ちました。テストは働いています。

    ただし数字を見てください。200 回中 13 件でしか検出していません。 残りの 187 回は、壊れた合成でも同じ結果になりました。ランダムに選んだ変換の多くは、別の利用者や別のリストを触るので、順番を変えても結果が変わらないのです。

    試行回数が少なければ見逃します。 20 回なら 1〜2 件、運が悪ければ 0 件です。性質テストは「回数」と「入力の多様性」の両方が要ります。

    記事に書いたこの回数も、検査の対象にしました。実装が宣言する試行回数と記事の記述がずれたら、CI が落ちます。

    単位元の壊れ方¶

    単位元の側も壊してみます。恒等変換 が状態に余計なキーを足すようにすると、200 回すべてで落ちます（実測 100 件 = 左右 2 通り × 50 回相当）。

    結合律より検出率がずっと高い。単位元は「何もしない」という強い主張なので、少しでも何かすれば必ず見つかります。 法則によって、テストの感度が違います。

    まとめ¶

    • 保存するのは「何が起きたか」です。 起きたことの並びからは今の状態を導けますが、逆はできません
    • イベント 1 件は「状態から状態への関数」になります。 関数なら合成できます
    • 再帰は書けましたが、畳み込みの形では書けませんでした。ループで書き、外から見た振る舞いを畳み込みに保ちました。再帰は畳み込みを表す 1 つの書き方であって、畳み込みそのものではありません
    • 辞書を複製する命令が無いので自分で書きました。不変性は言語ではなく約束が守ります
    • 集まり・つなげる操作・何もしないもの、そして結合律と単位元。この 3 点セットがモノイドです。 名前は最後に付きます
    • 通ったことは確かめたことになりません。 法則を破る実装を入れて、落ちることを見ました。200 回中 13 件でしか検出しないので、回数と入力の多様性の両方が要ります
