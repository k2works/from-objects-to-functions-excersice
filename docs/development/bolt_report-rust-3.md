## 判断と学び

### 1. 承認ゲートが 3 / 3 で同期停止した

Unit 1 が 3 / 3、Unit 2 が 2 / 2、Unit 3 が 3 / 3 で、**累計 8 / 8（100%）**です。3 対象を通した累計は 49 箇所中 9 回になりました。

| ゲート | 添えた数字 | 決定 |
| :--- | :--- | :--- |
| 関数型 DI の形 | 3 案 × 「第 5 章の畳み込みが書けたか」 | **案 A と案 B を使い分ける** |
| 段階をどこで切るか | 3 構成 × 初回・定常の秒数 | **第 4 章で切る。`bin` の名前を分ける** |
| 性質テストの既製品 | 依存 0 / 21 / 38、ビルド 0 / 12.82 / 26.77 秒 | **自作（[ADR-017](../adr/ADR-017-own-property-testing.md) を踏襲）** |

### 2. 第 4 章だけを見ていたら、DI の形を間違えていた

3 案とも、**第 4 章の範囲では通ります。**

落ちたのは第 5 章の畳み込みです。`impl Fn` は書くたびに別の型になり、自前トレイトは合成のたびに型が変わります。どちらも `fold` の途中経過を揃えられません。

[リリース計画](release_plan-rust.md) のリスク台帳が「**それぞれで第 5 章のクロージャ合成まで書けるか**」を条件に指定していたので、スパイクをそこまで進めました。**計画に条件を書いていなければ、第 4 章で決めて第 5 章で書き直しています。**

### 3. 数字を 2 度間違えて、2 度とも実測が直した

**この Unit で一番大きい学びです。**

| # | 間違えた主張 | 実測 | 何が変わったか |
| :--- | :--- | :--- | :--- |
| 1 | 「段階を増やすと初回 24.77 秒で上限 20 秒を超える」 | 依存のキャッシュを揃えると 14.03 秒。**24.77 秒は依存クレートの初回ビルド** | ゲート 2 の推奨が変わった。**人に誤った推奨を出していた** |
| 2 | 「合成の順序を入れ替えると 3/16 見逃す」 | **200 / 200 検出**。`compose(f, g)` は `g(f(x))` なので入れ替えると必ず結果が変わる | 壊し方を変えた。**分布の計算が間違ったまま記事になるところだった** |

どちらも**計算を実測と突き合わせて**気づきました。1 つめは人に訂正を出しています。

### 4. 3 回送った持ち込みを 2 件とも消化した

| 持ち込み | 消化 |
| :--- | :--- |
| **段階を切る手順を ADR に書く** | [ADR-029](../adr/ADR-029-cutting-a-step.md)。切る契機・複製・`[[bin]] name`・記事の落ちの処理まで 7 手順 |
| **カバレッジの下限の見直し** | [ADR-026](../adr/ADR-026-just-and-coverage.md) に追記。`src/bin/` を除いて **80 → 90** |

カバレッジは「揃えた」以外の根拠がありませんでした。測ると、**配線が段階ごとに 22 行の未到達を足す**ので、据え置くと下限が緩くなり続けることが分かりました。

**Unit 2 Try 2（送り先を条件で書く）が効きました。** 「2 つめの段階を切るとき」「ドメインが単独で意味を持つ行数になったとき」と書いていたので、どのステップで消化するかが計画の時点で決まっていました。

### 5. パリティ検査が落ちた。理由は二重管理ではなく検査の手抜きだった

`cov_skip` を足したら `check_rust_ci_parity.py` が落ちました。**落ちたこと自体は正しい**のですが、中身は `cov_min` だけを決め打ちで展開する作りでした。

justfile の変数を一般に読む形に直し、**展開できない変数が残ったら落ちる**ようにしました（持ち込み 6 の消化）。わざとずらして落ちることも再確認しています。

### 6. ADR が 1 つ不要になった

計画では ADR を 3 つ新設する予定でした。カバレッジの見直しは[ADR-026](../adr/ADR-026-just-and-coverage.md) への追記で足りたので、**2 つに減っています**。`just` とカバレッジの関係を決めた ADR がすでにあるためです。

### 7. 制約が設計を押した 3 件目・4 件目

| # | 押された箇所 | 押された先 |
| :--- | :--- | :--- |
| 3 | 合成を型で表すと、実行時に長さが決まる列を畳み込めない | **合成を値で持つ**（`Box<dyn Fn>`）。モノイドの形がそのまま出た |
| 4 | クロージャに借りた値を閉じ込められない（`'static`） | **借りずに所有する**。イベントは保存して後から畳むので形に合う |

なでしこ3 版で 5 回起きた「制約に押されて、押された先が正しかった」と同じです。**制約の出どころが型でも型の不在でも同じ**という仮説は、これで 4 件目です。

### 8. 検出率を測ったのに、何も分からなかった

最初に壊したのは合成そのもので、**200 / 200 検出**でした。数字は良いのですが、**検出率が 1 に張り付く壊し方では数えた意味がありません。**

見逃しのある壊し方（`item7` のときだけ足さない）に変えて **12 / 200** を得ました。期待値 15・σ 3.72 で、実測は 1σ 以内です。

しきい値は期待値から **3σ 下**に置きました。なでしこ3 版は **1.58σ** しか離しておらず、CI が確率 5.7% で落ちていました。

この数字は、**試行回数が 200 であることの意味**も示します。20 回なら期待値 1.5 で、1 度も引かない確率が約 22% です。
