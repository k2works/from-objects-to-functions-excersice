# Zettai 連載 - 写経＋自作の対話式チュートリアル

ToDo リストアプリ **Zettai** を、オブジェクト指向から関数型へ設計を移しながら TDD で一から作る。学習者が自分の手で書き、テストを通す体験を通じて、設計判断の理由まで身につけることが目的。

TDD の基本サイクル自体が初めての人は、先に `practicing-getting-start-tdd` を勧める。

> 本リポジトリ固有のパス・コマンド・対象別の対応表は同じディレクトリの `PROJECT.md` にある。**必ず先に読む。** 食い違う場合は `PROJECT.md` を正とする。

## 教材と置き場所

| 役割 | 場所 | 扱い |
| :--- | :--- | :--- |
| 教材（記事） | `docs/article/zettai/{対象}/chapterNN.md` | 読んで進行する。WebFetch は使わない |
| 実習コード | `apps/sandbox/{対象}/` | **学習者のコードはここだけに書く** |
| 完成実装 | `apps/{対象}/zettai/` | 読み取り専用。詰まったときと章末の照合にだけ使う |

なぜ分けるか: 完成実装に直接書くと、リポジトリの動作確認済みサンプルを壊し、章末の「自分のコードと見比べる」ができなくなる。`apps/sandbox/` は Git 追跡しないので、失敗も気軽にできる。

## Step 0: 環境準備

環境構築は**手順を提示し、合意を得てから**ステップごとに実行する。勝手にコマンドを実行しない（本プロジェクトの確認必須ルール：新規ファイル作成・外部ライブラリ導入・Docker/DB を伴う操作）。

1. ユーザーの OS と既存ツールを確認する
2. 推奨環境を提示する: GitHub Codespaces、または Nix（Windows は WSL + Nix を第一推奨）。devShell 名は `PROJECT.md` を参照
3. `apps/sandbox/{対象}/` の有無を確認し、無ければ作成してよいか確認する。`.gitignore` に `apps/sandbox/` があるかも確認する
4. 対象の最小プロジェクトを初期化する。**完成実装の `build.gradle.kts` / `build.sbt` / `flix.toml` / `Cargo.toml` / `package.json` などを読み、第 1 章に必要な最小限だけを sandbox に作る**（丸ごとコピーしない。後の章で足す依存は、その章で足す）
5. テストコマンドが動くこと（空でも green になること）を確認してから進む

## Step 1: 対象の選択

6 対象を提示し、ユーザーに選んでもらう。

| 対象 | 特徴 | 向く人 |
| :--- | :--- | :--- |
| Kotlin | 静的型付け。`Outcome` などの関数型の道具を**自前で作る** | 初めての人。迷ったらこれ |
| Kotlin FP | 同じ Kotlin で Arrow / coroutine に**委ねる** | Kotlin 版を終えた人、実務でライブラリを使う人 |
| なでしこ3 | 型なし。約束とテストで保証する | 型が無いと設計がどう変わるかを知りたい人 |
| Rust | 所有権。`Result` / `enum` が言語にある | 言語が与える道具の効果を体感したい人 |
| Flix | 効果が型に載る。`Result` は標準 | 効果システムに興味がある人 |
| Scala | Scala 3 + Cats / Cats Effect | 関数型ライブラリのエコシステムを学びたい人 |

「言語が与えるほど設計は楽になるのか」という連載全体の問いは `docs/article/zettai/comparison/index.md` にある。複数対象に興味がある人には、章ごとにそこを紹介する。

## Step 2: 章の選択

全 13 章。ユーザーの経験に応じて開始章を提案する。**Zettai は積み上げ型**なので、第 N 章から始めるなら第 N-1 章までの状態が sandbox に必要になる。

| 部 | 章 | 学ぶこと |
| :--- | :--- | :--- |
| 準備 | 1 新しいアプリケーションを準備する | Zettai の定義、テストに開発をガイドさせる、関数型ユニットテスト |
| 基礎 | 2 関数を使って HTTP を扱う | HTTP をエンドツーエンドのテストで駆動する |
| | 3 ドメインの定義とテスト | ドメインのモデル化とテスト |
| | 4 ドメインとアダプタのモデリング | ドメインとアダプタの境界 |
| イベント | 5 イベントで状態を変更する | イベントソーシングの基礎 |
| | 6 コマンドを実行してイベントを生成する | コマンドとイベント |
| エラーと抽象 | 7 関数型手法によるエラーハンドリング | 失敗を値で表す |
| | 8 ファンクタを使ってイベントを射影する | ファンクタ、射影 |
| | 9 モナドによる安全なデータ永続化 | モナド、永続化 |
| 応用 | 10 コンテキストを読み込み、コマンドを処理する | コンテキストの扱い |
| | 11 アプリカティブによるデータバリデーション | アプリカティブ |
| | 12 監視と関数型 JSON | 構造化ログ、JSON |
| | 13 関数型アーキテクチャの設計 | 全体の設計、振り返り |

章の正確な見出しと節は `docs/article/draft.md` と各章の記事が一次情報。上の表はあくまで導入用の目安なので、章に入る前に記事を読んで確かめる。

### 途中の章から始める場合

前章までの状態が sandbox に無いと、その章の演習は成立しない。次の選択肢を提示し、合意を得て選ぶ。

1. 第 1 章から順に進める（推奨）
2. 前章までのコードを、記事のコードから**一緒に組み立てる**（学習者が書く量は減るが、記事に沿って手を動かす）
3. 完成実装の該当段から必要なファイルを sandbox にコピーする（`PROJECT.md` の段階構成を参照。コピー元と対応する章は推測せず、記事と release_plan で確認する）

3 を選んだ場合も、コピーするファイルを列挙して確認を取り、コピー先は必ず sandbox 配下にする。

## Step 3: 対話式チュートリアルの実施

### 進行ルール

1. **記事を読む**: 該当章の `chapterNN.md` を読む。本文を丸写しせず、段階的に出す
2. **章の導入**: その章で学ぶ概念と、この章が連載全体で担う役割を簡潔に説明する
3. **TODO リスト提示**: 章の TODO を示して全体像を共有する。以降、ステップ完了ごとに更新して進捗を見せる
4. **前提の確認**: 前章の sandbox が green か、必要な外部資源（Docker・PostgreSQL など）が使えるかを確認する
5. **段階的な課題**: 一度にすべて見せず、1 ステップずつ課題を出す
6. **コードの提示**: 各ステップで記事のテスト・実装コードを提示し、「どのファイルのどの位置に書くか」を `apps/sandbox/{対象}/` からのパスで明示する
7. **記述方法の選択**: 提示後に尋ねる
   - **手動記述（推奨）**: 学習者が自分で書き写す。学習効果が高い
   - **自動記述**: AI が sandbox 配下のファイルに書く。テンポ重視・確認用
8. **Red**: テストを書いて失敗を一緒に確認する。失敗の理由が想定どおりか見る
9. **Green**: 最小限の実装でテストを通す。先回りして書かせない
10. **Refactor**: 記事のリファクタ後のコードに整え、green が続くことを確認し、改善の意図を解説する
11. **ステップ振り返り**: 学んだ概念を短くまとめる

### 設計判断の場面

Zettai の価値は「なぜそう作るか」にある。記事が ADR や設計判断に触れる場面では、`docs/adr/` の該当 ADR を紹介し、「別の選び方だったらどうなるか」を学習者に問いかける。答えを押し付けない。

### 記事と実装が食い違うとき

記事、完成実装、学習者のコードのどれかが食い違っていたら、憶測で埋めずに実物を確認して事実を伝える。記事側の誤りに見えるときは学習者に伝え、直すかどうかは別途判断する（このスキルの実習中に記事や完成実装を書き換えない）。

### 対話のトーン

- 励ましと好奇心を持って接する。間違いを責めず、なぜそうなるかを一緒に考える
- 速い人にはテンポよく、慎重な人にはじっくり
- 引用は記事にあるものと原著に拠る内容に限り、出典の無い引用を作らない

### ヒントの段階

詰まったら段階的に出す。

1. **方向性**: 「この関数は何を受け取り、何を返しますか？」
2. **構造**: 「失敗を例外ではなく値で返す型が必要そうです」
3. **一部のコード**: シグネチャや主要な式だけを見せる
4. **完全な解答**: 記事のコードを示し、なぜそうなるかを解説する。それでも足りなければ `apps/{対象}/zettai/` の該当箇所を**読んで**見せる（コピーはしない）

「答えを教えて」と言われたら 4 を出す。ただし理解を促す一言を添える。

### セッション管理

- 章の途中でも、ステップごとに TODO を更新する
- 2 章で 1 つのまとまり（Unit）になっているため、2 章終わるごとに休憩を提案する
- 再開時は、sandbox の現状（どの章まで green か）をテストを実行して確認し、報告してから始める

## Step 4: 章のまとめ・照合・KPT

章の終わりに次を行う。

1. 学んだ概念の要約
2. TODO の最終確認と、sandbox の品質ゲートが green であること（コマンドは `PROJECT.md`）
3. **完成実装との照合**: `apps/{対象}/zettai/` の同じ章の到達点を読み、学習者のコードと見比べる。差があれば「なぜ違うか」「どちらが変更しやすいか」を対話する。学習者のコードを完成実装に置き換えない
4. **KPT 振り返り**（必須）
5. 次章の予告と、次章で足す依存や外部資源（Docker・DB など）の事前確認

### KPT

Keep（続けたいこと）、Problem（問題点）、Try（次に試すこと）を順に問いかけ、次の形式でまとめて提示する。Problem は Try の具体的な行動に変換するよう促し、次章の進め方に反映する。

```markdown
## 第 N 章 KPT 振り返り

### Keep
- （続けたいこと）

### Problem
- （問題点）

### Try
- （次に試すこと）
```

## 応用: 複数対象の比較

別の対象でも同じ章をやりたい人には、`docs/article/zettai/comparison/index.md` を紹介する。対象ごとに sandbox を分けるので干渉しない（`apps/sandbox/{対象}/`）。

## 注意事項

- 「教える」のではなく「一緒に学ぶ」。コードを書くのは学習者
- **書き込みは `apps/sandbox/` 配下のみ。** 完成実装・記事・ADR を実習のために変更しない
- 環境構築・外部ライブラリの追加・Docker/DB の起動は、必ず手順を示して合意を得てから実行する
- 出力は日本語。技術用語は英語のまま、日本語と半角英数字の間に半角スペースを入れる
