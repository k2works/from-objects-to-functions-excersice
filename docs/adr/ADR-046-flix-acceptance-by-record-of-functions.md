# ADR-046 Flix 版は受け入れテストの経路を関数値のレコードで差し替え、Cucumber を入れない

日付: 2026-11-02

## ステータス

2026-11-02 提案されました

## コンテキスト

第 3 章で受け入れテストを抽象化します。同じシナリオを複数の経路で走らせ、片方だけ落ちたらそこに業務のロジックが漏れている、と判断する形です（[ADR-028](ADR-028-own-acceptance-trait.md)）。

既存の対象の手段は次のとおりです。

| 対象 | 手段 |
| :--- | :--- |
| Kotlin | Pesticide の `DdtActions` |
| Kotlin FP | Gherkin と Cucumber |
| なでしこ3 | 関数値を詰めた辞書 |
| Rust | トレイト。cucumber は依存 127 クレート・ビルド +92 秒で採らなかった |

Flix 版の執筆計画（[outline.md](../article/outline.md)）では、Cucumber を使えるかを確認する事実の 1 つに挙げていました。

### 確かめたこと、確かめていないこと

| 項目 | 状態 |
| :--- | :--- |
| テストの実行方法 | **確認済み。** `flix test` が唯一の実行方法で、`@Test` を付けた関数を実行する |
| Flix から匿名クラスで Java のインターフェースを実装できること | **確認済み。** 第 2 章で `HttpHandler` を実装した |
| Cucumber の step definitions は Java のアノテーション付きメソッドであること | 公式の仕様として知られている |
| Flix でアノテーションを付けたクラスを定義できること | **確認できていない。** Flix の公式ドキュメントの相互運用の章に記述が見つからなかった |
| Cucumber を Flix から実際に動かしてみること | **試していない** |

つまり、**Cucumber が使えないと確かめたわけではありません。** 試さずに採らない、という判断です。

## 決定

**関数値のレコード `ZettaiActions` で経路を差し替えます。Cucumber を入れません。**

1. シナリオが使う操作を、関数値のレコードに並べる
2. 経路ごとにレコードを作る（`domainActions` / `httpActions`）
3. シナリオは `ZettaiActions` を受け取り、どの経路か知らない
4. レコードの `name` を失敗メッセージに含め、どの経路で落ちたかが分かるようにする

### 採った理由

- **必要なのは経路の差し替えで、Gherkin ではない。** シナリオは第 2 章の時点で、業務の言葉だけの関数として書ける
- **Flix の標準の道具で足りる。** 追加の依存も、ビルドへの変更も要らない
- **試すコストが高く、得るものが小さい。** Cucumber を動かすには、Java のアノテーションを Flix で付けられるかという未確認の問題を先に解く必要がある。得られるのは `.feature` ファイルによる一覧性だけ

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| Cucumber を Java の補助クラス経由で動かす | Java のソースをこのリポジトリに足すことになり、「Flix 版」の範囲を超える。`flix test` と別のランナーが並ぶ |
| 効果多相の `ZettaiActions[ef]` | 経路ごとに効果が違うため、`List` に入れて 1 つのテストで回せない |
| 経路ごとにテスト関数を複製する | シナリオが増えるたびに経路の数だけ複製することになる |

## 影響

- 依存もビルド時間も増えない
- シナリオは経路を知らない。経路を足すとき、シナリオは変わらない
- 実際に HTTP 経路だけを壊すと、失敗メッセージに `(http, None)` と経路名が出る（第 3 章）
- ドメイン経路の純粋な関数を `IO` の枠に入れるため、テスト側に `inIO` という補助関数を 1 つ置く。第 2 章で確認したとおり、Flix は純粋な関数を `IO` を期待する場所に渡すことを許さない

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| 非エンジニアがシナリオを読み書きすること | Gherkin を入れればできるが、この連載の読者は開発者。必要になったら入れ直す |
| シナリオの一覧性 | `.feature` のような一覧はない。テスト関数の名前が代わりになる |
| Cucumber が使えるかどうかの確認 | 未確認のまま残る。使えると分かった場合も、この決定は覆さないが、記事の記述は直す |
| 経路が増えたときの組み合わせ | 第 9 章で永続化の経路が入る見込み。そのときに重みを測る |

## コンプライアンス

- シナリオが具体的な経路（`domainActions` / `httpActions`）を名指ししないこと
- 経路を足したとき、シナリオのコードが変わらないこと
- 失敗メッセージに経路の名前が入ること
