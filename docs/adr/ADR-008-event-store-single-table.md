# ADR-008 イベントストアを 1 テーブルで持ち状態を保存しない

日付: 2026-09-27

## ステータス

2026-09-27 提案されました

## コンテキスト

第 5 章で、状態を上書きせず出来事として残す設計にしました。第 9 章で永続化を入れる際、何を保存するかを決める必要があります。

| 案 | 内容 |
| :--- | :--- |
| A. 状態を保存する | `todo_list` と `todo_item` のテーブルを作り、UPDATE で更新する |
| B. 出来事を保存する | 出来事のテーブルだけを作り、追記のみ。状態は読み出して畳み込む |
| C. 両方保存する | 出来事を追記し、状態も別テーブルに持つ（リードモデル） |

## 決定

**案 B を採ります。テーブルは 1 つだけで、状態を保存しません。**

```sql
CREATE TABLE IF NOT EXISTS todo_list_event (
    id          BIGSERIAL PRIMARY KEY,
    entity_id   TEXT        NOT NULL,
    event_type  TEXT        NOT NULL,
    payload     JSONB       NOT NULL,
    recorded_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_todo_list_event_entity
    ON todo_list_event (entity_id, id);
```

詳細は [データモデル設計](../design/data-model.md) を参照。

### 個別の判断

**`id` を `BIGSERIAL` にし、順序の根拠にしました。** `recorded_at` は順序の根拠にしません。同じ時刻に複数の出来事が記録されうるためです。

**`payload` を `JSONB` にしました。** 出来事の種類ごとにカラムを用意すると、出来事を追加するたびにスキーマ変更が必要になります。`JSONB` なら追加はアプリケーション側で済みます。

**`entity_id` を `{user}/{listName}` の複合文字列にしました。** 読み出しは常に両方で絞るため、分ける利益がありません。`user` だけで絞る必要が出たら、そのときカラムを分けます。

**インデックスは `(entity_id, id)` の 1 つだけです。** 読み出しのパターンが「ある対象の出来事を追記順に全部」の 1 つしかありません。

**ORM（Exposed）を使いません。** テーブルが 1 つ、操作が追記と読み出しの 2 つだけで、ORM が解決する問題（関連の読み込み、変更の追跡、N+1）が起きません。加えて第 9 章の主題は「データベースアクセスをモナドで組み立てる」ことなので、既製の ORM を使うと「Exposed の使い方」の説明になります。生の JDBC + PostgreSQL ドライバのみを使います。

**原著は Exposed を使っています。** 差分として記事に注記します（[ADR-001](ADR-001-kotlin-toolchain.md) の決定 5）。

### 正規化を論じない理由

イベントストアは追記のみで、UPDATE も DELETE もしません。**正規化が解決する問題（更新時の不整合、重複データの矛盾）が起きません。**

正規化を考えるのは、射影を永続化するようになったとき（案 C）です。現在は射影をメモリ上で作り直しているので、その必要がありません。

## 影響

- **状態を読むたびに全出来事を畳み込みます。** 出来事が増えると遅くなります。連載の規模では問題になりませんが、実務では案 C（リードモデルの永続化）かスナップショットが必要になります。この限界を第 9 章の記事に書きます
- **削除ができません。** 誤って作ったリストも出来事として残ります。取り消しは「取り消した」という出来事を足して表します（第 9 章では未実装）
- **スキーマ変更が起きにくいので、マイグレーションツールを入れていません。** 起動時に `CREATE TABLE IF NOT EXISTS` を実行します
- JSON のシリアライズを手書きしています。第 12 章で Kondor に置き換えます

### 実際に踏んだこと

**PostgreSQL の `JSONB` は保存時に JSON を正規化します。** 書き込んだ文字列とそのまま同じものは返ってきません（コロンの後に空白が入る）。自作の JSON パーサが読めず、結合テストが落ちました。空白を許すように直しました。

`JSONB` を選ぶなら、**保存した文字列がそのまま返る前提を置けない**ことを知っておく必要があります。文字列として厳密に往復させたいなら `TEXT` にします。

## 再検討の条件

次のいずれかに当たったら、ORM（Exposed・JPA など）の導入を検討します。

1. 出来事以外の表が増え、表ごとに同じ形の読み書きを書き写すようになった
2. 射影の読み出しが複数の表をまたぐようになり、結合の組み立てが手書きでは追えなくなった
3. スキーマの変更が複数箇所の SQL に波及し、変更のたびに漏れが出るようになった

**再検討は「表が 3 つを超えたとき」を目安にします。** 表が 1 つのうちは ORM が解く問題そのものが起きません。

## コンプライアンス

- テーブルが `todo_list_event` の 1 つだけであること
- UPDATE と DELETE を発行しないこと（`TRUNCATE` はテスト用のみ）
- 読み出しが `ORDER BY id` であること
- 結合テストで追記と読み出しの往復が green であること
