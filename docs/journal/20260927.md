# 2026-09-27 Unit 3 — ゲートを外せる条件と、名前を最後に出すこと

Unit 3（第 4〜5 章）を完了させた。序盤から中盤へ、アプローチをアウトサイドインからインサイドアウトに切り替えた最初の Unit だった。

## ゲートを 11 から 5 に減らして、変更依頼が 0 件だった

Unit 2 の終了報告で「Unit 3 は自律実行に寄せる」と決めた。承認ゲートを 11 箇所から 5 箇所に減らした。

結果は**変更依頼 0 件、回帰 0 件**。Unit 1・2 ではそれぞれ 1 件の変更依頼が出ていたので、減らしても品質は落ちなかった。

### なぜ落ちなかったのか

最初は「慣れてきたから」だと思った。違う。

Unit 1・2 で出た変更依頼は、**どちらも同じ領域**だった。「記事のコード例が実装に存在しない」だ。そしてその領域を、Unit 2 で CI の検査に移した。

つまり、**人が見ていた判断を機械に移したから、人のゲートを外せた**。慣れとは関係ない。

これは一般化できる。**機械に移せていない判断のゲートは外せない。** 実際、記事の構成と全文検証は疎にしても止め続けた。CI の検査は「実装に存在するか」しか見ておらず、「読者に伝わるか」は見ていない。

ゲートを減らしたいなら、減らしたいゲートで何を判断しているかを特定して、それを機械に移すのが先だ。順序を逆にすると、同じ問題が再発する。

## スパイクを置かなかった

Unit 1・2 では Bolt の先頭にスパイクを置いた。未解決の仮定が HIGH だったからだ。どちらも当たった（Unit 1 は Kotlin のバージョン差、Unit 2 は Pesticide が動くか）。

Unit 3 は未解決の仮定を LOW と評価して、**スパイクを置かなかった**。使う道具はすべて Unit 2 で検証済みだったからだ。問題は起きなかった。

**スパイクは毎回やる儀式ではなく、未解決の仮定があるときの対処だ。** 前の Unit で効いたからといって、次も置く理由にはならない。

## プロパティベーステストのライブラリを入れなかった

第 5 章でモノイド則を確かめる必要が出た。「例をいくつか挙げても法則は示せない」ので、ランダムな入力を多数試すプロパティベーステストが要る。

kotest-property を検討して、見送った。

決め手は「**ドメイン固有の生成器はどちらにせよ自前で書く**」ことだった。kotest を入れても `List<ToDoListEvent>` の生成器は `Arb.bind` を組み合わせて自作することになり、書く量はあまり減らない。加えて `checkAll` は suspend 関数なので `runBlocking` が要り、記事で「なぜこれがあるのか」を説明する必要が出る。モノイドの説明から読者の注意が逸れる。

結果、`repeat` + シード固定の 20 行で済んだ。失うのはシュリンキング（失敗する最小の入力を探す機能）だが、入力が小さいので実用上の差は小さい。

ADR-004（静的解析を入れない）と同じ判断の形になった。**このプロジェクトで実際に効くかどうかで決める。** 「一般にあったほうがいい」では決めない。再検討の条件を ADR に書いたので、必要になったら入れられる。

## 4 章前の伏線が回収された

第 1 章で、ボウリングの得点計算を関数型で書いた。ループではなく再帰で、「終わりの条件」と「1 つ処理して残りを続ける」の形にした。あのときの目的は「テストを純粋関数にする」ことの説明だった。

第 5 章で、イベントの畳み込みが**まったく同じ形**になった。

```text
第 1 章: remainingFrames == 0 -> 0 / rolls.frameScore(...) + rolls.nextFrames(...)
第 5 章: isEmpty() -> from      / drop(1).replayByRecursion(from.apply(first()))
```

記事でこの対応を示せたので、読者は「あのとき練習した形だ」と気づける。そのうえで `fold` に置き換えると、`fold` が何をしているかが分かる。

第 1 章の時点でこれを意図していたわけではない。結果としてそうなった。ただ、**教材の題材は後の章で回収されるように選ぶ**という観点は、今後の章でも意識したい。

## 抽象概念の名前を最後に出した

モノイドの説明で、名前を最後に回した。

「モノイドとは結合律と単位元を持つ代数構造である」から始めると、定義は正しいが、なぜ嬉しいのか分からない。読者は言葉を覚えるだけになる。

順序をこうした。

1. 出来事を「状態の変換」として見る
2. 変換は合成できる。合成しても変換であり続ける
3. 何もしない変換がある
4. 繋ぐ順序をどう括っても結果が同じ（名前を出さない）
5. 何もしない変換を繋いでも変わらない（名前を出さない）
6. 例では足りないので、ランダム 200 回で確かめる
7. **この構造をモノイドと呼ぶ**
8. 整数の足し算、文字列の連結も同じ構造だと気づく

8 番が効く。**知っていたことに名前が付いた**という感覚になる。新しい概念を覚えるのではなく、既に知っていたものが整理される。

第 7 章のファンクタ、第 9 章のモナドでも同じ順序を使う。

## 局面移行は思ったより静かだった

アウトサイドインからインサイドアウトへの切り替えを、大きな変化だと思っていた。実際はそうでもなかった。

変わったのは**テストをどこから書き始めるか**だけだ。Red-Green-Refactor の回し方も、コミットの分け方も、記事の書き方も変えていない。開発戦略に「変わるのはテストの入口とレイヤー貫通の順序のみ」と書いたが、そのとおりだった。

既存の受け入れテストは毎回実行し、回帰 0 件だった。ドメインを大きく作り替えた（Map の直接操作からイベントの畳み込みへ）のに、外から見た振る舞いは変わっていない。**第 3 章で作った受け入れテストの入口が効いている。**

## 次回に活かすこと

- **Unit 4 も疎のまま。** ただし第 7 章で `Outcome` を導入すると `null` を一斉に置き換えることになる。影響範囲が広いので、置き換えの方針を決めるステップは止める
- **Unit 5（第 9 章）では密に戻す。** PostgreSQL の導入で検証の不確実性とリスクが上がる。ゲートを減らしたまま突っ込まない
- **ポートの型が変わる影響を見積もる。** 第 7 章で `ToDoListFetcher` の戻り値が `ToDoList?` から `Outcome<...>` になる。これまで「ポートの型が変わらなければ上のコードは変わらない」と書いてきたが、今回は型そのものが変わる。第 2 章から積み上げた「矢印で依存を表す」設計が、本当に変更を楽にしているかが試される
