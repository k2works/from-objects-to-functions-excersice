# ADR-060 TypeScript FP 版は業務上ありうる失敗だけを型で運び、想定外の失敗は defect にする

日付: 2026-11-28

## ステータス

2026-11-28 推奨の案 A を採用しました（Unit 4 のゲート ④）。**同期停止していません。** 利用者の事前の指示「執筆完了まで、判断はすべて推奨を採用する」によるもので、この判断を人が個別に確認してはいません

## コンテキスト

第 7 章で、失敗を型で運びます。`Effect<A, E, R>` には、型に現れる失敗（`E`）と、型に現れない失敗（defect）があります。どの失敗をどちらにするかを決めます。

### 先に確かめたこと

同じ処理（コマンドの受け付け、拒否、保存の失敗、アダプタの誤り）を 3 通りに書きました（2026-11-28、TypeScript 7.0.2、Effect 4.1.6）。比較のコードは、実行の後に削除しました。

| 項目 | A: 業務の失敗だけを `E` に | B: 想定外も包んで `E` に | C: 業務の失敗も defect に |
| :--- | :--- | :--- | :--- |
| `execute` の型の `E` | `ZettaiError` | `Unexpected \| ZettaiError` | `never` |
| 保存の失敗、アダプタの誤り | defect | 型付きの失敗（500） | defect |
| `execute` にすべてを捕まえる `Effect.catch` を掛けると | 拒否だけを捕まえる | **保存の失敗と実装の誤りも捕まえる** | 何も捕まえない |
| `ZettaiError` に種類を足すと | HTTP の対応で `TS2366` | HTTP の対応で `TS2366` | **型検査が通る** |
| 行数（空行とコメントを除く） | 27 | 35 | 33 |

- この比較の「行数」は、比較用の小さな実装のものです
- B は、`Effect.catchDefect` で defect を型付きの失敗に包みました
- C は、受け取った値が業務の失敗かを、実行時に調べました。調べ方は `_tag` の有無だけで、確実ではありません

## 決定

1. **業務の上で起こりうる失敗（`ZettaiError`）は、型で運ぶ。** 純粋な核では `Result`、実行を表す境界では `Effect` の `E` にする
2. **想定外の失敗（保管の故障、実装の誤り）は defect にする。** ハブもアプリケーションも捕まえず、最外周の `node:http` への接続が、理由を出さずに 500 にする
3. **業務の失敗の対応には、defect を捕まえない操作を使う。** web で `catchDefect` や `catchCause` を使わない
4. 失敗の応答の本文は、状態ごとの固定の文字列にする

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| B | すべてを捕まえる 1 行で、実装の誤りが業務の失敗と同じ扱いになる。型の `E` を見ても、呼び出し側が対応すべき失敗と、そうでない失敗を区別しにくい |
| C | 型から、起こりうる失敗が読めない。失敗の種類を足しても、型検査が通る |

## 影響

### ポジティブ

- `E` に現れるものは、呼び出し側が対応する失敗だけになる
- 業務の失敗の種類を足すと、対応の漏れを型検査が止める

### ネガティブ

- 保管の故障は、型に現れない。呼び出し側は、型からは備えを求められない
- defect の記録は、まだ無い。500 の原因を後から追えない。ログは第 12 章で扱う
- **見込み（確かめていない）:** 第 9 章でデータベースの失敗を扱うとき、再試行などで型に乗せたい失敗が出るかもしれない。その時点で、この決定を確かめ直す

## コンプライアンス

- 業務の失敗が 500 にならず、defect の応答に理由が出ないことを確かめるテストがある
- 失敗の応答の本文に、利用者やリストの名前が出ないことを確かめるテストがある
- web が `catchDefect`・`catchCause` を使わないことは、テストで固定していない。レビューで確かめる
