## 設計

### 本 Unit のスコープでの設計図

**4 図とも掲載しません。** 理由を明記します。

| 図 | 掲載しない理由 |
| :--- | :--- |
| ドメインモデル図 | 本 Unit ではドメインを作らない。第 2 章（Unit 2）で最初の型が出る |
| 状態遷移図 | ToDo 項目の状態は第 4 章（Unit 3）から。既存の [ドメインモデル設計](../design/domain-model.md) にある |
| ER 図 | 永続化は第 9 章（Unit 5）から。既存の [データモデル設計](../design/data-model.md) にある |
| 画面遷移図 | 画面は第 2 章から。既存の [UI 設計](../design/ui_design.md) にある |

**本 Unit で決めるのは設計ではなく、設計を書く前提（async・HTTP クレート・検査）です。**

### 依存の構造（決めること）

```text
apps/rust/zettai/
├── Cargo.toml          workspace
├── Makefile            just check
├── README.md           既知の制約の一覧（器を先に作る）
└── zettai-step1-http/  最初のメンバー
    ├── Cargo.toml
    ├── src/
    └── tests/
```

**cargo workspace のメンバーが、Kotlin 版のモジュール・なでしこ3 版の `stepN/` に対応します。** メンバーを増やす手順は、2 つめを切るとき（Unit 2）に ADR へ書きます（なでしこ3 版 Unit 7 Try 2）。

**境界はクレートの分割そのものが守ります。** `Cargo.toml` の `dependencies` に無ければ、使おうとした時点でコンパイルが通りません。2 対象のような境界検査を書く必要がありません。**これは第 3 章（Unit 2）で扱います。**

**本 Unit では作りません。** 本連載の成果物は記事であり、利用者向けマニュアルを持ちません（2 対象と同じ）。画面もありません。

## リスクと対策

| リスク | 影響 | 対策 | 検知 |
| :--- | :--- | :--- | :--- |
| **同期クレートで第 9 章まで行けず、async が第 2 章から必要になる** | 高 | スパイク 2 で先に確かめる。**必要なら第 2 章の主題に「async をいつ入れるか」を加える**（隠さない） | 1-1.2 |
| **HTTP クレートの選定を誤り、第 2 章で書き直す** | 中 | 候補 3 つで同じハンドラを書いてから決める。**書いた 3 つは捨てずにスパイクの記録として残す** | 1-1.3 |
| `clippy -- -D warnings` が厳しすぎて進まない | 中 | 止まった箇所を制約の一覧に記録する。**それでも `-D warnings` は外さない**（外すなら ADR に理由を書く） | 1-1.5 |
| ゲートがまた止まらない | **高** | 選択肢と数字を必ず添える。**3 箇所中 2 箇所を下回ったら Unit 2 で箇所を減らす**（増やさない） | 1-2.6 |
| 第 1 章が 2 対象の焼き直しになる | 中 | 受入条件 4 で「2 対象に無い内容を 1 つ以上」を要求する。無ければ未完了 | 1-2.3 |
| Nix の devShell に `cargo-llvm-cov` が無い | 低 | 入れない判断を ADR に記録する（Kotlin 版 ADR-004 と同じ形） | 1-1.4 |
