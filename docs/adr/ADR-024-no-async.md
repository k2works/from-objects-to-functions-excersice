# ADR-024 async を採らず、同期のクレートで 13 章を通す

日付: 2026-09-28

## ステータス

2026-09-28 提案されました

## コンテキスト

Rust で HTTP と DB を扱うとき、async を採るかどうかは**最初に決めなければならない**判断です。

**async は伝播します。** `async fn` を呼べるのは `async fn` の中だけなので、第 9 章で async な DB クレートを選ぶと、そこから上のすべて（第 1〜8 章のコード）が `async fn` に書き換わります。依存 DAG には現れませんが、**第 2 章の時点で決まっていなければならない依存**です。

2 対象（Kotlin 版・なでしこ3 版）にはこの判断がありませんでした。Kotlin 版は http4k と JDBC が同期、なでしこ3 版はそもそも選択肢がありません。

### 実測したこと

Unit 1 のスパイクで、**同期のクレートだけで第 9〜10 章の題材が書けるか**を確かめました。

| 確かめたこと | 結果 |
| :--- | :--- |
| 同期の `postgres` 0.19.14 で `INSERT` / `SELECT` | **書けた**（実 DB に対して実行） |
| 同じクレートでトランザクション（`client.transaction()` と `rollback()`） | **書けた**（ロールバック後の件数を確認） |
| 同期の HTTP クレートで縦串 | **書けた**（3 候補とも実際に応答） |

**第 9 章（永続化）と第 10 章（トランザクションの境界）が、同期のまま成立します。**

## 決定

**async を採りません。同期のクレートだけで第 1〜13 章を書きます。**

1. HTTP は同期のクレートを使う（[ADR-025](ADR-025-tiny-http.md)）
2. 永続化は同期の `postgres` クレートを使う（第 9 章）
3. トランザクションは `client.transaction()` を使う（第 10 章）
4. **tokio を依存に入れない**

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| 第 2 章から async で書く（axum + tokio） | Rust の実務には近いが、**第 4 章（関数型 DI）・第 5 章（クロージャ合成）・第 10 章（境界）の主題に async の説明が混ざる**。連載の主題は設計であって async ではない。また関数の形が 2 対象と変わり、横断比較が読みにくくなる |
| 第 8 章まで同期で書き、第 9 章で async に切り替える | 切り替えそのものを第 9 章の主題にできるが、**第 1〜8 章のコードと記事のコード例を書き換える**ことになる。`check_article_code.py` が落ち、公開済みの章に手が入る |
| 同期で書き、最終章で「async ならこうなる」を補足する | 検討に値する。**第 13 章の対比の材料として扱う**（この ADR では決めない） |

## 影響

- **第 1〜8 章の書き換えリスクが 0 になります。** 後戻りの効かない判断を Unit 1 で潰しました
- **関数の形が 2 対象と揃います。** `fn f(x: X) -> Y` のまま比較できます
- ビルドが速くなります（tokio と依存群が入らない）。`just check` は 2〜3 秒です
- **Rust の実務で多い async の絵を見せられません。** これは失うものです

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| **同時実行性** | 同期のサーバは接続ごとにスレッドを使います。同時接続数がスレッド数に縛られます。**教材なので問題にしませんが、本番では効きます** |
| **async 版の設計** | 「async だとこの設計はどう変わるか」は書きません。第 13 章で触れるかを Unit 7 で判断します |
| **将来の切り替え** | 後から async にするなら、第 1〜13 章のコードを書き換えることになります。**この決定は連載の期間中は覆しません** |

## コンプライアンス

- `Cargo.toml` に `tokio` が現れないこと
- `async fn` / `.await` を書かないこと
