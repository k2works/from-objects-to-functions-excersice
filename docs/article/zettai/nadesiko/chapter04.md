# 第 4 章 ドメインとアダプタのモデリング

## ToDoリストを変更するための新しいストーリーを始める

第 3 章までで、ToDo リストを表示できるようになりました。次に欲しいのは**変更**です。項目を追加したい。終わったことにしたい。

しかしその前に、片付けておくことがあります。

```nako3
●保管庫作成
    本=「write chapter」でToDo項目作成
```

**データの取得元が、HTTP アダプタの中に埋まっています。** `Zettai処理` は `保管庫作成` を呼び、保管庫は毎回同じ 3 件を返します。テストから別のデータを渡すことができません。

第 9 章では、この取得元がデータベースに変わります。そのとき `Zettai処理` を書き換えることになったら、設計が間違っています。**取得元が変わっても、その上のコードは変わらないはずです。**

この章では 2 つのことをします。

1. データの取得元を、外から差し替えられるようにする
2. `ToDo項目` に期限と状態を足す

### 局面が変わる

ここから進め方が変わります。第 2〜3 章は**外側のテストから内へ**向かいました（アウトサイドイン）。第 4 章からは**内側から作ります**（インサイドアウト）。

理由は、ここから扱うものがドメインの中で完結するからです。イベント、状態変換、モノイド。外側から入ると、HTTP のハンドラに業務ロジックが漏れます。

型の無い言語では、この必要性がさらに高くなります。**外から入ると「この辞書がどんなキーを持つか」が誰にも分からないまま、HTTP の層まで伝わってしまう**からです。先に辞書の契約を決め、契約テストで固定してから上へ展開します。

## 関数型の「依存性の注入」を使う

### ハブを置く

ドメインの入口を 1 つ作ります。名前は**ハブ**です。HTTP の層は、このハブしか知りません。

```nako3
●(取得Fで)ハブ作成
    # ドメインの入口。アダプタを関数値で受け取るので、
    # 取得元を後から差し替えられる。
    {"リスト取得":取得F}で戻る
ここまで
```

ハブは**関数値を受け取ります**。フレームワークも設定ファイルも要りません。**「依存性の注入」は、関数を引数で渡すことです。**

使う側はこうです。

```nako3
●(ハブで利用者とリスト名の)ハブリスト取得
    取得F=ハブ["リスト取得"]
    取得F(利用者,リスト名)で戻る
ここまで
```

### テストから差し替える

差し替えられることを、テストで示します。

```nako3
●(利用者名とリスト名で)偽装取得
    見本=「fake item」でToDo項目作成
    結果=リスト名と[見本]でToDoリスト作成
    結果で戻る
ここまで
```

```nako3
対象=ハブで「uberto」と「book」のハブリスト取得
「差し替えたアダプタの結果が返る」と(対象["項目"][0]["説明"])と「fake item」で検証
```

インメモリの保管庫を一度も触らずに、ハブの振る舞いをテストできました。第 9 章で取得元がファイルに変わっても、**このテストは変わりません。**

### つまずき 1: 関数値を引数に渡すときはカッコで包む

最初こう書いて落ちました。

<!-- code-check: ignore わざと壊した書き方。直した形は下に載せている -->

```nako3
ハブ={関数}偽装取得でハブ作成
```

```bash
[文法エラー]test/hub_test.nako3(12行目): 未解決の単語があります: [『hub_test__偽装取得』で]
```

`{関数}偽装取得で` が、`{関数}偽装取得` + 助詞 `で` に切れてくれません。カッコで包むと通ります。

```nako3
# 関数値を引数に渡すときはカッコで包む。包まないと助詞の前で切られる。
ハブ=({関数}偽装取得)でハブ作成
```

第 2 章の「助詞は引数の名前のようなもの」という話の裏返しです。**助詞で引数を区切る言語では、引数の終わりがどこかを書き手が示す必要があります。**

### HTTP の層をハブ経由にする

アダプタ側も整えます。保管庫の作り方を知っているのは 1 箇所だけにします。

```nako3
●(利用者とリスト名で)インメモリ取得
    # ハブに渡すアダプタ。保管庫の作り方を知っているのはここだけ。
    状態=保管庫作成
    対象=状態で利用者とリスト名の状態内リスト取得
    対象で戻る
ここまで
```

> この章を書いた時点では `保管庫作成` が辞書を直接返していました。第 5 章でイベントの畳み込みに置き換わり、取り出し方も変わります。**上のコードは置き換え後の形です。** 章ごとのコードは `src/stepN/` に残っているので、第 2〜3 章の形は `src/step1/` で読めます（[ADR-015](../../../adr/ADR-015-step-directories.md)）。

```nako3
    # HTTP の層はハブしか知らない。保管庫の存在を知らない。
    ハブ=既定ハブ作成
    対象=ハブで要素[1]と要素[2]のハブリスト取得
```

**依存の向きが 1 本になりました。** HTTP アダプタ → ハブ → アダプタの関数値。ドメインは誰も知りません。

第 3 章で作った 2 経路の受け入れシナリオは、書き換えずに通ります。**内側を作り替えても、外から見た振る舞いが変わっていない**ことの証明です。中盤のリファクタリングは、この安全網の上で行います。

## 関数型コードをデバックする

型の無い言語で設計を変えると、何が起きるでしょうか。

Kotlin 版ならコンパイラが教えてくれます。`ToDoListFetcher` の型を変えれば、使っている場所が全部エラーになります。**なでしこ3 では何も起きません。** 動かしてみるまで分かりません。

### 道具は 3 つ

| 道具 | 使いどころ |
| :--- | :--- |
| `表示` | 値がどうなっているかを見る。`「{変数}」と表示` |
| `変数型確認` | それが何なのかを見る。`"number"` / `"string"` / `"function"` / `"object"` |
| `エラー監視` | 落ちる場所を絞る |

デバッグの多くは「この辞書に何が入っているか」を見ることに費やされます。`[object Object]` としか表示されないので、キーを 1 つずつ見るか、`辞書キー列挙` で並べます。

### 契約テストがデバッグを減らす

この章で一番効いたのは、デバッグの道具ではなく**契約テスト**でした。

`ハブ作成` が `{"リスト取得":取得F}` を返すと決め、それをテストで固定しました。

```nako3
「ハブはリスト取得キーを持つ」と(ハブ["リスト取得"]の変数型確認)と「function」で検証
```

このテストがあると、**キーの綴りを間違えた瞬間に落ちます。** 無ければ、HTTP を叩いて 404 が返ってきて、そこから遡ることになります。

**型検査は「書いた瞬間」に教えてくれます。契約テストは「テストを走らせた瞬間」に教えてくれます。** その差は数秒か数分です。デバッグが数十分かかることを思えば、どちらも十分に早い。

大事なのは**契約をどこかに書くこと**です。書かなければ、間違いは本番まで届きます。

## 関数型ドメインモデリング

`ToDo項目` に期限と状態を足します。ここで 2 つ、言語の制約に当たります。

### つまずき 2: 既定引数が無い

Kotlin 版はこう書けます。

```text
data class ToDoItem(
    val description: String,
    val dueDate: LocalDate? = null,
    val status: ToDoStatus = ToDoStatus.Todo
)
```

説明だけ渡せば、残りは既定値です。なでしこ3 に既定引数はありません。

**入口を 2 つ用意しました。**

```nako3
●(説明で)ToDo項目作成
    # なでしこ3 に既定引数は無いので、既定つきの入口を別に用意する。
    # 期限は日付の型が無いため文字列で持つ。無いことは空文字列で表す。
    {"説明":説明,"期限":"","状態":"Todo"}で戻る
ここまで

●(説明と期限と状態で)ToDo項目詳細作成
    {"説明":説明,"期限":期限,"状態":状態}で戻る
ここまで
```

**既存の呼び出しが 1 つも壊れませんでした。** `ToDo項目作成` の助詞も引数も変えていないためです。Kotlin 版が既定引数で得ている「後方互換な拡張」を、関数を増やすことで得ました。

期限は文字列です。なでしこ3 に日付の型はありません。`今日` は `2026/09/28` という形の文字列を返します。**「無い」を空文字列で表しているのは、第 2 章の `空` と同じ暫定です。**

### つまずき 3: 列挙型が無い

状態は 4 つです。`Todo`・`InProgress`・`Done`・`Blocked`。

Kotlin 版は `enum class` で、取りうる値の網羅をコンパイラが保証します。`when` で 1 つ書き忘れればコンパイルが通りません。

なでしこ3 には列挙型がありません。**文字列の約束にするしかない。** ただし、約束を 1 箇所に集めることはできます。

```nako3
●状態一覧
    # 列挙型が無い。取りうる 4 値をここに集め、契約テストが網羅を守る。
    ["Todo","InProgress","Done","Blocked"]で戻る
ここまで
```

そして契約テストで守ります。

```nako3
# 列挙型が無いので、状態の 4 値は一覧と契約テストで守る。
一覧=状態一覧
「状態は4値」と(一覧の要素数)と4で検証
「状態にTodoがある」と(一覧で「Todo」の出現回数)と1で検証
```

既定値が一覧に含まれることも確かめます。

```nako3
「既定の状態は一覧に含まれる」と(一覧で項目["状態"]の出現回数)と1で検証
```

**失われたものははっきりしています。** 状態を使う側で 1 つ書き忘れても、何も起きません。第 6 章で状態遷移を実装するとき、Kotlin 版は `when` の網羅がコンパイラに守られますが、こちらは**遷移表の 16 マスすべてをテストする**ことで代えます。

### モデルの形

この章の終わりで、ドメインはこうなっています。

| 概念 | 辞書のキー | 章 |
| :--- | :--- | :--- |
| ToDo 項目 | 説明・期限・状態 | 2（説明）、4（期限・状態） |
| ToDo リスト | リスト名・項目 | 2 |
| ハブ | リスト取得（関数値） | 4 |

**キーの一覧が、Kotlin 版の型定義に相当します。** 違うのは、この表を守るのがコンパイラではなくテストだということです。

## まとめ

- **データの取得元を外に出しました。** ハブが関数値でアダプタを受け取るので、テストから差し替えられます
- **「依存性の注入」は関数を引数で渡すことです。** フレームワークも設定ファイルも要りません
- 関数値を引数に渡すときは**カッコで包みます**。助詞で区切る言語では、引数の終わりを書き手が示します
- **既定引数が無いので、入口を 2 つ用意しました。** 既存の呼び出しは 1 つも壊れていません
- **列挙型が無いので、4 値を 1 箇所に集めて契約テストで守ります。** 網羅の保証は失われ、第 6 章では遷移表の全マスをテストして代えます
- 型の無い言語でのデバッグを減らすのは、デバッグの道具ではなく**契約をどこかに書くこと**です

次の章では、状態を書き換えるのをやめます。「今どうなっているか」を保存する代わりに、「何が起きたか」を保存します。起きたことの並びを畳み込むと、今の状態が出てきます。そしてその畳み込みの中に、**モノイド**という構造が見つかります。
