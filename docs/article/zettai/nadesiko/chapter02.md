# 第 2 章 関数を使って HTTP を扱う

## プロジェクトのキックオフ

第 1 章でテストを書く道具ができました。この章から Zettai を作り始めます。

最初にやることは決まっています。**ウォーキングスケルトンを通します。** HTTP のリクエストを受け取り、ToDo リストを HTML で返すまでを、最小の厚みで一度だけ通します。

### この章の到達点

`GET /todo/uberto/book` にアクセスすると、uberto さんの book というリストの項目が HTML で表示される。存在しないリストなら 404 が返る。これだけです。

範囲を狭く決めておきます。

- ToDo リストは 1 つだけ表示できる。作成も編集もできない
- データはメモリの中にある。ファイルにもデータベースにも保存しない
- 項目には説明しかない。期限も状態もない
- エラーは 404 を返すだけ

**薄く通すことを優先します。** ここでドメインを作り込むと、記事で説明していないコードが残ります。

## 関数型で HTML ページを提供する

なでしこ3 で HTTP サーバを書くには、簡易 HTTP サーバのプラグインを取り込みます。

```nako3
!「../node_modules/nadesiko3/src/plugin_httpserver.mjs」を取り込む
```

パッケージ名だけでは解決しません。**相対パスで書く**必要があります。パスはこのファイルからの相対です。

サーバの起動とルーティングは、入れ子の「〜には」で書きます。

```nako3
8080で簡易HTTPサーバ起動時には
    「/todo」に簡易HTTPサーバ受信時には
```

`〜には` は無名関数を渡す書き方です。**つまりこれは「ポート 8080 でサーバを起動し、そのときこの関数を実行する」という高階関数の呼び出し**です。ハンドラが関数であることが、日本語の語順のまま表れています。

ここで 1 つ注意があります。**ルーティングは URL の前方一致です。** `/todo` に登録すると `/todo/uberto/book` も `/todo/anything` も同じハンドラに届きます。パスの分解は自分で書く必要があります。

## Zettai の開発を始める

### 受け入れテストを書く（Red）

実装の前にテストを書きます。

```nako3
応答=「/todo/uberto/book」のZettai処理
「ToDo リストの項目が HTML に含まれる」と(応答["本文"]で「write chapter」の出現回数)と1で検証
```

`Zettai処理` はまだありません。実行すると、期待どおり落ちます。

```bash
$ make test
--- test/web_test.nako3
[エラー]NakoError: [取り込みエラー]test/web_test.nako3(2行目): ファイル .../src/web.nako3 が存在しません。
  -> FAILED
```

このテストは **HTTP を通しません。** `Zettai処理` はパスを受け取って応答の辞書を返す関数で、ネットワークを触りません。HTTP の層は第 2 章の終わりに配線します。テストが速く、落ちたときに原因の切り分けが要らないからです。

### ドメインとアダプタの境界を決める

実装の前に、どこで分けるかを決めます。ファイルは 3 つです。

| ファイル | 役割 |
| :--- | :--- |
| `src/domain.nako3` | ドメイン。ToDo リストと ToDo 項目 |
| `src/web.nako3` | HTTP アダプタ。パスの分解、HTML の組み立て、インメモリの保管庫 |
| `src/main.nako3` | 配線。サーバの起動とルーティング |

境界の定義は 1 つだけです。

> **`src/domain.nako3` は簡易 HTTP サーバのプラグインを取り込まない。**

なでしこ3 にはパッケージもアクセス修飾子もありません。**取り込みの不在だけが境界です。** 目に見えるので、破ろうとしたときに分かります。

## 矢印で設計する

### 型が無いときドメインをどう表すか

Kotlin 版ではドメインを型で表しました。`data class ToDoItem(val description: String)` と書けば、コンパイラが「説明を持つ何か」を保証します。

なでしこ3 には型がありません。**辞書で表します。**

```nako3
●(説明で)ToDo項目作成
    {"説明":説明}で戻る
ここまで

●(リスト名と項目列で)ToDoリスト作成
    {"リスト名":リスト名,"項目":項目列}で戻る
ここまで
```

これだけです。**問題は、この辞書が「説明」というキーを持つと誰も保証していないこと**です。呼び出す側が `項目["せつめい"]` と書いても、何も起きません。`undefined` が返るだけです。

だから契約テストを書きます。

```nako3
# 契約テスト。型が無いので、辞書のキーの有無と値の型をテストが守る。
項目=「write chapter」でToDo項目作成
「ToDo項目は説明キーを持つ」と(項目["説明"])と「write chapter」で検証
「ToDo項目の説明は文字列」と(項目["説明"]の変数型確認)と「string」で検証
```

**辞書を返す関数それぞれに、契約テストを 1 本置きます。** これがこの連載でコンパイラの代わりを務めるものです。以降の 11 章すべてでこの形を使います。

### つまずき 1: 助詞が契約の一部

`●(説明で)ToDo項目作成` と定義したら、呼ぶときは `「write chapter」でToDo項目作成` です。`「write chapter」のToDo項目作成` と書くと落ちます。

```bash
$ make test
[文法エラー]src/web.nako3(7行目): 未解決の単語があります: [文字列『write chapter』の]
次の命令の可能性があります:
 - Aでdomain__ToDo項目作成
```

**助詞は引数の名前のようなものです。** 型の無い言語で、これは悪いことばかりではありません。`保管庫で要素[1]と要素[2]のリスト取得` と書けば、3 つの引数がそれぞれ何なのかが呼び出し側で読めます。Kotlin の名前付き引数に近い働きをします。

エラーメッセージが「こう呼べばいい」と教えてくれるので、詰まる時間は短いです。

### つまずき 2: `変数型確認` は配列と辞書を区別しない

契約テストで項目の並びが配列であることを確かめようとして、落ちました。

```bash
  FAIL ToDoリストの項目は配列: 値が違う 実際=object 期待=array
```

`変数型確認` は配列にも辞書にも `"object"` を返します。**この 2 つを型名では区別できません。**

第 1 章で作った検証関数は `3` と `「3」` を区別できましたが、`[1,2]` と `{"x":1}` は区別できません。**型検査の代わりとしての網には、目が粗い部分があります。** 配列であることは、別の方法で確かめます。

```nako3
# 変数型確認 は配列も辞書も "object" を返す。区別できないので、
# 配列であることは「要素数が取れる」ことで確かめる。
「ToDoリストの項目は配列」と(リスト["項目"]の変数型確認)と「object」で検証
「ToDoリストは項目を1件持つ」と(リスト["項目"]の要素数)と1で検証
```

網の目が粗いところを知っておくことが、型の無い言語で設計するということです。

## ToDo リストをマップで提供する

データはメモリの中に置きます。辞書の入れ子で、利用者 → リスト名 → ToDo リストと辿ります。

```nako3
●保管庫作成
    本=「write chapter」でToDo項目作成
    符=「insert code」でToDo項目作成
    出=「publish book」でToDo項目作成
    書籍=「book」と[本,符,出]でToDoリスト作成
    {"uberto":{"book":書籍}}で戻る
ここまで
```

### つまずき 3: 辞書に無いキーは「空」ではない

取り出す関数を、最初こう書きました。

<!-- code-check: ignore わざと壊した最初の実装。直した形は下に載せている -->

```nako3
    利用者分=保管庫[利用者]
    もし、利用者分=空ならば
```

存在しない利用者を指定したテストが、404 ではなく実行時エラーで落ちました。

```bash
[実行時エラー]src/web.nako3(23行目): TypeError: Cannot read properties of undefined (reading '項目')
```

**辞書に無いキーを引くと `undefined` が返り、`空` との比較では捕まえられません。** 第 1 章で「`空` の実体は空文字列」と書きましたが、`undefined` はそれとも違います。

`辞書キー存在` で先に確かめます。

```nako3
●(保管庫で利用者とリスト名の)リスト取得
    # 「見つからない」を空で表すのは暫定。第 7 章で結果辞書に置き換える。
    # 辞書に無いキーを引くと undefined になり、空との比較では捕まえられない。
    # 辞書キー存在 で先に確かめる。
    もし、(保管庫に利用者が辞書キー存在)=偽ならば
        空で戻る
    ここまで
```

コメントに書いたとおり、**「見つからない」を `空` で表すのは暫定です。** `空` は「値が無い」も「空文字列」も「まだ調べていない」も同じ形で表してしまいます。第 7 章で、失敗の理由を持った結果の辞書に置き換えます。

**問題を認識しつつ、解決を後の章に譲るのも設計判断です。** ここで正しく直そうとすると、まだ説明していない概念を第 2 章に持ち込むことになります。

### HTML を組み立てる

テンプレートエンジンは使いません。文字列の `{}` 展開と `&` 連結で足ります。

```nako3
●(ToDoリストの)HTML描画
    項目行=「」
    項目列=ToDoリスト["項目"]
    Iを0から(項目列の要素数)-1まで繰り返す
        項目=項目列[I]
        項目行=項目行&「<li>{項目["説明"]}</li>」
    ここまで
    「<html><body><h1>{ToDoリスト["リスト名"]}</h1><ul>{項目行}</ul></body></html>」で戻る
ここまで
```

HTML エスケープはしていません。**これは教材だからです。** 実際のアプリケーションなら、項目の説明に `<script>` が入るだけで壊れます。

### 縦串が通る

パスを分解して、保管庫から取り出して、HTML にします。

```nako3
●(パスの)Zettai処理
    要素=パスのパス分解
    もし、(要素の要素数)≠3ならば
        {"状態":404,"本文":"<h1>404</h1>"}で戻る
    ここまで
```

そして配線です。

```nako3
8080で簡易HTTPサーバ起動時には
    「/todo」に簡易HTTPサーバ受信時には
        要求=GETデータ
        応答=要求["?URL"]のZettai処理
        応答["状態"]で{"Content-Type":"text/html; charset=utf-8"}を簡易HTTPサーバヘッダ出力
        応答["本文"]を簡易HTTPサーバ出力
    ここまで
ここまで
```

**`main.nako3` は配線しか持ちません。** 何を返すかは `Zettai処理` が決めます。だから `Zettai処理` は HTTP を通さずにテストできました。

`簡易HTTPサーバヘッダ出力` の助詞は **で** と **を** です。`404と{...}を` と書いて落ちました。つまずき 1 と同じ形です。

動かします。

```bash
$ make run
```

```bash
$ curl -s http://localhost:8080/todo/uberto/book
<html><body><h1>book</h1><ul><li>write chapter</li><li>insert code</li><li>publish book</li></ul></body></html>
```

存在しないリストは 404 です。

```bash
$ curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/todo/uberto/none
404
```

### 境界を検査する

「ドメインはプラグインを取り込まない」という約束を、テストで守ります。

```nako3
# ドメインの境界を検査する。ドメインは簡易 HTTP サーバのプラグインを取り込まない。
# 取り込みの不在が境界なので、不在を機械で確かめる。
中身=「src/domain.nako3」を開く
回数=中身で「plugin_httpserver」の出現回数
「ドメインは簡易HTTPサーバのプラグインを取り込まない」と回数と0で検証
```

ファイルの中身を読んで文字列を数えるだけの、素朴な検査です。それでも**わざと取り込みを足すと落ちます**。

```bash
  FAIL ドメインは簡易HTTPサーバのプラグインを取り込まない: 値が違う 実際=1 期待=0
```

**設計の規則は、書いておくだけでは守られません。** 検査にすると守られます。

### テストランナーの穴がもう 1 つ見つかった

つまずき 3 の実行時エラーが出たとき、テストランナーは**「6 本成功 / 0 本失敗」と表示していました。**

第 1 章でランナーは終了コードと出力のエラー表示の 2 つを見るようにしました。ところが出力を見る側の条件が狭すぎました。`[エラー]` という表示だけを探していたのです。実行時エラーは `[実行時エラー]` と出るので、**ひっかかりませんでした。**

```makefile
	  if [ $$code -ne 0 ] || echo "$$out" | grep -qE 'エラー\]'; then \
```

`エラー]` で終わるものをすべて拾うように直しました。**第 1 章で同じ形のバグを直したばかりです。** 判定条件を狭く書くと、想定していない形の失敗をすり抜けます。

## まとめ

- **ウォーキングスケルトンを通しました。** HTTP のリクエストから HTML までが、薄く一度だけつながっています
- **型の無い言語では、ドメインを辞書で表します。** キーが契約で、契約テストがそれを守ります。辞書を返す関数それぞれに 1 本置きます
- **境界は取り込みの不在です。** パッケージもアクセス修飾子も無いので、不在を機械で検査します
- 助詞は引数の名前のようなもので、**呼び出し側で引数の意味が読めます**
- `変数型確認` は配列と辞書を区別しません。**網の目が粗いところを知っておきます**
- 辞書に無いキーは `undefined` で、`空` では捕まえられません。`辞書キー存在` で確かめます。**「見つからない」の表し方は第 7 章で直します**

この章のテストは、まだ実装の詳細を知りすぎています。`Zettai処理` という関数の名前も、応答の辞書のキーも、テストに書かれています。第 3 章では、テストを業務の言葉で書き直し、実行経路を差し替えられる形にします。
