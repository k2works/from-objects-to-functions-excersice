# ADR-004 静的解析を check に組み込まず記事のコード例検査を優先する

日付: 2026-09-26

## ステータス

2026-09-26 提案されました

## コンテキスト

[開発戦略](../development/development_strategy.md) は「静的解析（ktlint / detekt）を `check` に組み込むかは Unit 1 の Gradle 雛形作成時に決めて ADR に記録する」としていましたが、**Unit 1 では決めずに積み残しました**。Unit 2 の開始準備の検証（`validating-design` 軸 A）でこの積み残しが検出され、本 Unit で消化することになりました。

判断の材料は次のとおりです。

- 本プロジェクトの成果物は**記事とサンプル実装の対**であり、コードは読者に読まれることを前提に書く
- 記事のコードは説明のために意図的に単純化する箇所がある。ボウリングの得点計算の定数、短い関数名、`when` の分岐の並びなど
- 開発者は 1 名で、複数人の書き方のブレという問題が発生していない
- Unit 1 で実際に起きた品質問題は **1 件**で、それは「記事に載せたコードの実装が存在しなかった」ことだった。静的解析では検出できない種類の問題である

## 決定

**静的解析（ktlint / detekt）を `check` に組み込みません。** 代わりに、記事のコード例が実装に存在することを検査するスクリプトを CI に入れます。

1. `check` に集約するのはコンパイル・テスト・カバレッジ検証（Kover、ドメイン層 80%）とする
2. 記事のコード例検査（`ops/scripts/article/check_article_code.py`）を CI の独立したジョブとして実行する
3. 逐語の転記でない抜粋は、記事側に `<!-- code-check: ignore 理由 -->` を置いて除外する
4. **再検討は Unit 5（第 9 章）**。永続化が入りコード量が増える時点で、書き方のブレが実際に問題になっているかを見て判断する

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| detekt を入れる | 複雑度・マジックナンバー・命名のルールが、説明のために単純化した教材コードと衝突する。抑制コメント（`@Suppress`）が記事のコードに写り込むと、説明していない要素が増えて記事が読みにくくなる |
| ktlint（整形のみ）を入れる | 衝突は detekt より少ないが、1 名体制で整形のブレが問題になっていない。`check` にゲートを増やすと、得られるものより CI 時間とビルドの複雑さが増す |
| 両方入れて記事用に緩い設定を作る | 設定の維持が新しい仕事になる。連載を書き切ることが目的であり、ビルド設定の作り込みはその手段にすぎない |

## 影響

- **書き方のブレは人のレビューで吸収する。** 記事の全文検証（承認ゲート）でコードも読むため、極端なブレはそこで止まる
- **記事と実装の乖離は機械的に止まる。** Unit 1 で実際に起きた問題に対して、直接効く検査を入れた
- CI のジョブは 2 つ（`check` と記事のコード例検査）にとどまり、実行時間が短い
- Unit 5 で再検討する。そこで必要と判断すれば、静的解析を後から足せる。**逆に、入れたものを外すほうが難しい**

## コンプライアンス

- `.github/workflows/kotlin-zettai.yml` に記事のコード例検査のジョブがあること
- 第 1 章以降のすべての章で、検査が違反 0 件であること
- Unit 5 の Bolt 計画に、静的解析の再検討をステップとして入れること

## 再検討の結果（Unit 5・2026-09-27）

再検討条件は「Unit 5 で、書き方のブレが実際に問題になっているかを見て判断する」でした。**ブレは実際に起きていました。**

| 検査 | 結果 |
| :--- | :--- |
| 行長 120 超 | 2 件（`ToDoListState.kt`） |
| `import` の並びがアルファベット順でない | 3 件 |
| タブの混入・インデント幅の不一致 | 0 件 |

行長は記事のコードブロックが折り返す原因になり、**本プロジェクト固有のリスク（記事の読みやすさ）に直結**します。そこで ktlint（`org.jlleitschuh.gradle.ktlint` 12.3.0）を導入し、実際に動かしました。

### ktlint を試して、採用しなかった

ktlint の標準ルールセットを適用すると、次の整形が入りました。

| 入った整形 | 記事への影響 |
| :--- | :--- |
| 引数が 2 つ以上の関数シグネチャを強制的に複数行に分割 | **教材コードが縦長になり、記事のコードブロックが読みにくくなる** |
| `if (x) a else b` を必ずブロックに展開 | 同上 |
| 式の本体を必ず改行してインデント | 同上 |
| ファイル名をクラス名に合わせる | 第 1 章の `BowlingGameOO.kt`（OO 版）と `BowlingGame.kt`（FP 版）を並べられない |
| 関数名を camelCase に強制 | DDT のステップ名（`` `has a list` ``）とテスト名（日本語）が書けない |

下 2 つは `.editorconfig` でルールを外して回避できました。しかし**上 3 つは ktlint の中核の整形**で、外すと導入の意味がほとんど残りません。

整形を適用した結果、記事のコード例が **40 件**実装とずれました（記事のコード例検査が検出）。つまり ktlint の整形は、この連載のコードを「記事に載せにくい形」に変える方向に働きます。

**目的（行長と import 順の 2 点）に対して副作用が大きすぎる**ため、採用しませんでした。整形は取り消しました。

### 代わりにしたこと

必要な 2 点だけを検査するスクリプトを作りました（`ops/scripts/article/check_code_style.py`）。

- 行が 120 文字を超えていないか
- `import` がアルファベット順に並んでいるか

検出した 5 件は手で直しました。行長の 2 件は、鍵を作る関数（`ToDoListEvent.key()`）を切り出して短くしました。**汎用ツールの整形より、意味のある切り出しになりました。**

### 次の再検討

**時期では区切りません。** 次のいずれかが起きたら再検討します。

1. 開発者が 2 名以上になる（書き方のブレが人の間で起きる）
2. 自作の検査で拾えない種類の問題（複雑度・未使用コード・バグの兆候）が実際に起きる
3. 記事のコードの縦長さを許容してよい章が出てくる（たとえば第 13 章の総括）

**「Unit 5 で見直す」という時期の期限は、見直しを忘れないためには有効でした。** ただし判断そのものは事象で行うべきで、時期が来たことは判断の理由になりません。
