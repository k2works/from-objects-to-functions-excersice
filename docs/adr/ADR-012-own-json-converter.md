# ADR-012 JSON の変換を自前の Converter で書き Kondor を導入しない

日付: 2026-09-27

## ステータス

2026-09-27 提案されました

## コンテキスト

第 9 章で、出来事を JSON に書き出す処理を手書きしました。そのとき記事にこう書きました。

> JSON のシリアライズは手書きです（第 12 章で Kondor に置き換えます）。

第 12 章で置き換えを検討します。[執筆計画](../article/outline.md) も第 12 章の参照先を「Kondor による JSON」としています。

### 第 9 章の手書きの問題

書き出し（`toJson`）と読み込み（`eventFrom`）が**別々の関数**でした。

| 問題 | 内容 |
| :--- | :--- |
| 片方だけ直せる | 書き出しにフィールドを足して読み込みを忘れると、実行時に落ちる |
| 対応が型に現れない | 「この 2 つは対である」ことをコンパイラが知らない |
| 文字列を正規表現で読む | 入れ子に対応できない |

第 11 章で `ListRenamed` を足したとき、**実際に両方を直す必要がありました**。忘れたら往復が壊れます。

### Kondor を調べた

[Unit 5（ktlint）・Unit 6（テンプレート）と同じ順序](ADR-004-static-analysis.md)で、**既製品を先に調べました。**

Kondor 3.5.2 の依存を確認しました。

| 依存 | バージョン |
| :--- | :--- |
| `kondor-outcome` | 3.5.2 |
| `kotlin-stdlib-jdk8` | 2.1.0 |

Kotlin 2.1 の stdlib に依存しているので、**本プロジェクトの Kotlin 2.2 では動きます。**

問題は 1 つめです。**Kondor は独自の `Outcome` 型を持ち込みます**（`kondor-outcome`）。

本連載は第 7 章で `Outcome` を自作しました。**教材としての中心的な成果物**です。Kondor を入れると、`zettai.fp.Outcome` と Kondor の `Outcome` が並びます。

| 選択 | 結果 |
| :--- | :--- |
| 両方持つ | 同じ名前の型が 2 つ。読者が混乱する |
| 変換する | 境界で相互変換するコードが増える。第 7 章の成果物の意味が薄れる |
| Kondor の `Outcome` に統一する | **第 7 章を書き直すことになる** |

どれも取りたくありません。

### 主題との関係

第 12 章の節構成は「JSON を関数型にする」「プロファンクタとの出会い」です。**主題は JSON ライブラリの使い方ではなく、双方向変換をプロファンクタとして型にすること**です。

原著も Kondor ではなく Klaxon（JSON ライブラリ）を使い、その上に `Parser<A, S>` という**自前の双方向変換の型**を定義しています。プロファンクタの主題はそちらです。

## 決定

**Kondor を導入しません。** 第 9 章の手書きシリアライズを、双方向変換の型に発展させます。

```kotlin
/**
 * 双方向の変換。
 *
 * 書き出し（render）と読み込み（parse）を 1 つの型で対にする。
 * 片方だけ直して壊れることを防ぐ。
 *
 * 出力側は map で、入力側は contramap で変換できる。
 * 両方持つ構造をプロファンクタと呼ぶ。
 */
data class Converter<A, B>(
    val render: (A) -> B,
    val parse: (B) -> Outcome<ZettaiError, A>
)
```

構成は 2 段です。

| 段 | 型 | 役割 |
| :--- | :--- | :--- |
| 1 | `Converter<ToDoListEvent, JsonObject>` | 出来事と「名前と値の並び」の対応 |
| 2 | `.map(JsonObject::toJsonString, String::toJsonObject)` | 文字列への変換を重ねる |

**`map` で段を重ねられるのがプロファンクタの利点です。** 出来事 ↔ 文字列を直接書かず、途中の形を経由できます。

## 影響

- **書き出しと読み込みが 1 つの型になりました。** 片方だけ直すことができません
- **往復をプロパティベーステストで確かめられます。** `roundTrip` があるので、ランダムな出来事で「書いて読むと元に戻る」ことを検証しました
- **第 9 章の記事のコード例が古くなります。** 記事のコード例検査が検出するのでマーカーを足します
- 入れ子のある JSON は扱えません。Zettai の出来事は平坦なので足りています

## 失うもの

| 失うもの | 影響 |
| :--- | :--- |
| 入れ子の JSON | 出来事が平坦なので今は不要。必要になったら `JsonObject` を再帰的にする |
| 配列 | 同上 |
| 数値・真偽値の型 | すべて文字列として扱う。`ToDoStatus` は `valueOf` で復元している |
| エスケープ | 値に `"` が入ると壊れる。**実務では必須**。第 13 章の「扱わなかったこと」に加える |

最後の項目は第 11 章の HTML エスケープと同じ種類の限界です。**第 13 章で明示します。**

## 再検討の条件

次のいずれかに当たったら、Kondor などの JSON ライブラリの導入を検討します。

1. 入れ子の JSON や配列を扱う必要が出た
2. 外部と JSON をやり取りするようになり、エスケープと型（数値・真偽値）の正しさが要求になった
3. 変換する型が増え、`Converter` の組み立てが重複しはじめた

**再検討は「2 の事象が起きたとき」を最優先の目安にします。** 自前の実装はエスケープを扱っていないので、外部と JSON をやり取りする時点で条件を満たします。

## コンプライアンス

- `Converter` が `render` と `parse` を 1 つの型で持つこと
- `roundTrip` のプロパティベーステストが green であること
- プロファンクタ則（出力側・入力側の恒等則と合成則）が green であること
- `zettai.json` がフレームワークを import しないこと（`DomainBoundaryTest` の対象に加えるかはステップ 7-1.3 で判断）
