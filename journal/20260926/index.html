    2026-09-26 Zettai 連載の計画立ち上げと Unit 1 の完了¶

    この日やったこと¶

    プロジェクト管理が未初期化の状態から、Zettai 連載の計画一式を立ち上げ、最初の Unit を完了させた。

    /orchestrating-project --status で状態を見たところ、docs/development/ は索引のみ、Issue も Milestone も 0 件だった。一方で連載の執筆計画（docs/article/outline.md）には全 13 章の構成と前提整備のチェックリストが揃っていた。計画が無かったのではなく、記事側の言葉で書かれていたというのが実際のところだった。

    そこで執筆計画をプロジェクト管理の言葉に写すところから始めた。

    判断と、その理由¶

    1. 記事の執筆計画を計画の入力にした¶

    ゼロから計画を書き起こさず、outline.md の 13 章構成をそのまま Unit とストーリーに写した。章立てが設計の到達順序を決めている題材なので、計画を別に立てると二重管理になる。

    両者の役割を明示的に分けた。執筆計画は章構成と執筆規約の一次情報、リリース計画は進行と進捗の一次情報。 章の割り当てを変えたら同じコミットで揃える規約を執筆規約に書いた。

    2. XP 版で書いた計画を AI-DLC に作り直した¶

    最初にストーリーポイントとベロシティで計画を書いたが、「AI-DLC に準拠していない」と指摘を受けて作り直した。

    作り直して分かったのは、見た目の用語の置き換えではなく、測っているものが変わるということだった。

    変えたもの 前 後
    ポイントの意味 人が実装する規模 人が検証に費やす時間（AI 自律度の逆数）
    見積もりの方法 相対見積もり 5 軸のエントロピー評価
    進捗の指標 ベロシティ 完了 Unit 数・承認ゲート通過数・変更依頼数・リードタイム
    タスク 人が実装する作業 AI が 1 回のやり取りで完結させるステップ + 完了判定 + 人の確認要否
    バッファ フィーチャ / スケジュール スコープ / 検証（人の検証時間がボトルネック）

    指摘を受けるまで、この違いを軽く見ていた。AI-DLC は XP の用語を言い換えたものではなく、ボトルネックが「人が書く時間」から「人が検証する時間」に移ったことを前提にした計画法だった。

    3. 未解決の仮定が HIGH の Unit で、スパイクを先頭に置いた¶

    Unit 1 のエントロピー評価で、未解決の仮定だけが HIGH になった。「nixpkgs の kotlin で Kotlin 2.x が入る」「Gradle プラグインと JDK 21 が組み合わせて動く」がいずれも未検証だった。

    そこで Bolt 1-1 の最初のステップをスパイクにした。これが当たった。 nixpkgs の kotlin は 2.3.0 だが、Maven Central の kotlin-gradle-plugin の最新安定版は 2.2.0 で、CLI とビルドでバージョンが一致しない。

    スパイクなしで雛形を作っていたら、ビルドが壊れてから原因を探すことになっていた。結果として「ビルドの正は Gradle 側に置く」という判断が生まれ、そのまま ADR-001 になった。仮定を潰す作業が、そのまま設計判断の記録になる。

    4. BDD / Gherkin を採用しないと決めた¶

    開発戦略で受け入れテストの書き方を決めるとき、docs/reference/BDD導入ガイド.md の Cucumber-JVM を採るか迷った。

    採らないことにした。理由は 2 つある。第 3 章の主題が「受け入れテストを高階関数で抽象化し、DDT を Pesticide に変換する」ことなので、外から Cucumber を持ち込むと読者が学ぶべき組み立てが「解決済みの問題」に見える。そして 1 名体制で 13 章を書き切るには、受け入れテストの層を 2 つ維持するコストが見合わない。

    「ガイドがあるから使う」ではなく「この題材で何を教えたいか」から決めた。不採用の理由を戦略に書き残したので、後から蒸し返さずに済む。

    詰まったところ¶

    nix flake show が新しい shell.nix を見つけられなかった¶

    devShell を足した直後、nix develop .#kotlin が「path does not exist」で落ちた。flake は git が追跡しているファイルしか見ない。git add -N で index に載せたら通った。

    新しいファイルを足して flake を評価するときは、先に git に知らせる。

    記事に、実装の無いコードを書いていた¶

    第 1 章に「オブジェクト指向で書くとこうなる」という比較用のコード例を載せたが、そのコードを実装していなかった。執筆規約の「コード例は動作確認済み実装から転記する」に反している。

    BowlingGameOO とそのテストを追加して転記し直した。

    気づけたのは人が読んだからで、機械的には検出していなかった。 章が進むほどコード例は増えるので、Unit 2 で「記事のコードブロックが実装に存在するか」を検査する仕組みを CI に入れることにした。

    あわせて、逐語の転記ではない 3 種類（使用例・リファクタリング前の履歴・... を含む省略）を記事に明示した。書いておかないと、検証のたびに同じ議論をすることになる。

    次回に活かすこと¶

    • リードタイムの実績（1 日）を額面どおり受け取らない。 Unit 1 は本番機能を持たない基盤 Unit で、検証の大半がコマンドの終了コードで済んだ。人が読む量が支配的になる Unit 2 以降とは別物として扱う
    • ゲート密度の見直しは Unit 2 の完了時。 開発戦略では「ウォーキングスケルトンのゲートを通過した時点で 1 回だけ決める」としているが、スケルトンそのものは Unit 2（第 2 章）。Unit 1 はその土台なので、まだ判断材料が揃っていない
    • 自動判定できない領域にゲートを残す。 変更依頼が出たのは記事のコード例の出所という、コマンドで判定できない領域だった。記事のステップは引き続き人の全文検証を必須にする
