# 第 3 章 ドメインの定義とテスト

## 受け入れテストを改善する

第 2 章で縦串が通りました。テストも通っています。ではこのテストは良いテストでしょうか。

```nako3
応答=「/todo/uberto/book」のZettai処理
「ToDo リストの項目が HTML に含まれる」と(応答["本文"]で「write chapter」の出現回数)と1で検証
```

### このテストが知りすぎていること

2 行のうち、業務として意味があるのは「uberto の book というリストに write chapter という項目がある」ことだけです。残りは全部、実装がたまたまそうなっているだけの事情です。

| テストに書いてあること | 業務の話か |
| :--- | :--- |
| `Zettai処理` という名前の関数がある | いいえ。関数の名前は実装の都合 |
| パスが `/todo/uberto/book` という形をしている | いいえ。URL の設計は実装の都合 |
| 応答が `状態` と `本文` というキーを持つ辞書である | いいえ。返り値の形は実装の都合 |
| 本文が HTML で、項目が文字列として含まれる | いいえ。表示の形式は実装の都合 |
| uberto の book に write chapter がある | **はい** |

**4 対 1 です。** このテストは、実装を少し変えるだけで壊れます。壊れたとき、業務の要求が変わったのか実装の都合が変わったのかが分かりません。

### 目指す形

シナリオはこう書きたいはずです。

> uberto は book の項目を 3 件見られる。最初の項目は write chapter である。

ここに `Zettai処理` も HTML も出てきません。**「何を確かめるか」と「どうやって確かめるか」を分けます。**

## 高階関数を使う

分ける道具は高階関数です。シナリオは「どうやるか」を引数として受け取ります。

### 操作の一覧を決める

シナリオが使える操作を決めます。今のところ 1 つです。

- **リスト参照**: 利用者名とリスト名を渡すと、項目の説明の並びが返る

これを関数値として辞書に詰め、シナリオに渡します。

```nako3
●ドメイン直接_操作作成
    {"経路名":"ドメイン直接","リスト参照":{関数}ドメイン直接_リスト参照}で戻る
ここまで
```

`{関数}名前` が関数を値にする書き方です。**なでしこ3 でも関数は第一級の値です。** 辞書に入れて持ち回せます。

### シナリオを書く

```nako3
●(操作で)シナリオ_ToDoリスト参照
    取得F=操作["リスト参照"]
    経路表示=操作["経路名"]
    項目列=取得F(「uberto」,「book」)
    「{経路表示}: uberto は book の項目を 3 件見られる」と(項目列の要素数)と3で検証
    「{経路表示}: 最初の項目は write chapter」と項目列[0]と「write chapter」で検証
ここまで
```

`Zettai処理` も HTML も消えました。**残ったのは業務の言葉だけです。**

辞書から取り出した関数は、一度変数に受けてから呼びます。`操作["リスト参照"](…)` と直接書くとパーサが落ちます。受けてしまえば `取得F(「uberto」,「book」)` とカッコで呼べます。

### つまずき 1: 識別子にひらがなを混ぜると切られる

シナリオの名前を最初 `シナリオ_ToDoリストを見る` と書いて落ちました。

```bash
[文法エラー]test/ddt/scenario.nako3(7行目): 不完全な文です。単語『見』が解決していません。
```

**`を` が助詞として切られます。** `シナリオ_ToDoリスト` + `見る` の 2 つの単語だと解釈されます。

```nako3
# 関数名に「を」「に」などのひらがなを入れると助詞として切られるので、
# シナリオ名は漢字とカタカナと英数字で組む。
```

業務の言葉で書きたいのに、日本語の名前が制約を受けるのは皮肉です。`シナリオ_ToDoリスト参照` に落ち着きました。**「を」を使わずに業務を語る**のが、この言語での書き方です。

同じ理由で `参照` という変数名も使えませんでした。組み込み命令と衝突します（第 2 章のつまずき 3 と同じ形）。`取得F` にしました。

## ドメインとインフラストラクチャの分離

分離できたと言うには、確かめる方法が要ります。**同じシナリオを 2 つの経路で走らせます。** 片方だけ落ちたら、そこに業務ロジックが漏れています。

### 経路 1: ドメイン直接

HTTP を通さず、ドメインを直接呼びます。

```nako3
●(利用者名とリスト名で)ドメイン直接_リスト参照
    保管庫=保管庫作成
    対象=保管庫で利用者名とリスト名のリスト取得
    もし、対象=空ならば
        []で戻る
    ここまで
```

### 経路 2: HTTP 経由

起動中のサーバを叩いて、返ってきた HTML から項目を抜き出します。

```nako3
●(本文の)LI抽出
    説明列=[]
    断片列=本文を「<li>」で区切る
```

**この 2 つは、シナリオから見れば同じものです。** 同じ引数を受け取り、同じ形の値を返します。違うのは中身だけです。

## ドメインからテストを駆動する

2 経路を走らせます。

```nako3
操作=ドメイン直接_操作作成
操作でシナリオ_ToDoリスト参照
操作でシナリオ_無リスト参照
```

```bash
$ make check
--- test/see_a_todo_list_test.nako3
  ok ドメイン直接: uberto は book の項目を 3 件見られる
  ok ドメイン直接: 最初の項目は write chapter
  ok ドメイン直接: 無いリストの項目は 0 件
--- doctest/see_a_todo_list_http.nako3
  ok HTTP経由: uberto は book の項目を 3 件見られる
  ok HTTP経由: 最初の項目は write chapter
  ok HTTP経由: 無いリストの項目は 0 件
```

**同じ 3 つのシナリオが、2 つの経路で通りました。** ドメイン直接の経路は簡易 HTTP サーバのプラグインを一度も触りません。それで同じ結果になるということは、業務ロジックが HTTP の層に漏れていないということです。

境界そのものも検査しています（第 2 章）。ドメインのファイルがプラグインを取り込んでいないことを、ファイルの中身を読んで確かめます。**分離は 2 つの方法で守られています。** 取り込みの不在（構造）と、2 経路が同じ結果になること（振る舞い）です。

### つまずき 2: 関数値ごしに呼ぶと非同期が待てない

HTTP 経由の経路を最初こう書きました。

<!-- code-check: ignore わざと壊した最初の実装。直した形は下に載せている -->

```nako3
    本文=URLからAJAXテキスト取得
    (本文のLI抽出)で戻る
```

シナリオから呼ぶと、項目が 0 件になりました。返っていたのはこれです。

```bash
R=[object Promise] 型=object
```

**関数値ごしに呼ぶと、中の非同期な組み込み命令が待たれません。** 直接 `「…」からAJAXテキスト取得` と書けば待ちます。`{関数}名前` で値にして `F(…)` と呼ぶと、Promise がそのまま返ります。

回避策は、**シナリオに渡す関数から入出力を追い出すこと**でした。

```nako3
●(利用者名とリスト名で)HTTP経由_応答記録
    保存先=「.ddt_response.html」
    「curl -s -o {保存先} http://localhost:8080/todo/{利用者名}/{リスト名}」をコマンド実行待機
    応答表[「{利用者名}/{リスト名}」]=保存先を開く
ここまで
```

応答を先に記録しておき、シナリオが呼ぶ関数は記録を引くだけにします。

```nako3
# もう 1 つ制約がある。関数値ごしに呼ぶと、中の非同期な組み込み命令が
# 待たれず Promise がそのまま返る。そこでシナリオに渡す関数は
# 入出力をせず、先に記録した応答を引くだけにする。
```

**副作用を関数の外に追い出したのは、制約に押されての判断でした。** 結果として、シナリオに渡す関数はどちらの経路も純粋になりました。関数型の設計としてはむしろ良い形です。

サーバの起動と停止も、テストの外に出しました。テストの中からサーバを起こすと親プロセスが返らないためです。`Makefile` が持ちます。

<!-- code-check: ignore 第 3 章時点の Makefile。第 8 章で起動待ちを到達確認に変える -->

```makefile
	  $(CNAKO) src/$$s/main.nako3 > /dev/null 2>&1 & \
	  pid=$$!; \
	  sleep 2; \
```

### つまずき 3: `繰り返す` は逆向きに回る

HTTP 経由の「無いリストは 0 件」だけが落ちました。

```bash
  FAIL HTTP経由: 無いリストの項目は 0 件: 値が違う 実際=2 期待=0
```

404 の本文は `<h1>404</h1>` で、`<li>` は 1 つもありません。それなのに 2 件返っています。

原因は `LI抽出` のループでした。

```bash
$ cnako3 -e 'A=[「x」]
回数=0
Iを1から(Aの要素数)-1まで繰り返す
  回数=回数+1
ここまで
「{回数}」と表示'
2
```

**`Iを1から0まで繰り返す` が、空回りせずに 2 回まわります。** 1 と 0 を順に取って、逆向きに回っているのです。

多くの言語では、開始が終了より大きい範囲のループは 0 回です。なでしこ3 は違います。**「空の配列を回す」コードが全部、静かなバグでした。**

```nako3
    # なでしこ3 の「繰り返す」は開始が終了より大きくても空回りせず、
    # 逆向きに回る。要素が無いときは先に戻る。
    もし、(断片列の要素数)<2ならば
        説明列で戻る
    ここまで
```

第 1 章と第 2 章で書いたコードにも同じ形が 4 箇所ありました。**まだ空の配列を渡していなかったから、通っていただけです。** すべてにガードを入れました。

型検査があってもこのバグは止まりません。**言語の癖は、踏んでから知るしかない**部分が残ります。だからこそ、踏んだら検査かガードにして、二度目を防ぎます。

## DDT を共通の仕組みに変換する

> この節はマインドマップでは「DDT を Pesticide に変換する」です。Pesticide は Kotlin のライブラリで、なでしこ3 には存在しません。読み替えの規則は [執筆計画](../../outline.md) にあります。

Kotlin 版はここで、手作りした受け入れテストの構造を Pesticide というライブラリに載せ替えます。構造に名前が付き、維持する対象が減るからです。

なでしこ3 にはそういうライブラリがありません。**載せ替える先が無いとき、何をするのが同じことになるでしょうか。**

答えは「構造に名前を付けて、1 箇所に集める」ことです。ライブラリはその手段の 1 つにすぎません。

| ライブラリがやってくれること | なでしこ3 版でやったこと |
| :--- | :--- |
| シナリオと実行経路を分ける枠組み | 操作の辞書。キーが操作の一覧、値が関数 |
| 複数の経路で同じシナリオを回す | 経路ごとに `操作作成` を用意し、シナリオに渡す |
| 結果の集計と報告 | 第 1 章で作った `検証` と `テスト結果報告` |
| 置き場所の規約 | `test/ddt/` に集める |

ファイルはこう分かれました。

| ファイル | 役割 |
| :--- | :--- |
| `test/ddt/scenario.nako3` | シナリオ。業務の言葉だけ |
| `test/ddt/actions_domain.nako3` | 実行経路 1: ドメイン直接 |
| `test/ddt/actions_http.nako3` | 実行経路 2: HTTP 経由 |
| `test/see_a_todo_list_test.nako3` | ドメイン直接で走らせる |
| `doctest/see_a_todo_list_http.nako3` | HTTP 経由で走らせる |

**ライブラリを使わないと決めたのではなく、使えるものが無かっただけです。** それでも得られたものは同じでした。構造に名前が付き、置き場所が決まり、シナリオが業務の言葉になりました。

代わりに失ったものもあります。この枠組みは自分で維持します。壊れたら自分で直します。**Kotlin 版が「やめるときに捨てるものが少ないか」を考えて載せ替えを決めたのに対し、こちらは捨てる判断すらできません。** 選択肢が無いことは、判断が要らないということでもあります。

## まとめ

- **テストが知りすぎている問題を特定しました。** 5 つのうち業務として意味があるのは 1 つで、残りは実装がたまたまそうなっているだけでした
- **高階関数で実行経路を外に出しました。** 操作の一覧を辞書で宣言し、「どうやるか」を関数値に閉じ込めました
- **ドメインとインフラストラクチャが分離されました。** 同じシナリオが 2 経路で通ることで確かめられます。片方だけ落ちたら、そこに業務ロジックが漏れています
- 関数値ごしに非同期の命令は待てません。**シナリオに渡す関数から入出力を追い出したら、結果としてどちらの経路も純粋になりました**
- `繰り返す` は逆向きに回ります。**空の配列を回すコードが 5 箇所、静かなバグでした**
- ライブラリが無くても、**構造に名前を付けて 1 箇所に集めれば同じことができます**

この章で作った受け入れテストの入口を、**残りの 10 章すべてが使います**。次の章からは、この入口の内側を作り込んでいきます。第 4 章では、アダプタを関数値で差し替えられるようにします。今はまだ `保管庫作成` が実装の中に埋まっています。
