    第 9 章 モナドによる安全なデータ永続化¶

    安全に永続化する¶

    第 8 章までで、イベントから状態も射影も作れるようになりました。ただしイベントはメモリの中にしかありません。 アプリケーションを落とすと消えます。

    保存します。保存するのはイベントだけです。状態も射影もそこから作れるので、保存する必要がありません（第 5 章）。

    何が「安全」なのか¶

    この章の題は「安全に永続化する」です。安全とは何でしょうか。

    保存も読み出しも失敗しうる、ということです。ファイルが無い、書き込めない、壊れている。そして失敗しうる処理はつながります。読んで、畳み込んで、また書く。途中のどこで失敗しても、後ろの処理が動いてはいけません。

    第 7 章で失敗を値にしました。この章では、失敗しうる処理をつなぐところまで進みます。

    ファイル永続化と結合テスト¶

    この節はマインドマップでは「PostgreSQLと結合テスト」です。なでしこ3 の処理系（cnako3）にデータベースのプラグインがありません。 ファイルに保存します。読み替えは 執筆計画 の規約に従い、章構成マインドマップ に登録しています。

    何が変わり、何が変わらないか¶

    観点 Kotlin 版 この版 同じか
    状態を保存するか しない しない 同じ
    追記のみか そう そう 同じ
    保存先 PostgreSQL の 1 テーブル 1 ファイル 違う
    順序の根拠 id BIGSERIAL 行の並び 形は違うが役割は同じ
    検索 インデックス 無い。全行を走査 違う
    結合テストの用意 docker-compose と CI のサービスコンテナ 不要。一時ファイルだけ 違う

    判断は同じで、手段だけが違います。 判断は ADR-019 に記録しました。

    Kotlin 版が結合テストのために DB を用意する判断（ADR-009）は、この版では不要になります。「不要」も判断のうちなので、そのことも ADR に書きました。 書かないと、後から「移植しそこねた」ように見えます。

    結合テストは一時ファイルで¶

    テストは自分が作ったファイルを消します。

    # 永続化の契約テスト。
# テストは自分が作ったファイルを消す。残すと次の実行に影響する。

    外部サービスが要らないぶん、CI は軽くなりました。代わりに後始末を自分でする必要があります。

    なでしこ3 でファイルに書き出す¶

    この節はマインドマップでは「Kotlinでデータベースに接続する」です。言語名と製品名がそのまま入っているので読み替えました。

    追記の命令が無い¶

    なでしこ3 のファイル命令は 開 と 保存 だけです。追記がありません。

    ●(事象列を保存先へ)保管追記
    # 追記の命令が無いので、読んで足して書き戻す。
    旧=「」
    もし、保存先が存在ならば
        旧=保存先を開く
    ここまで

    読んで、足して、書き戻します。これは件数が増えると遅くなります（毎回全文を読み書きする）。本連載では扱いませんが、ADR-019 の「この決定が解かないこと」に書きました。

    1 行 1 JSON¶

        出力=旧
    Iを0から(事象列の要素数)-1まで繰り返す
        行=事象列[I]をJSONエンコード
        出力=出力&行&改行
    ここまで
    出力を保存先へ保存

    イベントの辞書をそのまま JSONエンコード します。読み戻すときは行ごとに JSONデコード します。

    {"種別":"ListCreated","利用者":"uberto","リスト名":"book"}
{"種別":"ItemAdded","利用者":"uberto","リスト名":"book","項目":{"説明":"write chapter"}}

    キーを改名しません。 改名すると過去の行が読めなくなります。キーの追加には強い形です。

    無いファイルは失敗ではない¶

    ●(保存先から)保管読出
    # 無いファイルは「まだ何も起きていない」。失敗ではない。
    もし、(保存先が存在)=偽ならば
        []で成功で戻る
    ここまで

    これは第 2 章の 空 と同じ形の判断に見えますが、違います。「無い」の意味が 1 つに定まっているからです。ファイルが無い = イベントが 1 件も起きていない = 空の並び。曖昧さがありません。

    保存先を準備する¶

    この節はマインドマップでは「データベースを準備する」です。データベースを使わないので読み替えました。

    起動時にファイルが無ければ、初期イベントを書き込みます。

    ●保管初期化
    # ファイルが無ければ初期イベントを書き込む。あれば何もしない。
    # 追記のみなので、2 度目の起動で種を足さない。
    道=保管パス
    もし、道が存在ならば
        真で成功で戻る
    ここまで

    2 度目の起動で種を足さないことが要です。追記のみなので、毎回足すとリストが二重になります。

    準備は以上です。マイグレーションもスキーマもありません。用意するものが少ないのは、ファイルの利点です。

    関数型スタイルでリモートデータにアクセスする¶

    つまずき 1: ポートを関数値で注入できない¶

    第 4 章から、アダプタは関数値で注入してきました。ハブに {関数}インメモリ取得 を渡す形です。永続化も同じにするつもりでした。

    できませんでした。

    3. 関数値ごし: 戻り=[object Promise] 型=object
   最終: []

    関数値ごしに呼ぶと、中のファイル I/O が待たれず Promise がそのまま返ります。 第 3 章で受け入れテストの HTTP 経路を作ったときと、まったく同じ制約です。

    副作用を端に寄せる¶

    回避策は同じでした。入出力をする関数を、注入される側から外します。

    # イベントログの保管。**このファイルだけが入出力をする。**
#
# なでしこ3 では関数値ごしに呼ぶと非同期の組み込み命令が待たれないため、
# 永続化のポートを関数値で注入できない（第 3 章と同じ制約）。
# そこで入出力をアダプタ層の端に寄せ、ドメインは「何を保存すべきか」を
# 返すだけにする。ポートは「注入される関数値」ではなく「呼び出しの順序」で表す。

    ポートという考え方は残ります。表し方が変わっただけです。

    第 4〜8 章 第 9 章
    ポートの表し方 注入される関数値 呼び出しの順序
    ドメインがすること アダプタを呼ぶ 何を保存すべきかを返す
    入出力の場所 アダプタの実装 store.nako3 1 ファイルだけ
    ドメインは保存先を知るか 知らない 知らない（変わらない）

    制約に押されて、ドメインはより純粋になりました。 第 3 章でも同じことが起きています。この言語は、副作用を端に寄せろと繰り返し言ってきます。

    モナドの力を探る¶

    つなぐ操作¶

    読み出して、畳み込んで、取り出す。どれも失敗しうる処理です。素直に書くとこうなります。

    読出=道から保管読出
もし、(読出の成功判定)=偽ならば
    読出で戻る
ここまで
射影=読出["値"]を射影畳込
取得=射影で利用者とリスト名の射影内リスト取得

    第 7 章で見た形です。「失敗だったらそのまま返す」が処理のたびに出てきます。

    第 7 章は 結果マップ でまとめました。しかしここでは使えません。射影内リスト取得 が返すのは値ではなく結果だからです。結果マップ でつなぐと、結果の中に結果が入った二重の箱になります。

    欲しいのは、結果を返す関数をつなぐ操作です。

    ●(結果にFを)結果連鎖
    # F は「値を受け取って結果を返す」関数。失敗はそのまま素通しする。
    # 結果マップ（ファンクタ）との違いは、F が結果を返すこと。
    # 失敗しうる処理をつなげる。これがモナド。
    もし、結果["成功"]=偽ならば
        結果で戻る
    ここまで
    F(結果["値"])で戻る
ここまで

    結果マップ との違いは 1 行だけです。 map は中身を包み直し、連鎖 は F が返した箱をそのまま使います。

    3 つの法則¶

    ファンクタの法則は 2 つでした。モナドは 3 つです。

    名前 言っていること
    左単位元 値を包んでから F をつなぐのは、F を直接呼ぶのと同じ
    右単位元 「包むだけの関数」をつないでも、何も変わらない
    結合律 どこから括ってつないでも、結果は同じ

    この 3 つが成り立つから、処理を好きな順に切り分けて並べられます。

      ok 左単位元が 200 回とも成り立つ
  ok 右単位元が 200 回とも成り立つ
  ok 結合律が 200 回とも成り立つ

    壊して確かめる¶

    第 5 章から続けているやり方です（ADR-017）。

    壊し方 左単位元 右単位元 結合律
    失敗も連鎖する（素通しをやめる） 0 58 / 200 0
    値を 1 足す 200 / 200 135 / 200 138 / 200

    1 行目が衝撃的です。 3 つの法則のうち、右単位元だけがこの壊れ方を見つけます。

    理由は考えれば分かります。

    • 左単位元は成功で始まるので、失敗の経路を一度も通りません
    • 結合律は両辺が同じように壊れるので、差が出ません
    • 右単位元だけが、失敗で始まる場合を含み、かつ片側だけが壊れます

    これまで見てきた検出率を並べます。

    構造 壊し方 検出しない法則
    ファンクタ（第 7 章） 失敗も map する 合成則
    ファンクタ（第 8 章） F を 2 回適用する 恒等則
    モナド（第 9 章） 失敗も連鎖する 左単位元と結合律

    法則が複数あるのは飾りではありません。 どの法則も、別の法則が見逃す壊れ方を捕まえます。数学の定義に「余計な条件」が並んでいるように見えるとき、たいてい余計ではありません。

    読み戻す¶

    書けたら、読み戻せることを確かめます。

    「2 件読み戻せる」と(事象列の要素数)と2で検証

    入れ子の辞書（項目）も JSON の往復で戻ります。

    そして本当の確認は、アプリケーションを落として起動し直すことです。

    $ make run
$ curl -s http://localhost:8080/todo/uberto/book
<html><body><h1>book</h1><ul><li>write chapter</li><li>insert code</li><li>publish book</li></ul></body></html>

    サーバを落とし、ファイルにイベントを 1 件足して、起動し直します。

    $ curl -s http://localhost:8080/todo/uberto/book
<html><body><h1>book</h1><ul>…<li>review draft</li></ul></body></html>

    足した項目が出ました。 状態をどこにも保存していないのに、画面が変わっています。イベントが唯一の事実であることが、目で見える形になりました。

    ３経路目¶

    第 3 章で、同じシナリオを 2 経路（ドメイン直接・HTTP 経由）で走らせる形を作りました。永続化が入ったので、3 経路目を足します。

    # 実行経路その 3: 永続化経由（第 9 章）。
# ファイルに書いてから読み戻す。同じシナリオが 3 経路で通れば、
# 永続化がドメインに漏れていない。

    シナリオは書き換えません。経路を差し替えるだけです。

      ok ドメイン直接: uberto は book の項目を 3 件見られる
  ok 保管経由: uberto は book の項目を 3 件見られる
  ok HTTP経由: uberto は book の項目を 3 件見られる

    3 経路が同じ結果になることが、永続化がドメインに漏れていない証拠です。 たとえば読み戻したイベントの順序が入れ替われば、保管経由だけが落ちます。

    代償もあります。シナリオを 1 つ足すと、確かめる箇所が 3 倍になります。 シナリオを増やすときの重みが上がりました。判断は ADR-020 に記録しました。

    つまずき 2: 既定の経路が変わるとテストが壊れる¶

    読む側の既定を保管経由にしたところ、HTTP のテストが落ちました。ファイルが無い状態でテストが走ったからです。

    # 第 9 章から既定の読む側は保管経由。テストは保管を用意して後で消す。
保管パスを保管消去
保管初期化

    用意して、後で消します。テストが環境に依存するようになりました。 これは永続化を入れた代償で、避けられません。避けられるのは「後始末をしないこと」だけです。

    まとめ¶

    • 保存するのはイベントだけです。 状態も射影もそこから作れます
    • データベースを使わず、1 行 1 JSON のファイルに追記しました。判断（状態を保存しない・追記のみ）は Kotlin 版と同じで、手段だけが違います
    • 追記の命令が無いので、読んで足して書き戻します。件数が増えると遅くなります。解かないことを ADR に書きました
    • ポートを関数値で注入できませんでした。 入出力を 1 ファイルに寄せ、ポートを「呼び出しの順序」で表しました。制約に押されて、ドメインはより純粋になりました
    • 失敗しうる処理をつなぐ操作がモナドです。結果マップ との違いは、F が結果を返すこと
    • モナド則は 3 つあり、どれも別の法則が見逃す壊れ方を捕まえます。 「失敗も連鎖する」は右単位元だけが見つけました
    • 3 経路目を足しました。同じシナリオが 3 経路で通ることが、永続化がドメインに漏れていない証拠です

    これで Phase 2 が終わります。次の章からは、文脈を持ち回る計算を扱います。Kotlin 版ではデータベースの接続が文脈でしたが、この版には持ち回る文脈がありません。 何を文脈と呼ぶかから考えます。
