    第 12 章 監視と関数型 JSON¶

    ここまで 11 章かけて Zettai を作りました。動きます。テストも 751 件通ります。

    しかし、動いているところを外から見る手段がありません。

    この章でそれを作ります。そして 7 つめの構造が現れます。

    アプリケーションを監視する¶

    テストは「こう動くはず」を確かめます。本番で起きるのは、テストが想定していないことです。

    第 7 章で失敗を結果辞書に載せました。しかし失敗を「返す」だけでは、誰も見ていません。 HTTP の応答として利用者に返るだけです。

    表示 を撒けば見えます。この版の 表示 は標準出力に出るので、動かしている間は読めます。

    足りないのは 2 つです。

    1. 後から読めない。 標準出力は流れていきます
    2. 機械が読めない。 「uberto の book を読みました」という文は、あとで数えられません

    人が読む文章ではなく、機械が読める形にします。

    ●(水準と事象と付帯で)記録作成
    # 付帯情報を先に写し、予約キー（時刻・水準・事象）を後から上書きする。
    # 逆にすると、付帯情報が予約キーを潰せてしまう。
    記録=付帯の辞書写し
    記録["時刻"]=今日&「 」&今
    記録["水準"]=水準
    記録["事象"]=事象
    記録で戻る
ここまで

    付帯情報を先に写し、予約キーを後から書きます。 逆にすると、呼び出し側が {"水準":"error"} を渡したときに予約キーを潰せてしまいます。型が無いので、この順序だけが約束です。契約テストで確かめます。

    上書き=「warn」と「X」と{"水準":"error"}で記録作成
「予約キーは付帯情報に負けない」と上書き["水準"]と「warn」で検証

    水準は 3 種類です。列挙型が無いので、第 6 章の状態と同じく一覧に集めます。

    ●記録水準一覧
    ["info","warn","error"]で戻る
ここまで

    構造化されたロギング¶

    1 行 1 レコードの JSON にします。

    ●(記録の)記録整形
    # 1 行 1 レコード。改行は入れない。
    記録をJSONエンコードで戻る
ここまで

    出力はこうなります。

    {"利用者":"uberto","時刻":"2026/09/28 20:31:05","水準":"info","事象":"保管読出","件数":5}
{"種別":"CreateToDoList","時刻":"2026/09/28 20:31:05","水準":"info","事象":"保管追記","件数":1}

    あとで grep も JSONデコード もできます。 テストも読み戻せます。

    書き出す場所を分ける¶

    記録の「形」と「書き出し」を別のファイルにしました。

    # **このファイルは記録の「形」だけを持ちます。** どこへ書くかは知りません。
# 書き出しは `log_sink.nako3` にあり、そちらが入出力をします。

    分けた理由は、この章の後半で嫌というほど効いてきます。

    JSON を関数型にする¶

    Kotlin 版はここで Converter を自前で書きます。JSON を作る処理が手書きだったので、それを双方向の型に育てるという話です（ADR-012）。

    この版は状況が違います。 第 9 章から組み込みの JSONエンコード / JSONデコード を使っています。

            行=事象列[I]をJSONエンコード

    Unit 6 のふりかえりで「『自前で書く』を惰性で続けない」と決めました。まず、組み込みで何が足りないかを確かめます。

    確かめたこと 結果
    入れ子の辞書・配列の往復 できる。再エンコードした文字列も一致する
    キーの順序 挿入順を保つ
    壊れた入力 例外を投げる（空を返さない）

    JSON そのものは足りています。 自前で書き直す理由はありません。

    それでも残る問題¶

    足りないのは 1 点だけです。

    書き出しと読み込みが別々の関数だと、片方だけ直して壊せます。

    第 11 章で ListRenamed を足したとき、store.nako3 の書き出しと読み込みの両方を直しました。忘れたら往復が壊れます。これは Kotlin 版 ADR-012 が挙げた問題とまったく同じ形です。 手書きかどうかは関係ありませんでした。

    そこで組み込みの上に層だけを置きます。

    ●(書出Fと読込Fで)変換作成
    # `{関数}` を辞書リテラルの中に直接書くと呼び出しになる（既知の制約 19）。
    # 呼び出し側で一度変数に受けてから渡す。
    {"書出":書出F,"読込":読込F}で戻る
ここまで

    書き出しと読み込みが 1 つの辞書に入りました。 片方だけ取り出して直すことはできます。しかし対であることが形に出ているので、直すときに目に入ります。型があれば「対である」をコンパイラが知りますが、ここでは辞書の形が知っています。

    イベント用の変換はこうです。

    ●事象変換作成
    書出F={関数}事象書出
    読込F={関数}事象読込
    書出Fと読込Fで変換作成で戻る
ここまで

    例外を境界で結果に変える¶

    JSONデコード は壊れた入力で例外を投げます。空を返しません。

    [実行時エラー].../src/step5/converter.nako3(78行目): SyntaxError: Unexpected token 'こ', "これは JSON ではない" is not valid JSON

    第 7 章で「例外をやめて結果辞書にする」と決めました。やめると決めたものが、組み込みの命令から降ってきます。

    捕まえます。

        # `JSONデコード` は壊れた入力で**例外を投げます**（既知の制約 24）。
    # 空を返しません。第 7 章で「例外をやめて結果辞書にする」と決めたので、
    # 境界のここで捕まえて結果に変えます。**捕まえる場所は 1 か所だけ**です。
    復元=空
    エラー監視
        復元=文字をJSONデコード
    エラーならば
        (「PersistenceError」で失敗)で戻る
    ここまで

    この版で エラー監視 を書いたのはここだけです。 例外を使わないと決めても、外から来る例外は捕まえる場所が要ります。その場所を 1 か所に絞れるかどうかが、決めたことを守れるかどうかです。

    保管も変換を通すようになりました。壊れた行は黙って捨てません。

                違えば
                # 壊れた行は落とさず数える。**黙って捨てない。**
                壊れ数=壊れ数+1

    プロファンクタとの出会い¶

    変換に 2 つの操作を足します。

    出力側は、書き出した結果を後から変えます。第 7 章の 結果マップ と同じ向きです。

    ●(変換にFを)変換出力写像
    # 出力側を後ろに足す（map）。書き出した結果に F を適用する。
    元書出=変換["書出"]
    新書出=関数(値)
        中間=元書出(値)
        F(中間)で戻る
    ここまで
    新書出と変換["読込"]で変換作成で戻る
ここまで

    入力側は向きが逆です。

    ●(変換にGを)変換入力写像
    # 入力側を前に足す（contramap）。読み込む前に G を適用する。
    # **向きが逆**なのがプロファンクタの肝。
    元読込=変換["読込"]
    新読込=関数(文字)
        中間=G(文字)
        元読込(中間)で戻る
ここまで

    読み込みは「文字列を受け取る」ので、足した関数は前に来ます。後から足したほうが先に効きます。

    出力側の map と入力側の contramap の両方を持つ構造をプロファンクタと呼びます。

    法則を確かめる¶

    第 5 章から同じやり方です。乱数で入力を作り、法則が成り立つかを 200 回試します。

    「プロファンクタの恒等則が {試行回数} 回とも成り立つ」と恒等失敗と0で検証
「出力側の合成則が {試行回数} 回とも成り立つ」と出力合成失敗と0で検証
「入力側の合成則が {試行回数} 回とも成り立つ」と入力合成失敗と0で検証

    入力側の合成は、向きが逆であることをそのままテストにしました。先に「空白を足す」を足し、次に「前後を除去」を足すと、後から足した除去が先に効いて汚れた入力が読めます。

        # 先に「空白を足す」を足し、次に「前後を除去」を足す。
    # 読み込みは**後から足したほうが先に**効く。
    段1=元3に空白Fを変換入力写像
    段2=段1に除去Fを変換入力写像

    壊してから信じる¶

    ADR-017 に従い、検出率を測ります。7 つめの構造です。

    まず、よくある間違い。「contramap を map と同じ向きに書く」。

      ok 取り違えた実装は 200 回とも検出される
検出率（出力側と入力側の取り違え・汚れた入力のみ）: 200 / 200

    200 / 200。ここまでで初めての全検出です。

    しかし法則が強いからではありません。 取り違えると「文字列用の関数を結果辞書に当てる」ことになり、結果が必ず食い違うだけです。Kotlin なら型エラーとして書いた時点で止まります。 ここでは走らせて 200 / 200 という形で現れます。

    もう 1 つ、もっと起こりやすい間違いを測ります。

        正5=(元5に空白Fを変換出力写像)に大文字Fを変換出力写像
    壊5=(元5に大文字Fを変換出力写像)に空白Fを変換出力写像

      ok 順序の取り違えは検出しない
検出率（出力側の合成順の取り違え）: 0 / 200

    1 回も検出しません。 「後ろに空白を足す」と「大文字にする」は順序を入れ替えても結果が同じ（可換）だからです。

    第 5・7・8 章と同じ結論です。法則が捕まえない壊し方は必ずあります。 7 つの構造で測ってきて、検出率が 0 になる組み合わせが出なかった構造はありません。

    保管の読み書きのロギング¶

    この節はマインドマップでは「データベース呼び出しのロギング」です。データベースを使わないので読み替えました（執筆計画 の規約）。

    ここで 1 時間つまずきました。

    最初に書いたもの¶

    保管の読み書きを記録したいので、store.nako3 の中に記録を入れました。自然な置き場所に見えます。

        出力を保存先へ保存
    「info」と「保管追記」と{"件数":(事象列の要素数),"保存先":保存先}を記録パスへ記録出力
    真で成功で戻る

    単体テストは通りました。受け入れテストが落ちました。

      FAIL undefined: uberto は book の項目を 3 件見られる: 値が違う 実際=1 期待=3
[実行時エラー].../test/step5/ddt/scenario.nako3(15行目): TypeError: Cannot read properties of undefined (reading '0')

    調べると、こうでした。

    列の型=object 値=[object Promise]
直接呼び=3 件

    直接呼べば 3 件。関数値ごしに呼ぶと Promise。

    5 度目の同じ制約¶

    既知の制約 1 です。第 3 章（HTTP）、第 7 章（結果を返す関数）、第 9 章（ファイル I/O）、第 10 章（ContextReader）に続いて 5 度目。

    今回は今までと違いました。これまでの 4 回は「最初から関数値ごしに入出力を呼ぼうとした」ケースです。 今回は違います。

    動いていた経路が、記録を足した瞬間に壊れました。

    保管読出 は受け入れテストの保管経由から関数値として呼ばれています。純粋ではないものの、読み込みだけなら待たれていました。そこに書き出し（記録）を足したので、Promise が返るようになりました。

    制約の一覧に 25 件目を足しました。

    関数値ごしに呼べるかどうかは「中で何を呼ぶか」で決まる。 既存の関数に書き出しを足すと、それまで注入できていた経路が壊れる。

    一覧を読んでいても防げませんでした。 制約 1 は知っていました。しかし「既にある関数に何かを足すと、その関数の呼ばれ方が壊れる」という形で現れるとは思っていませんでした。

    直し方¶

    記録を呼び出し側（tx.nako3）へ移しました。

    # 第 12 章: 記録はここに置く。**`store.nako3` には置けませんでした。**

    記録するかどうかは呼び出し側が決める、という形です。store.nako3 は読み書きだけをします。

    結果として、記録が業務の言葉で出るようになりました。保管の中に置いていたら「ファイルを N バイト書いた」しか書けません。

            「warn」と「コマンドの拒否」と{"種別":コマンド["種別"],"理由":判断["理由"]}を記録先へ記録出力

    制約に押されて動かした先が、設計としても正しい場所でした。 第 9 章と同じことが起きています。

    記録先も文脈が持つ¶

    もう 1 つ直しました。記録先を決め打ちにしていたので、並列に走るテストが同じファイルに書いて件数が混ざりました。

    第 10 章で決めた文脈は「どこを読み書きするか」でした。記録の行き先も同じ資格で入ります。

    ●(保管先と記録先で)文脈作成詳細
    {"保管先":保管先,"記録先":記録先}で戻る
ここまで

    テストが自分の記録先を持てるようになりました。文脈の定義を広げずに済んだのは、第 10 章で「接続」ではなく「どこを読み書きするか」と決めておいたからです。

    まとめ¶

    • 組み込みの JSON を捨てませんでした。 足りているものを組み直すのは、連載の主題ではありません（ADR-023）
    • 足りなかったのは「書き出しと読み込みが対であること」だけでした。手書きかどうかに関係なく、Kotlin 版と同じ問題が残っていました
    • エラー監視 を書いたのはこの章の 1 か所だけです。例外を使わないと決めても、外から来る例外は捕まえる場所が要ります。1 か所に絞れるかどうかが、決めたことを守れるかどうかです
    • プロファンクタの検出率は 200 / 200 と 0 / 200 でした。200 / 200 は法則が強いからではなく、型があれば書いた時点で止まる間違いだからです。可換な写像の順序入れ替えは 1 回も捕まえません
    • 記録を足した瞬間に、動いていた経路が壊れました。 既知の制約 1 の 5 度目で、一覧を読んでいても防げない形でした。「既にある関数に書き出しを足すと、その関数の呼ばれ方が壊れる」
    • 制約に押されて動かした先が、設計としても正しい場所でした。 記録は保管の中ではなくアダプタ層にあるべきで、そうしたら業務の言葉で記録が出るようになりました

    次が最終章です。13 章分の設計判断を並べ、Kotlin 版と対比します。型で保証するものと、約束とテストで保証するもの。 その違いを言葉にします。
