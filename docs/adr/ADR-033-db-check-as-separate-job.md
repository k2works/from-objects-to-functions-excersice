# ADR-033 DB を使う検査を別ジョブに分ける

日付: 2026-09-29

## ステータス

2026-09-29 提案されました

## コンテキスト

第 9 章で PostgreSQL を使います。**その検査をどこで走らせるか**を決めます。

Kotlin 版は [ADR-009](ADR-009-integration-test-database.md) で「**結合テストを `check` に含める。別ジョブに分けない**」と決めています。理由は「ローカルと CI で通る範囲を揃える」でした。

**同じ判断が Rust 版にも当てはまるかを、測ってから決めます。**

### 実測した

CI のサービスコンテナの代償は、**使い捨てのブランチで同じワークフローに 2 つのジョブを置いて**測りました（Unit 2 のゲート 1 と同じ手）。

| 測ったもの | 結果 |
| :--- | :--- |
| CI のサービスコンテナ | **DB 無し 3 秒 / DB 有り 25 秒（+22 秒）** |
| `postgres` の依存 | 7 → **67 クレート** |
| 依存の初回ビルド | **+95.47 秒**（一度きり） |
| `just check` 定常 | **足す前と変わらず**（7.48〜12.86 秒） |
| DB を使うテストの実行 | **0.37〜0.43 秒** |
| `docker compose up --wait` | 3.29 秒 |

**走らせるコストはほとんどありません。** 重いのは 2 つです。

1. CI のサービスコンテナ **+22 秒**
2. ローカルで **docker が要る**

## 決定

**DB を使う検査を `just check` に含めず、別立てにします。**

1. DB を使うテストは `db` フィーチャの裏に置く。`cargo test --all` では走らない
2. `just test-db` で走らせる。**docker が要る**
3. CI では `db` ジョブとして**並走**させる
4. **`just check-all` には入れる。** リリース前に忘れないため

```just
check-all:
    {{run}} just fmt lint test cov test-db

test-db:
    {{run}} cargo test -p zettai-step4-http --features db --test persistence
```

### Kotlin 版と結論が分かれた理由

**割合が違います。**

| 対象 | `check` の所要 | +22 秒すると |
| :--- | :--- | :--- |
| Kotlin | 95 秒 | 117 秒（+23%） |
| **Rust** | **26 秒** | **48 秒（+85%）** |

そして**別ジョブなら並走するので、総時間は増えません**。Rust 版の CI はすでに `check` と `parity` が並走しています。

**同じ ADR の題材でも、数字が違えば結論が変わります。**

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| `just check` と CI の両方に含める（[ADR-009](ADR-009-integration-test-database.md) を踏襲） | CI が 26 → 48 秒。**書いている間も docker が必須**になり、上げ忘れで `just check` が落ちる |
| CI だけに含める | **ローカルと CI で通る範囲が違う。** 「ローカルで通ったが CI で落ちる」が戻ってくる（Unit 1 で潰した問題） |
| DB を使わず、保管をファイルにする | なでしこ3 版と同じになり、**Kotlin 版との比較が効かなくなる** |

## 影響

- **書いている間は docker 無しで `just check` が回ります**（3.06〜4.41 秒）
- **CI の `check` ジョブは 26 秒 → 56 秒になりました。** サービスコンテナのせいではなく、`postgres` クレートの**コンパイル**です。`cargo test --all` はテストを走らせなくても依存をビルドします

| ジョブ | 所要（実測） |
| :--- | :--- |
| `fmt, clippy, test, coverage` | **56 秒** |
| 保管との往復 | 51 秒 |
| `parity` | 5 秒 |

  **「別ジョブなら総時間は増えない」は、サービスコンテナについては正しく、CI 全体については間違いでした。** 依存を足した時点で 30 秒は乗り、どの案でも同じです。並走した総時間（約 56 秒）は、含めた場合の見込み（26 + 22 + 30 ≒ 78 秒）より短いので判断自体は正しいままです
- CI のジョブが 3 つになります（`check` / `parity` / `db`）。**並走するので総時間は増えません**
- `parity` 検査の対象が 4 段 → 5 段になりました。**`justfile` の変数を一般に読む形にしてあった**ので、検査側の変更は不要でした（Unit 3 の持ち込み 6 の効き目）
- **ローカルと CI で通る範囲は揃っています。** どちらも `check-all` と同じ 5 段を走らせます

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| **`just check` だけ叩いて DB の検査を忘れる** | `check-all` に入れてありますが、**叩き忘れは止められません**。CI が止めます |
| CI のジョブが増え続けたとき | いまは 3 つです。**増えたら `parity` 検査の対象を広げるかを判断します** |
| ジョブの順序と `parity` 検査 | 検査は `check-all` の子レシピの順と workflow の `run:` の出現順を突き合わせます。**ジョブを並べ替えると落ちます**。落ちるのは正しいが、理由が分かりにくい |
| docker が無い環境 | `just test-db` が落ちます。**落ちたときのメッセージは `Unreachable { detail: "error connecting to server" }`** で、理由は分かります |

## コンプライアンス

- `just check` が docker 無しで通ること
- `check-all` に `test-db` が含まれていること
- `parity` 検査が `check-all` と CI の一致を見ていること
