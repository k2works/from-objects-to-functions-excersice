    Unit 4 の Bolt 終了報告 - Zettai 連載（Kotlin 版）¶

    基本情報¶

    項目 内容
    Unit Unit 4 コマンドとエラーハンドリング
    Bolt Bolt 4-1（第 6 章・コマンド）、Bolt 4-2（第 7 章・Outcome）
    期間 2026-09-27（計画は 2026-11-09 〜 11-20 の 2 週間）
    計画 Unit 4 の Bolt 計画
    局面 中盤（インサイドアウト）
    状態 完了（Deployment Unit として検証済み）

    この Unit の山の結果: 波及は 6 ファイル¶

    計画で「第 2 章から積み上げた設計が本当に変更を楽にしているかが試される」としていました。測定結果です。

    変わったもの（6 ファイル）¶

    ファイル 変更の内容
    domain/ToDoListHub.kt ポートの型定義、getList と handle の戻り値
    web/InMemoryToDoListFetcher.kt null を Failure に
    web/Zettai.kt ?: を fold に。404 / 400 の振り分けを追加
    domain/ToDoListHubTest.kt 期待値を Outcome に
    ddt/DomainOnlyActions.kt 戻り値の取り出しを fold に
    ddt/HttpActions.kt 同上

    変わらなかったもの¶

    変わらなかったもの 理由
    ドメインの型（ToDoList・ToDoItem・ToDoStatus） ポートを知らない
    イベントと状態の畳み込み（第 5 章） ポートを知らない
    モノイドのテスト 同上
    コマンドとステートマシン（第 6 章） 引数で状態を受け取るだけ
    遷移表とそのテスト 同上
    受け入れテストのシナリオ（SeeATodoListDdt・ToDoListOwner） 実装を知らない

    解釈¶

    「ポートの型が変わらなければ上のコードは変わらない」という説明は条件付きでした。 正確には次のとおりです。

    型が変われば、その型を触る場所だけが変わる。

    そして重要なのは、波及しなかった理由が「関数の型を使ったから」ではないことです。ドメインがポートを知らず、シナリオが実装を知らないからです。インターフェースで書いていても、同じ境界を引いていれば同じ結果になったはずです。

    記事にもこの解釈をそのまま書きました。設計を弁護せず、起きたことと、その理由を書くという方針に従いました。

    成果¶

    Bolt 4-1: コマンドと関数型ステートマシン（第 6 章）¶

    確認したい仮説: コマンドとイベントを分けることの利益を、「両方あると冗長では」という読者の当然の疑問に答える形で示せるか。

    結果: 示せた。違いを 1 点に絞れた。

    コマンドは拒否できますが、イベントは拒否できません。

    そこから「1 つのコマンドから 0 個以上のイベント」が導かれ、拒否と複数イベント生成の余地が説明できました。加えて代償（コード量が 2 倍、直感に反する、現在の状態を知るコスト）も表にして、「小さなアプリケーションなら上書きのほうが素直」と書きました。

    遷移表は 4×4 の 16 マスをすべてテストにし、表が 16 マスあること自体もテストしました。状態を 1 つ足して行と列を足し忘れたら落ちます。

    Bolt 4-2: Outcome によるエラーハンドリング（第 7 章）¶

    確認したい仮説: ポートの型が変わるという「これまでの前提が崩れる変更」を通して、積み上げた設計が実際に変更を楽にしているかを測れるか。

    結果: 測れた（6 ファイル）。上述のとおり、楽になった理由も正確に言語化できた。

    ファンクタの説明は、第 5 章のモノイドで機能した「構造 → 性質 → 名前 → 身の回りの例」の順序を再利用しました。List.map が同じ構造だと示すことで「知っていたことに名前が付いた」形にしました。圏論には踏み込まず、「法則を確かめて、使う」方針を明記しました。

    ゲートを場所で決めた判断の評価¶

    計画で「ゲート数を機械的に維持せず、エントロピー評価で MED に上がった原因にゲートを当てる」としました。結果は変更依頼 0 件です。

    ゲート数は Unit 2 の 11 から Unit 3 の 5、Unit 4 の 4 へ減っていますが、変更依頼は Unit 3・4 とも 0 件です。減らし方が正しかったと言えます。

    置いたゲート（4-2.2 ポートの型変更の方針）は実際に機能しました。段階的な置き換えの順序を先に決めたので、各段階で check を green に保てました。

    エントロピー評価の的中度¶

    評価軸 事前評価 実績 的中
    意図の曖昧さ LOW 迷いがなかった ○
    構造的不確実性 MED ポートの型変更で 6 ファイルに波及した。ゲートを置いた判断が効いた ◎
    検証の不確実性 MED 状態遷移の網羅性が MED とした理由。遷移表を先に作ったことで漏れなくテストできた ◎

    未解決の仮定 LOW 道具は検証済み。Outcome は自前 ○

    MED の 2 軸がいずれも当たり、どちらも対策（ゲート・遷移表）が効きました。

    判断と学び（ジャーナルへ転記）¶

    1. コンパイルが通ったから正しいとは限らない¶

    orElse をメンバー関数で書き、@UnsafeVariance を付けてコンパイルを通しました。実行すると ClassCastException が出ました。

    Failure<E> は Outcome<E, Nothing> なので、そこでは T = Nothing です。コンパイラは引数を Nothing にキャストするコードを生成します。Nothing にキャストできる値はありません。

    @UnsafeVariance は名前のとおり unsafe でした。拡張関数に切り出して解決しました。テストがあったので実行時に気づけました。

    2. 受け入れテストが表示の不足を教えてくれた¶

    第 6 章で status を動かしたとき、HTTP 経由の受け入れテストだけが落ちました。ドメイン直接の経路は通りました。

    原因は HTML に状態を表示していなかったことです。ドメインに状態があるのに画面に出ていない、という不整合でした。

    2 経路で実行していたから、原因が表示側だと切り分けられました。 1 経路だけなら「どこかがおかしい」で終わっていました。第 3 章で 2 経路を用意した価値が、ここで出ました。

    3. 表を先に作ると、判断の漏れが目に見える¶

    状態遷移をコードから書き始めると、when の分岐を書いたところで満足して、書いていない組み合わせに気づきません。

    4×4 の表を先に作ったところ、Todo → Blocked を許すかという判断が必要になりました。表にしなければ考えずに済んでいた判断です。

    表は「判断すべき箇所の一覧」でもあります。

    4. 引数を足すと呼び出し側の書き方が壊れることがある¶

    ハブに引数を 2 つ足したところ、末尾ラムダ ToDoListHub { ... } が persist に束縛されるようになりました。コンパイルエラーで気づき、名前付き引数に直しました。

    インターフェースなら起きない種類の問題です。 関数の型を使う設計の小さなコストとして記事に書きました。技法の利点だけを書くと、読者が実務で踏んだときに驚きます。

    次の Bolt¶

    Unit 5 のゲート密度: 密に戻す¶

    計画どおり密に戻します。 リリース計画 のエントロピー評価で、Unit 5 は「検証の不確実性 HIGH / リスク HIGH」です。

    理由 内容
    データベースの導入 docker-compose.yml への PostgreSQL 追加は確認必須（CLAUDE.md）
    結合テストの不安定さ ローカルと CI で安定して green になるかが未知
    永続化の設計 イベントをどう保存するか（イベントソーシング）の判断が要る
    ER 図の初回作成 データモデルの設計が初めて入る

    Unit 3・4 で疎にして変更依頼 0 件でしたが、それは「人が見ていた判断を機械に移せていたから」です。 Unit 5 で新しく現れる判断（DB スキーマ・結合テストの安定性）は、まだ機械に移せていません。減らしたまま突っ込みません。

    Unit 5 に持ち込む項目¶

    • zettai-step3-events モジュールを新設するか、zettai-step2-domain を続けて使うかを決める（章とモジュールの対応が 2 章ずれている）
    • 射影（domain/queries/）を新設する（第 8 章。アーキテクチャ設計 が第 8 章を初回作成としている）
    • docker-compose.yml に PostgreSQL を追加する（確認必須）
    • docs/design/data-model.md と ER 図を作成する（開発戦略 が Unit 5 を初回作成としている）
    • モナド則をプロパティベーステストで検証する（第 9 章。モノイド・ファンクタと同じ形）
    • 静的解析の導入を再検討する（ADR-004 が Unit 5 を再検討時期としている）
    • プロパティベーステストのライブラリ導入を再検討する（ADR-005 が Unit 5 を目安としている。法則が 3 種類になる）
    • 結合テストを check に組み込むかを決める（CI の実行時間との兼ね合い）

    再検討の予約が 2 件あります（ADR-004・ADR-005）。いずれも「入れない」と決めた判断で、条件を満たしたら見直すと書いていました。Unit 5 がその時期です。
