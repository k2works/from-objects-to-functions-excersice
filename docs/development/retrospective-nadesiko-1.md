## Problem（問題）

| # | Problem | 何が起きたか | 原因 |
| :--- | :--- | :--- | :--- |
| 1 | **計画が未検証の仮定を確定値として書いていた** | 執筆計画・リリース計画・Bolt 計画の 3 つに「Node 20」と書いた。実際は Node 22 以上が必要で、3 ファイルすべてを直した | 「Node 版だから Node 20 でよいはず」を、確かめずに計画本文に書いた。スパイクで確かめる項目としてではなく、決定として書いていた |
| 2 | **テストランナーが失敗を成功と数えた** | 取り込みエラーで落ちたテストを「2 本成功 / 0 本失敗」と表示した | cnako3 が実行時エラーでも終了コード 0 を返すことを、スパイクで見つけていながら**ランナーの実装に落とすときに半分しか反映しなかった**。`テスト結果報告` にたどり着かない失敗を考えていない |
| 3 | **1 言語目に書いた検査が 2 言語目で穴になった** | `check_adr_references.py` が章のディレクトリを `kotlin` 決め打ちにしていて、なでしこ3 の第 1 章を検査していなかった | 多言語シリーズを前提に設計したのは記事と実装の配置だけで、**検査スクリプトは 1 言語目の形のままだった** |
| 4 | **承認ゲートが 1 つも同期的に機能しなかった** | 計画では 10 箇所で人が止まるはずが、0 箇所だった | 計画の承認後に「Unit 1 を完了させる」という指示で連続実行した。**ゲートの運用形態（同期で止まるのか、事後にまとめて検証するのか）を計画に書いていなかった** |
| 5 | **人が検証に使った時間を計測できなかった** | Kotlin 版 Try 6 で主指標にしたのに、実績が空欄になった | Problem 4 の結果。同期的な検証が発生しなければ、計測する対象そのものが無い |

Problem 2・3 は同じ形です。**知っていたことを、作るものすべてに反映しきれていません。** 終了コードの問題はスパイクで見つけていたし、多言語シリーズであることは計画に書いていました。

## Try（次に試すこと）

| # | Try | 期待効果 | 期限・契機 |
| :--- | :--- | :--- | :--- |
| 1 | **計画に書く環境の値は「スパイクで確かめる項目」として書き、確定値として書かない**（Problem 1） | 計画が実物とずれない。ずれたときに直すファイルが減る | Unit 2 の Bolt 計画から |
| 2 | **新しい言語を足すときは、既存の検査スクリプトが言語決め打ちでないかを前提整備の項目に入れる**（Problem 3） | 2 言語目以降で検査に穴が開かない | 3 言語目を足すとき。本 Unit で `check_adr_references.py` は直した |
| 3 | **テストランナーを作った直後に「わざと壊したテストが FAILED になるか」を必ず確かめる**（Problem 2） | ランナー自身のバグを、テストを書き始める前に潰す | Unit 2（`doctest/` のランナーを書くとき） |
| 4 | **承認ゲートの運用形態を Bolt 計画に明記する**（Problem 4・5） | 「同期で止まる」「事後にまとめて検証する」のどちらかを先に決める。後者なら人の検証時間の計測方法も変わる | Unit 2 の Bolt 計画から |
