# ADR-035 複数の理由を集める型を別に作る

日付: 2026-09-29

## ステータス

2026-09-29 提案されました

## コンテキスト

第 11 章でリスト名の変更を作ります。**検証の規則が複数あり、同時に破れます。**

`Result` は最初の失敗で止まります。実測しました。

```text
assert_eq!(current("", TOO_LONG), Err(ZettaiError::EmptyUser));   // green
```

**理由が 1 つしか返りません。** 画面には全部出したいところです。

| 対象 | 作ったもの |
| :--- | :--- |
| Kotlin | `Validated`（アプリカティブ） |
| なでしこ3 | 検証結果（失敗を `理由列` 配列で持つ） |
| **Rust** | **これから決める** |

### 3 案を測った

`spikes/error-shapes/` で比べました。

| | A `Multiple` を足す | **B 別の型 `Validated<T>`** | C `Result<T, Vec<..>>` |
| :--- | :--- | :--- | :--- |
| 両方の理由が返るか | 返る | 返る | 返る |
| 行数 | 28 | **68** | **18** |
| 新しい型 | 0 | **1** | 0 |
| **既存の `match` が止まるか** | **止まる**（E0004） | 止まらない | 止まらない |
| `?` がそのまま通るか | 通る | 境界で `into_result()` | **通らない**（E0277） |
| **合わせる操作を書くか** | 不要 | **`zip`** | 不要 |

**3 案とも理由は 2 つ返ります。** 結果だけを見れば差がありません。

## 決定

**`Validated<T>` を別の型として作ります。**

1. `Valid(T)` と `Invalid(Vec<ZettaiError>)` の 2 枝
2. **`zip` で合わせる。** どちらも失敗なら理由を連ねる
3. `map` を持つ（ファンクタ）
4. **境界で `into_result()` して `Result` に戻す。** 溜めるのは検証の中だけ
5. 1 つの値に複数の規則をかけるときも `zip` を使う

### なぜ結果が同じなのに型を分けるのか

**「合わせる」操作が出てくるからです。**

案 A と案 C は、`if` を並べて `Vec` に push するだけです。**`zip` を書かないと、アプリカティブの法則（恒等・結合律・理由が落ちないこと）を確かめる対象がありません。**

そして `Result` と役割が分かれます。

| 型 | ふるまい |
| :--- | :--- |
| `Result` | 最初の失敗で止まる（モナド） |
| `Validated` | **理由を溜める**（アプリカティブ） |

**使い分けが型に出ます。**

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| A `ZettaiError` に `Multiple(Vec<Error>)` を足す | **合わせる操作が出てこない。** 加えて理由が入れ子になり、`Multiple(vec![Multiple(..)])` を作れてしまう。**ただし既存の `match` が止まる利点はあった**（E0004） |
| C `Result<T, Vec<ZettaiError>>` | いちばん小さい（18 行）が、**`?` が通らなくなる**（`From<Vec<E>>` が無い）。第 10 章の境界が書き換わる。理由が空の `Vec` を作れてしまう |
| 既製品（`validator` など） | **調べていません。** 要求は「理由を溜める」だけで、それは 68 行で書けます。**第 12 章で他の用途が出たら測ります** |

## 影響

- **`Result` と `Validated` を使い分けます。** 境界で戻すので、外からは `Result` に見えます
- `ZettaiError` に理由が 4 つ増えました（`EmptyUserName` / `EmptyListName` / `ListNameTooLong` / `ListNameHasMarkup`）。**状態コードに写す `match` がまた止まりました**（5 回目）
- **アプリカティブとモナドの差を数字で示せます**（下記）

### 測ったこと

| 測ったもの | 実測 | 期待値 |
| :--- | :--- | :--- |
| 両方だめな組 | 46 / 200 | 50（σ 6.12。**−0.65σ**） |
| **モナドが理由を落とした回数** | **46 / 200** | **両方だめな組と 1 対 1** |
| 壊した `zip` の検出 | 56 / 200 | 50（**+0.98σ**） |

**モナドが理由を落とすのは「両方だめ」のときだけ**です。片方だけなら結果が同じなので、**この型の存在理由は「両方だめな入力があること」に尽きます**。

200 回だから安定して捕まえられます。20 回なら期待値 5 で、**1 件以下に留まる確率が 2.43%** あります。

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| **`zip` が 3 つ以上のとき** | `zip` を重ねてタプルが入れ子になります。`(A, (B, C))` を `map` で平らにしています。**4 つを超えたら形を見直します** |
| 理由の順序 | 左から連ねます。**画面に出す順序を決めたい場合は別途** |
| `Validated` を境界の外に出すか | 出しません。**ポートの戻り値は `Result` のまま**です |
| 検証の規則をどこに書くか | いまはドメインの `validation.rs` に関数として並べています。**規則が増えたら組み立て方を見直します** |

## コンプライアンス

- `Validated` がポートの戻り値に現れないこと
- 検証の関数が `Validated` を返し、`Result` を返さないこと
- **「両方だめな入力」のテストがあること**（実物の値で）
