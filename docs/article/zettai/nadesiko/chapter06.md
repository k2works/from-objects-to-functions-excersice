# 第 6 章 コマンドを実行してイベントを生成する

## 新しいToDoリストの作成

第 5 章で、状態をイベントの畳み込みで作れるようになりました。ただし**イベントは初期データとして直接書いていました。**

```nako3
    書籍作成=「uberto」と「book」でリスト作成イベント
```

本当はそうではないはずです。誰かが「リストを作りたい」と思い、その求めが受け入れられて、はじめて「リストが作られた」という事実が生まれます。

**意図と事実は別のものです。**

| | 意図 | 事実 |
| :--- | :--- | :--- |
| 呼び方 | コマンド | イベント |
| 名前の形 | 命令形（リストを作れ） | 過去形（リストが作られた） |
| 拒否されるか | **される**（同名のリストが既にある、など） | されない。もう起きた |
| 保存するか | しない | **する** |

この章では、コマンドを受け取って、状態と突き合わせて、起きるべきイベントを決めます。

## コマンドを使って状態を変更する

コマンドも辞書です。3 つ用意します。

```nako3
●(利用者とリスト名で)リスト作成コマンド
    {"種別":"CreateToDoList","利用者":利用者,"リスト名":リスト名}で戻る
ここまで

●(利用者とリスト名と項目で)項目追加コマンド
    {"種別":"AddToDoItem","利用者":利用者,"リスト名":リスト名,"項目":項目}で戻る
ここまで

●(利用者とリスト名と説明と新状態で)状態変更コマンド
    {"種別":"ChangeItemStatus","利用者":利用者,"リスト名":リスト名,"説明":説明,"新状態":新状態}で戻る
ここまで
```

イベントとほとんど同じ形です。**違うのは名前と、拒否されうるかどうかだけ**です。

型のある言語なら、`ToDoListCommand` と `ToDoListEvent` は別の型です。渡し間違えればコンパイルが通りません。なでしこ3 ではどちらも辞書で、`種別` の中身が違うだけです。**渡し間違えても動いてしまいます。**

だから契約テストを置きます。

```nako3
作成=「uberto」と「book」でリスト作成コマンド
「リスト作成コマンドの種別」と(作成["種別"])と「CreateToDoList」で検証
```

## 状態とイベントによるドメインのモデリング

コマンドを処理するには、**今の状態を見る**必要があります。

- 「リストを作れ」→ 同名のリストが既にあれば拒否する
- 「項目を追加せよ」→ リストが無ければ拒否する
- 「状態を変えよ」→ その遷移が許されなければ拒否する

つまり `(コマンド, 状態) → イベントの並び` という関数です。**状態を書き換えません。** 何が起きるべきかを決めるだけです。

拒否をどう表すか。この章では**イベントが 0 件**で表します。

```nako3
# 拒否は「イベントが 0 件」で表す。第 7 章で失敗の理由を持つ結果に置き換える。
```

**これは暫定です。** 0 件では「なぜ拒否されたか」が分かりません。第 2 章で `空` を使ったのと同じ形の先送りです。第 7 章で直します。

## 関数型ステートマシンを記述する

### 遷移表を書き下す

状態は 4 つ（`Todo`・`InProgress`・`Done`・`Blocked`）。遷移の可否は 4×4 で 16 通りです。

```nako3
●遷移表
    {"Todo/Todo":偽,"Todo/InProgress":真,"Todo/Done":真,"Todo/Blocked":偽,"InProgress/Todo":偽,"InProgress/InProgress":偽,"InProgress/Done":真,"InProgress/Blocked":真,"Done/Todo":偽,"Done/InProgress":偽,"Done/Done":偽,"Done/Blocked":偽,"Blocked/Todo":偽,"Blocked/InProgress":真,"Blocked/Done":偽,"Blocked/Blocked":偽}で戻る
ここまで
```

読みやすくはありません。それでも**16 マスすべてを書き下しました。** 理由は次の節です。

```nako3
●(現状態から新状態に)遷移可否
    表=遷移表
    鍵=「{現状態}/{新状態}」
    もし、(表に鍵が辞書キー存在)=偽ならば
        偽で戻る
    ここまで
    表[鍵]で戻る
ここまで
```

### 16 マスすべてをテストする

Kotlin 版は `when` で書きます。`ToDoStatus` は `enum class` なので、**4 値のどれかを書き忘れればコンパイルが通りません。** 網羅がコンパイラに守られます。

なでしこ3 に列挙型はありません。書き忘れても何も起きません。

**代わりに 16 マス全件をテストします。**

```nako3
# 遷移表の 16 マスを全件テストする。
# 列挙型が無いので、Kotlin 版の when の網羅に相当する保証がない。
# 許す遷移だけを確かめると「常に許す」実装でも green になるため、
# 許さない 12 マスも明示して確かめる。
```

許す 5 マスだけを確かめても意味がありません。**「常に真を返す」実装でも green になる**からです。許さないマスも確かめて、はじめて表が表として働いていると言えます。

さらに、**組み合わせの網羅そのもの**も確かめます。

```nako3
# 4 値のすべての組み合わせが表にあること（書き忘れを検出する）
欠け=0
Iを0から(一覧の要素数)-1まで繰り返す
    Jを0から(一覧の要素数)-1まで繰り返す
        鍵=「{一覧[I]}/{一覧[J]}」
        もし、(遷移表に鍵が辞書キー存在)=偽ならば
            欠け=欠け+1
        ここまで
    ここまで
ここまで
「4 値の全組み合わせが表にある」と欠けと0で検証
```

第 4 章で作った `状態一覧` を使っています。**4 値の一覧と遷移表がずれたら落ちます。**

### 壊して確かめる

Unit 3 で覚えたやり方です。テストが通ったことは、テストが働いていることを意味しません。

| 壊し方 | 18 件中の失敗 |
| :--- | :--- |
| 遷移可否を「常に許す」に変える | **11 件** |
| 遷移表から `Blocked/Done` の 1 マスを消す | **2 件**（組み合わせの網羅テストを含む） |

どちらも落ちました。**「常に許す」で 11 件というのは、許さないマスを書いたおかげ**です。許すマスだけなら 0 件でした。

### 関数型ステートマシン

コマンドと状態から、起きるべきイベントを決めます。

```nako3
●(コマンドを状態で)コマンド処理
    種別=コマンド["種別"]
    利用者=コマンド["利用者"]
    リスト名=コマンド["リスト名"]
    既存=状態で利用者とリスト名の状態内リスト取得
    もし、種別=「CreateToDoList」ならば
        もし、既存≠空ならば
            []で戻る
        ここまで
        事象=利用者とリスト名でリスト作成イベント
        [事象]で戻る
    ここまで
```

純粋関数です。**状態を書き換えず、何も保存しません。** 「この状態でこのコマンドが来たら、これが起きるべきだ」と答えるだけです。

状態変更のときだけ、遷移表を引きます。

```nako3
        もし、(現状態から新状態に遷移可否)=偽ならば
            []で戻る
        ここまで
```

## ハブと接続する

第 4 章で作ったハブは、ドメインの入口でした。コマンドもここを通します。

```nako3
●(ハブでコマンドを状態に)ハブコマンド実行
    事象列=コマンドを状態でコマンド処理
    事象列で戻る
ここまで
```

**`ハブ作成` の引数は第 4 章から変えていません。** 入口が 1 つ増えただけです。

Kotlin 版はここでハブにアダプタを 2 つ足します（状態の取得と、イベントの保存）。**この版ではまだ足しません。** 保存先がインメモリのままで、保存するアダプタに意味がないからです。第 9 章で永続化が入るときに足します。

HTTP の層もまだ変えません。**この章の主題は「意図と事実を分ける」ことで、画面から操作できるようにすることではない**からです。画面に出すのは、失敗の理由を返せるようになってからにします（第 7 章）。

### つまずき: 助詞は 1 語として書く

`遷移可否` を最初こう定義して、`undefined` が返りました。

<!-- code-check: ignore わざと壊した書き方。直した形は上に載せている -->

```nako3
●(現状態から新状態への)遷移可否
```

`への` は助詞として認められません。`へ` か `に` です。定義は通ってしまい、**呼び出し側で引数が届かず `undefined` になりました。**

```bash
  FAIL Todo から InProgress は許す: 型が違う 実際=undefined 期待=boolean
```

検証関数が型を先に比べているので、`undefined` と `boolean` の違いとして出ました。**値だけを比べていたら「false が返った」ように見えて、遷移表のバグだと思い込んでいたはずです。** 第 1 章で入れた型の比較が、ここで効きました。

## コマンドとイベントを深く知る

この章で分けた 2 つを、もう一度並べます。

| | コマンド | イベント |
| :--- | :--- | :--- |
| 表すもの | これから起きてほしいこと | すでに起きたこと |
| 拒否 | される | されない |
| 数 | 1 つのコマンド | **0 個以上**のイベント |
| 保存 | しない | する |
| 冪等性 | 同じコマンドを 2 回送ると 2 回目は拒否されうる | 同じイベントを 2 回畳み込むと 2 回反映される |

「1 つのコマンドから 0 個以上のイベント」という点が要です。**拒否は「0 個」で表せます。** 逆に、1 つのコマンドが複数のイベントを生むこともありえます（この章ではまだありません）。

なでしこ3 で書いてみて分かったのは、**この区別が型ではなく規律で保たれている**ことです。コマンドもイベントも辞書で、`種別` の文字列が違うだけです。間違えて「コマンドを畳み込む」コードを書いても動いてしまいます。守っているのは、名前（`コマンド` / `イベント`）と、契約テストと、ファイルの分け方だけです。

**Kotlin 版はこれを型で分けています。** 型の無い言語では、同じ区別を人が守る側に回ります。

## まとめ

- **意図（コマンド）と事実（イベント）は別のものです。** 命令形と過去形、拒否されるかどうか、保存するかどうかが違います
- コマンド処理は `(コマンド, 状態) → イベントの並び` の純粋関数です。**状態を書き換えず、何も保存しません**
- 拒否は**イベント 0 件**で表しました。**なぜ拒否されたかが分からない暫定**です。第 7 章で直します
- 列挙型が無いので、`when` の網羅に相当する保証がありません。**遷移表の 16 マス全件をテストして代えました**
- 許すマスだけを確かめても意味がありません。「常に許す」実装でも green になります。**許さないマスを書いたから、壊したときに 11 件落ちました**
- `への` は助詞ではありません。定義は通り、呼び出しで `undefined` になります。**型を先に比べる検証関数がこれを捕まえました**

次の章では、拒否の理由を返せるようにします。「0 件だった」ではなく「同名のリストが既にある」と言えるようにします。そのために、成功か失敗かを持つ値を作ります。そしてその値に `map` を定義すると、**ファンクタ**という構造が現れます。
