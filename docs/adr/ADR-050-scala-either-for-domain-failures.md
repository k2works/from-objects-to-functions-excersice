# ADR-050 Scala 版は業務の失敗を Either で運び、IO の失敗は想定外の失敗に限る

日付: 2026-11-02

## ステータス

提案（人の承認待ち）

## コンテキスト

第 7 章で、失敗を値として運ぶ手段を決めます。Scala と Cats Effect には、候補が 2 つあります。

| 手段 | 型の例 | 失敗の見え方 |
| :--- | :--- | :--- |
| `Either` で運ぶ | `IO[Either[ZettaiError, ToDoList]]` | 型に失敗の種類が現れる |
| `IO` の失敗（例外）で運ぶ | `IO[ToDoList]`（`raiseError`） | 型には現れない。他の例外と区別がつかない |

既存の対象の手段は次のとおりです。

| 対象 | 手段 |
| :--- | :--- |
| Kotlin | 自作の `Outcome` |
| Kotlin FP | Arrow の `Either` |
| Rust | 標準の `Result` |
| Flix | 標準の `Result`（[ADR-047](ADR-047-flix-use-standard-result.md)） |

### 確かめたこと

| 項目 | 結果 |
| :--- | :--- |
| `Either` の `map` が恒等則と合成則を満たすか | 端の値（`Int` の最小値と最大値）と 4 種類の失敗を含む 8 つの値で満たす |
| 法則のテストが壊れた `map` を見分けられるか | 成功値に関数を 2 回当てる `map` で、恒等則は通り、合成則は落ちる |
| `Hub.getList` の戻り値を `Option` から `Either` に変えたときの波及 | 本番コード 3 ファイル（`Hub`、`View`、`ZettaiRoutes`）。既存のテストは 1 つも書き換えが要らず、`ZettaiRoutesSuite` には失敗の理由を確かめる検査を足した |
| 両方式の差 | `Either` で運ぶと、業務の失敗は `IO` の成功の中の `Left` として残る（`attempt` は `Right(Left(...))`）。例外で運ぶと、`attempt` は `Left(ZettaiException(...))` になり、型の上では `Throwable` の一種になる |

### 確かめていないこと

- `EitherT` で `IO[Either[E, A]]` の連鎖を短く書くこと。第 9 章以降で、`IO` と `Either` を重ねた連鎖が長くなったときに検討する
- `Either` 以外の標準の操作（`traverse` や `leftMap`）の法則

## 決定

1. **業務上ありうる失敗（`ZettaiError`）は、標準の `Either` で運ぶ。`Either` を自作しない**
2. **`IO` の失敗（例外）は、想定外の失敗に限る。** 接続が切れた、メモリが足りない、のような、呼び出し側が型で場合分けしない失敗
3. 失敗側の型 `ZettaiError` は自作する。`Either` は入れ物であって、業務上ありうる失敗の集合までは与えない
4. 失敗を HTTP のステータスに写す関数は、全ケースを列挙する `match` で書く

### 採った理由

- **失敗の種類が型に現れる。** `Either[ZettaiError, A]` は、どんな業務の失敗がありうるかを、呼び出し側のコンパイル時に示す
- **足し忘れがコンパイルで見つかる。** `ZettaiError` にケースを足すと、写像の `match` が `-Werror` の下で止まる
- **標準にある。** 追加の依存も、自作の型も要らない
- **他の対象と同じ形で比較できる。** Kotlin FP 版（`Either`）、Rust 版・Flix 版（`Result`）と同じ立場

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| `IO.raiseError` で業務の失敗を運ぶ | 型に失敗の種類が現れず、他の例外と区別がつかない。受け取る側が型を戻す処理を毎回書く |
| `Either` を自作する | 標準にあり、必要な操作がそろっている。自作する理由がない |
| `EitherT` を最初から使う | 今は連鎖が短く、読み手に要る知識が増える。必要になったら入れる |

## 影響

- `Hub.getList` の戻り値は `IO[Either[ZettaiError, ToDoList]]` になる
- 第 9 章で保存の失敗を足すとき、`StorageFailure` を `ZettaiError` に足すか、`IO` の失敗に任せるかを再び判断する。保存先の接続エラーは「想定外の失敗」に当たるので、`IO` の失敗に寄せる見込み。ただし、応答の本文に理由を出さない（Flix 版で見つけた情報漏えいと同じ穴を作らない）
- 応答の本文は、現時点では `ZettaiError` の文字列表現をそのまま返す。利用者名とリスト名しか入っていないので漏れはない。第 9 章で失敗の種類が増えるとき、本文に出す内容を見直す

### この決定が解かないこと

| 解かないこと | どうするか |
| :--- | :--- |
| 複数の入力の誤りをまとめて返すこと | `Either` は最初の失敗で止まる。第 11 章で `Validated` を使う |
| `IO` と `Either` を重ねた連鎖の短さ | `EitherT` を第 9 章以降で検討する |
| 想定外の失敗をどこで捕まえるか | 第 12 章のログと合わせて決める |

## コンプライアンス

- 業務上ありうる失敗は `IO.raiseError` で運ばないこと
- `ZettaiError` にケースを足したとき、`statusOf` が `match` の漏れでコンパイルエラーになること
- 応答の本文に、接続先・SQL・例外のメッセージを出さないこと
