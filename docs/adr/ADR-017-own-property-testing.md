# ADR-017 性質テストを自作し、検出率を測ってから信用する

日付: 2026-09-28（判断は第 5 章・Unit 3 で下した）

## ステータス

2026-09-28 提案されました

**この ADR は事後の記録です。** 判断は Unit 3（第 5 章）で下しましたが記録しておらず、Unit 4 の Kotlin 版 ADR の棚卸しで漏れとして見つかりました。

## コンテキスト

連載は第 5 章からモノイド・ファンクタ・モナド・アプリカティブ・プロファンクタを扱います。いずれも「ある法則を満たす」ことが定義です。**例示のテストでは法則の成立を示せません。** `f`・`g`・`h` を 1 組だけ試して通っても、法則が成り立つとは言えません。

Kotlin 版はプロパティベーステストを自前で書き、kotest-property を導入しませんでした（[ADR-005](ADR-005-property-based-testing.md)）。なでしこ3 にはそもそも該当するライブラリがありません。

## 決定

**性質テストを自作します。** 加えて、**法則を破って落ちることを確かめるまで、そのテストを信用しません。**

1. `test/stepN/helper.nako3` に土台を置く
   - `乱整数`: `Nの乱数`（0 以上 N 未満）を範囲つきに直したもの
   - `比較用文字列`: 辞書どうしを比べる手段が無いので JSON にして比べる
2. 入力だけでなく**適用する対象も乱数で作る**。空の状態だけで試すと、法則が成り立って見えることがある
3. 試行回数は `make check` が 30 秒に収まる範囲で決める。現在 **200 回**
4. **法則を破る実装を入れて、何件落ちるかを測る。** 検出率を Bolt 終了報告に記録する
5. 記事に書いた試行回数を `check_numbers.py` が実装の宣言と突き合わせる

### 検出率の実測

| 法則 | 壊し方 | 200 回中の検出 |
| :--- | :--- | :--- |
| モノイドの結合律 | 合成を非結合的にする | **13** |
| モノイドの結合律 | 合成の順序を逆にする | 0（**正しい。順序を変えても結合律は成り立つ**） |
| モノイドの単位元 | 恒等変換が状態を変える | 100 |
| ファンクタの恒等則 | 失敗も `map` してしまう | 104 |
| ファンクタの恒等則 | `map` が値を 1 足す | 96 |
| ファンクタの合成則 | `map` が値を 1 足す | 94 |

**結合律の検出率だけが際立って低い**のは、ランダムに選んだ変換の多くが別の利用者・別のリストを触り、順番を変えても結果が変わらないためです。**20 回なら見逃していました。**

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| 例示のテストで済ませる | 法則の成立を示せない。「1 組で通った」は反例が無いことを意味しない |
| 試行回数を 1000 回以上にする | `make check` が 30 秒を超える。段階ごとのディレクトリ（[ADR-015](ADR-015-step-directories.md)）で全段階を回すため、時間の余裕が少ない |
| 検出率を測らず green を信用する | **Unit 3 で実際に、順序を逆にする壊し方が結合律で検出されないことが分かった。** 測らなければ「テストが弱い」と「壊し方が法則を破っていない」を区別できない |

## 影響

- **性質テストを追加するたびに、壊す作業がセットで必要になります。** 手間は増えますが、Unit 3・4 とも実際に気づきを得ました
- 検出率が低い法則は、入力の多様性を上げる余地があると分かります
- 記事に書く試行回数がずれたら CI が落ちます

## コンプライアンス

- 新しい性質テストを足したら、**法則を破って検出率を測り、Bolt 終了報告に記録する**
- 記事に書いた試行回数が実装の宣言と一致すること（`check_numbers.py`）
- `make check` が 30 秒以内であること

## 再検討の条件

1. なでしこ3 にプロパティベーステストのライブラリが現れる
2. 検出率の低い法則（結合律）で、実際に見逃した欠陥が見つかる
3. `make check` が 30 秒を超え、試行回数を減らす必要が出る
