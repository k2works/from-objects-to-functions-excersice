# 第 8 章 ファンクタを使ってイベントを射影する

## イベントを射影する

画面に出しているのは、リスト名と項目の説明だけです。

```text
<h1>book</h1><ul><li>write chapter</li>…</ul>
```

ところが、画面に渡している値は違います。

| 持っているもの | 画面で使うか |
| :--- | :--- |
| リスト名 | **使う** |
| 項目の説明 | **使う** |
| 項目の期限 | 使わない（第 4 章で足した） |
| 項目の状態 | 使わない（第 4 章で足した） |

**表示に要らないものを、表示のために持ち回っています。**

第 6 章で状態遷移を実装したので、これから項目の状態は増える一方です。画面が増えれば、必要な形も画面ごとに変わります。**「業務のルールを守るための形」と「画面に出すための形」を、同じ 1 つの形で兼ねるのに無理が出てきます。**

### もう 1 つの畳み込み先

第 5 章で、状態はイベントの畳み込みで作ることにしました。**畳み込む先は 1 つでなくてかまいません。**

```nako3
●空射影
    {"表":{}}で戻る
ここまで
```

同じイベント列を、表示のための形に畳み込みます。

```nako3
            新表[鍵]={"リスト名":イベント["リスト名"],"説明列":[]}
```

`説明列` は文字列の配列です。**期限も状態も持ちません。** 項目の状態が変わっても、画面の見た目は変わらないので、射影は何もしません。

```nako3
    # 状態の変更は表示に影響しない。射影は説明しか持たない。
    恒等射影変換で戻る
```

第 5 章で作った `恒等変換` と同じ形が、ここでも出てきました。**何もしない変換があると、「この種類のイベントは関係ない」を素直に書けます。**

## ファンクタに対するクエリの実行

射影から 1 つのリストを取り出します。第 7 章で作った結果を返します。

```nako3
●(射影で利用者とリスト名の)射影内リスト取得
    表=射影["表"]
    鍵=「{利用者}/{リスト名}」
    もし、(表に鍵が辞書キー存在)=偽ならば
        敗=「ListNotFound」で失敗
        敗で戻る
    ここまで
    表[鍵]で成功で戻る
ここまで
```

**第 7 章とまったく同じ形です。** 見つからなければ理由を持った失敗、見つかれば成功。呼ぶ側は結果の扱い方を 1 つ覚えれば済みます。

そして射影にも `map` を足します。

```nako3
●(射影にFを)射影マップ
    # 箱の中身（各リストの説明列）に F を適用し、外側の形は変えない。
    # 第 7 章の結果マップと同じ形。これもファンクタ。
```

## ファンクタの観点から考察する

第 7 章で結果に `map` を作りました。この章では射影に `map` を作りました。**形が同じです。**

| | 結果（第 7 章） | 射影（第 8 章） |
| :--- | :--- | :--- |
| 箱 | 成功か失敗か | 利用者とリストの表 |
| 中身 | 成功のときの値 | 各リストの説明列 |
| `map` がすること | 中身に関数を適用する | 同じ |
| 外側 | 成功／失敗は変えない | 表の鍵とリスト名は変えない |

**同じ形をしたものに同じ名前を付けると、次に会ったときにすぐ分かります。** これがファンクタに名前が付いている理由です。

### 性質を確かめる

法則は第 7 章と同じ 2 つです。恒等則と合成則。

```bash
  ok 射影の恒等則が 200 回とも成り立つ
  ok 射影の合成則が 200 回とも成り立つ
```

そして壊します（[ADR-017](../../../adr/ADR-017-own-property-testing.md)）。

| 壊し方 | 恒等則 | 合成則 |
| :--- | :--- | :--- |
| `map` が外側の形を変える（リスト名に文字を足す） | **164 / 200** | **163 / 200** |
| `map` が F を 2 回適用する | **0** | **78 / 200** |

**2 つ目が重要です。** F を 2 回適用しても、恒等則では検出できません。「そのまま返す関数」を 2 回適用しても、結果は変わらないからです。

第 7 章では逆でした。「失敗も `map` してしまう」壊し方は、恒等則で 104 件・合成則で 0 件です。

| 壊し方 | 恒等則 | 合成則 |
| :--- | :--- | :--- |
| 失敗も `map` してしまう（第 7 章） | 104 | **0** |
| F を 2 回適用する（第 8 章） | **0** | 78 |

**きれいに逆になっています。片方の法則だけでは、もう片方が見つける壊れ方を見逃します。** 法則が 2 つあるのは、飾りではありません。

### つまずき: 破壊的な命令が法則を壊す

合成則のテストを書いたとき、最初は落ちました。

```bash
  FAIL 射影の合成則が 200 回とも成り立つ: 値が違う 実際=106 期待=0
```

原因は `map` ではなく、**`map` に渡した関数**でした。

<!-- code-check: ignore わざと壊した書き方。直した形は下に載せている -->

```nako3
●(列で)逆順化
    列を配列逆順で戻る
ここまで
```

`配列逆順` は破壊的で、**元の配列を書き換えます。** `map` に渡した関数が引数を書き換えると、比較の元になる射影まで変わってしまい、法則が成り立たなくなります。

```nako3
●(列で)逆順化
    # 配列逆順 は破壊的で、元の配列を書き換える。
    # map に渡す関数が引数を書き換えると、ファンクタ則が成り立たない。
    写=列を配列複製
    写を配列逆順で戻る
ここまで
```

**ファンクタ則は「`map` が正しいこと」だけでなく、「渡す関数が純粋であること」も前提にしています。** 型のある言語なら不変なコレクションを使えば防げますが、この版では約束で守ります。

法則が破れたとき、**疑う先が 2 つある**ということです。

## コマンドクエリ責務分離(CQRS)

射影ができたので、入口を分けます。

```nako3
# --- クエリ側のハブ（第 8 章） ---
# 読む側は射影しか知らない。全体の状態を見ない。
# 書く側（ハブ作成・ハブコマンド実行）とは入口が別になる。

●(射影取得Fで)クエリハブ作成
    {"射影取得":射影取得F}で戻る
ここまで
```

第 4 章のハブと同じ形です。**アダプタを関数値で受け取ります。** 違うのは受け取るものが「全体の状態を見るアダプタ」ではなく「射影を見るアダプタ」であることだけです。

HTTP の層は読む側なので、クエリハブを使います。

```nako3
    # 読む側なのでクエリハブを使う。全体の状態を見ない。
    ハブ=既定クエリハブ作成
    取得=ハブで要素[1]と要素[2]のクエリリスト取得
```

HTML を描く関数も、射影を受け取るようになりました。

```nako3
●(見えるリストの)HTML描画
    # 第 8 章から、描くのは射影。表示に要らないものを持たない。
```

**これが CQRS（コマンドクエリ責務分離）です。** 書く側と読む側で、必要なものが違うので、入口も形も分けます。

| | 書く側 | 読む側 |
| :--- | :--- | :--- |
| 入口 | `ハブ作成` → `ハブコマンド実行` | `クエリハブ作成` → `クエリリスト取得` |
| 見るもの | 全体の状態（業務のルールを守るため） | 射影（表示のため） |
| 元になるもの | **同じイベント列** | **同じイベント列** |

**同じイベントから、違う形を作っているだけです。** 分けたのは形であって、真実は 1 つです。イベント列が唯一の事実で、状態も射影もそこから導かれます。

### 分けて何が楽になったか

画面に出す項目を変えたくなったとき、**射影だけを変えれば済みます。** 業務のルール（どの遷移を許すか）には触りません。

逆に、状態遷移の規則を変えても、**画面は影響を受けません。** 射影は状態を持たないからです。

型のある言語なら、この分離は型が違うことで目に見えます。この版では**辞書のキーが違うこと**（`項目` と `説明列`）と、**ファイルが分かれていること**（`events.nako3` と `projection.nako3`）で示します。契約テストが両方のキーを守ります。

## まとめ

- **畳み込む先は 1 つでなくてかまいません。** 同じイベント列から、業務のための形と表示のための形を作れます
- 射影の `map` も**ファンクタ**です。第 7 章の結果と形が同じなので、名前を共有します
- **法則は 1 つでは足りません。** 「F を 2 回適用する」は恒等則で 0 件、合成則で 78 件。第 7 章の「失敗も map してしまう」は逆でした
- ファンクタ則は「`map` が正しいこと」だけでなく「**渡す関数が純粋であること**」も前提にします。破壊的な `配列逆順` が法則を壊しました
- **CQRS は、同じイベントから違う形を作ることです。** 分けたのは形であって、真実はイベント列 1 つです

次の章では、そのイベント列をファイルに保存します。アプリケーションを落としても消えないようにします。そして「失敗しうる処理をつなぐ」操作に、**モナド**という構造が現れます。
