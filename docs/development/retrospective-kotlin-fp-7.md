# Unit 7 のふりかえり（KPT）- Zettai 連載（Kotlin FP 版）

## Keep

- 計画を、実装に入る前に独立した読み取り専用の検証にかけました。実在しない関数名（`Request.listKey()`）、承認済みの ADR-040 との衝突、漏れていた持ち越し 2 件、横断比較の構造の誤解が、着手前に直りました。
- 新しい依存は、使い捨てのスパイクで確かめてから、人の承認を得ました。版、特殊文字の往復、壊れた入力の挙動が、推測ではなく実測でした。
- 承認済みの ADR と衝突したとき、置き換えず、用途を分けて新しい ADR で足しました。
- 載せるものを型で決める設計が、5 観点レビューで「機密が混ざる経路が構造上無い」と評価されました。
- テストが効くかを、実装を壊して確かめました。request の path に query を含める変更で、期待したテストが失敗しました。
- 第 13 章の主張に、対応するテスト名か「無い」を要求したので、確かめていないこと（検出率、ログの枠組みとの比較）を、本文に書けました。
- レビューを受けて、行数の数え方が再現できないこと（末尾の改行）や、「承認済み」と書いた根拠が未承認の ADR だったことを、公開前に直せました。
- Unit 6 のふりかえりの Try（出力の `BUILD` 行を確認する、Gradle の実行場所を固定する、`sealed` の制約を先に確かめる、期待値を数えず入力から導く）を計画に入れ、それぞれ守れました。

## Problem

- 同じ種類の間違いを、また踏みました。コマンド中の連続したバックスラッシュが畳まれる環境で、Kotlin の文字列リテラルを含むスクリプトが壊れました（`\\` が `\` になる）。Write ツールでファイルを作る方法に切り替えて避けましたが、最初の数回は気づかずに実行しました。
- Gradle を誤ったディレクトリで実行し、出力が空だったことが 3 回ありました。Try で決めたのに、`cd` を連鎖させる書き方を続けたためです。
- 置き場所を 2 回間違えました。request の filter を adapter に置いて、既存の境界テストに拒まれました。`zettai.app` の前置一致が `zettai.application` に当たって、境界テストが誤って失敗しました。
- 法則のテストの向きを逆に書いて失敗させました（右辺は、先に `dimap f k`、次に `dimap g h`）。実装の誤りではありませんでした。
- 初版の決定「例外は記録しない」は、例外が投げられた操作がログから消えるので、運用では使えませんでした。5 観点のうち 3 つが指摘しました。書いた時点で、運用者の目で読み返していませんでした。
- decorator を足したのに、本番の組み立てに配線する箇所がありませんでした。連載に起動する `main` が無いからで、組み立ての関数を作るまで、誰も気づきませんでした。
- 第 13 章の数値（行数）が、再現できない数え方でした。末尾の空要素を含めて数えていました。
- 横断比較で、他の 3 版が行った「法則を壊して検出率を数える」を、この版は行いませんでした。比べる軸が 1 つ欠けました。
- 実装の途中で、計画の書き方も食い違いました。計画の「Request.listKey()」は、前の Unit のレビューの表現をそのまま引き写したものでした。

## Try

- 連載を終えた後の持ち帰りとして、次の運用を残します。
  - 外部に見える設計（ログ、エラー応答）は、書いた直後に、運用者の目で読み返す
  - 新しい decorator や filter を足したら、本番の組み立て箇所と、それを通す結合テストを同時に作る
  - 数値を記事に書くときは、数え方（コマンド）を本文か注に残す
  - 比べる軸（検出率など）は、章の計画の時点で、やる・やらないを決めて書く
- ファイルを書き換えるスクリプトは、Write ツールで作る。バックスラッシュを含む文字列を、コマンド中に直接書かない。
- Gradle の実行は `apps/kotlin-fp/zettai` に固定し、`BUILD` の行が無ければ失敗として扱う（Unit 6 の Try を継続）。
- 前置一致で判定する検査（import の文字列）は、前置が別の語の一部に当たらないか、`.` を付けて確かめる。
- 新規の決定が承認済みの ADR と矛盾するときは、計画の段階で、見直す範囲を比較表にして、停止点に出す（今回、有効だった）。
