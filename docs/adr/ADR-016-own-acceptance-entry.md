# ADR-016 受け入れテストの入口を自作し、ライブラリに寄せない

日付: 2026-09-28（判断は第 3 章・Unit 2 で下した）

## ステータス

2026-09-28 提案されました

**この ADR は事後の記録です。** 判断は Unit 2（第 3 章）で下しましたが記録しておらず、Unit 4 の [Kotlin 版 ADR の棚卸し](../development/iteration_plan-nadesiko-4.md) で漏れとして見つかりました。

## コンテキスト

第 3 章の主題は、受け入れテストを「画面を叩く手順」から「業務の言葉」に移すことです。Kotlin 版は自作した DDT の構造を **Pesticide** というライブラリに載せ替えました（[ADR-002](ADR-002-ddt-pesticide.md)）。構造に名前が付き、維持する対象が減るからです。

**なでしこ3 には載せ替える先がありません。** 受け入れテストの枠組みを提供するライブラリが存在せず、テストフレームワーク自体が無い（[ADR-014](ADR-014-own-test-framework.md)）状態です。

加えて、言語の制約が 2 つ効きました。

- **関数値ごしに呼ぶと、中の非同期な組み込み命令が待たれず Promise がそのまま返る**
- **テストの中からサーバを起こすと親プロセスが返らない**

## 決定

**受け入れテストの入口を自作します。** ライブラリを使わない判断ではなく、使えるものが無いという事実への対処です。

1. シナリオは業務の言葉だけで書き、`test/stepN/ddt/scenario.nako3` に置く
2. 実行経路は**関数値を詰めた辞書**（操作の一覧）で差し替える。`actions_domain.nako3`（ドメイン直接）と `actions_http.nako3`（HTTP 経由）
3. **シナリオに渡す関数は入出力をしない。** HTTP 経由の経路は応答を先に記録し、シナリオが呼ぶ関数は記録を引くだけにする
4. サーバの起動と停止は `Makefile` が持つ
5. 同じシナリオが 2 経路とも green であることを、ドメインとインフラストラクチャが分離できた証拠とする

### ライブラリが提供するものを、何で代えたか

| ライブラリがやってくれること | 自作でやったこと |
| :--- | :--- |
| シナリオと実行経路を分ける枠組み | 操作の辞書。キーが操作の一覧、値が関数値 |
| 複数の経路で同じシナリオを回す | 経路ごとに `操作作成` を用意してシナリオに渡す |
| 結果の集計と報告 | `検証` と `テスト結果報告`（[ADR-014](ADR-014-own-test-framework.md)） |
| 置き場所の規約 | `test/stepN/ddt/` に集める |

### 検討した代替案

| 案 | 採らなかった理由 |
| :--- | :--- |
| JavaScript のテストフレームワーク（Jest など）から呼ぶ | なでしこ3 で書いた実装をなでしこ3 でテストする、という連載の前提が崩れる。読者が追えなくなる |
| 経路を 1 つ（ドメイン直接）に絞る | 分離できたことを確かめる手段が無くなる。第 3 章の主題そのものが失われる |
| シナリオに入出力をさせ、非同期を諦める | Promise がそのまま返り、テストが常に green になる。**確かめていないテストは有害** |

## 影響

- **枠組みを自分で維持します。** 壊れたら自分で直します。Kotlin 版が「やめるときに捨てるものが少ないか」を考えて載せ替えを決めたのに対し、こちらは捨てる判断すらできません
- **制約に押されて、結果的に良い設計になりました。** 副作用を追い出したので、シナリオに渡す関数は 2 経路とも純粋です
- 段階ごとのディレクトリ（[ADR-015](ADR-015-step-directories.md)）に伴い、入口も段階ごとに複製されます

## コンプライアンス

- 同じシナリオが 2 経路（ドメイン直接・HTTP 経由）とも green であること
- シナリオが HTTP やドメインの関数名を直接扱わないこと
- シナリオに渡す関数が入出力をしないこと

## 再検討の条件

1. なでしこ3 に受け入れテストの枠組みを提供するライブラリが現れる
2. 経路が 3 つ以上に増え、自作の枠組みでは扱いきれなくなる
3. 非同期の扱いが cnako3 で改善され、関数値ごしでも待てるようになる
