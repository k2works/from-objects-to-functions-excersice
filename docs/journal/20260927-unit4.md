# 2026-09-27 Unit 4 — 前提が崩れる変更を測った

Unit 4（第 6〜7 章）を完了させた。コマンドと `Outcome`。

この Unit には、これまでと性質の違う作業が 1 つあった。**自分が書いてきた前提を、自分で破る**作業だ。

## 前提を破った

第 2 章から、こう書いてきた。

> ポートの型が変わらなければ、ハブより上のコードは変わらない。

関数の型で依存を表すことの利点として説明してきた。第 7 章で `ToDoListFetcher` の戻り値を `ToDoList?` から `Outcome` に変えるので、**型そのものが変わる**。前提が効かない。

計画の段階で、これを「この Unit の山」として書き、終了報告に「変わったファイル数」を指標として置いた。設計が本当に変更を楽にしているかを測る唯一の数字だと考えたからだ。

### 結果は 6 ファイル

| 変わった | 変わらなかった |
| :--- | :--- |
| ハブ（ポートの型定義と戻り値） | ドメインの型 |
| インメモリのアダプタ | イベントと状態の畳み込み |
| HTTP アダプタ | モノイドのテスト |
| ハブのテスト | コマンドとステートマシン |
| DDT の 2 経路 | 遷移表とそのテスト |
| | **受け入れテストのシナリオ** |

変わった 6 つは、すべて `ToDoListFetcher` か `ToDoListHub` を直接触る場所だった。

### 波及しなかった理由を正確に書いた

ここで気をつけたことがある。**「関数の型を使ったから楽だった」と書きたくなる**。でもそれは違う。

波及しなかったのは、ドメインがポートを知らず、シナリオが実装を知らないからだ。**インターフェースで書いていても、同じ境界を引いていれば同じ結果になったはずだ。**

もし `ToDoList` 自体が `Outcome` を持つ設計だったら、関数の型を使っていてもドメイン全体に波及していた。効いたのは境界の位置で、依存の表し方ではない。

記事にもそう書いた。設計を弁護せず、起きたことと理由を書く。**自分の推してきた技法の効果を過大に書くのが、技術記事のいちばんありがちな嘘だと思う。**

そして説明を条件付きに直した。

> 型が変われば、**その型を触る場所だけ**が変わる。

## コンパイルが通ったから正しいとは限らない

`orElse`（失敗なら代わりの値を返す）をメンバー関数で書いた。`T` は共変（`out T`）なので引数に使えない。`@UnsafeVariance` を付けたらコンパイルが通った。

**実行したら `ClassCastException` が出た。**

`Failure<E>` は `Outcome<E, Nothing>` なので、そこでは `T = Nothing`。コンパイラは引数を `Nothing` にキャストするコードを生成する。`Nothing` にキャストできる値は存在しない。

`@UnsafeVariance` は名前のとおり unsafe だった。アノテーションが「危険だ」と言っているのに、コンパイルを通すために付けた。**警告を黙らせる道具を使うときは、何を黙らせているのかを確かめるべきだった。**

拡張関数に切り出したら解決した。`T` が呼び出し側で決まるので `Nothing` に固定されない。

テストがあったから実行時に気づけた。これは運ではなく、TDD の見返りだ。

## 受け入れテストが表示の不足を教えてくれた

第 6 章で `status` を動かしたとき、**HTTP 経由の受け入れテストだけが落ちた。** ドメイン直接の経路は通った。

原因は HTML に状態を表示していなかったこと。ドメインに状態があるのに画面に出ていない、という不整合だ。

**2 経路で実行していたから、原因が表示側だと切り分けられた。** 1 経路だけなら「どこかがおかしい」で終わっていた。第 3 章で 2 経路を用意したのは「ドメインとインフラが分離できているかを確かめるため」だったが、**不整合の切り分けにも効いた**。

## 表を先に作ると判断の漏れが見える

状態遷移を実装するとき、コードから書き始めなかった。4×4 の表を先に作った。

作ってみて気づいたことがある。**`Todo` から `Blocked` へ行けるか**という判断が必要だった。コードから書いていたら、この組み合わせを考えずに済んでいた（`when` に書かなければ「許さない」になるので、動いてしまう）。

表にしたので、16 マス全部について「許すか許さないか」を決めることになった。そしてその表からテストを起こした。**表が 16 マスあること自体**もテストにした。状態を 1 つ足して行と列を足し忘れたら落ちる。

表は「判断すべき箇所の一覧」でもある。

## 引数を足したら呼び出し側の書き方が壊れた

ハブにアダプタを 2 つ足した。すると第 4 章で書いていた `ToDoListHub { u, l -> ... }` という末尾ラムダの記法が、`persist` に束縛されるようになった。コンパイルエラーで気づいた。

名前付き引数に直した。

**インターフェースなら起きない種類の問題だ。** 関数の型を使う設計の小さなコストとして記事に書いた。技法の利点だけを書くと、読者が実務で踏んだときに驚く。

## ゲートは数ではなく場所で決める

Unit 3 で疎にして変更依頼 0 件だった。Unit 4 では、数を維持するのではなく**エントロピー評価で MED に上がった原因にゲートを当てた**。

ポートの型変更の方針を決めるステップ（4-2.2）に置いた。結果、段階的な置き換えの順序を先に決められたので、各段階で `check` を green に保てた。変更依頼は 0 件だった。

ゲート数は 11 → 5 → 4 と減っているが、変更依頼は Unit 3・4 とも 0 件。**減らし方が正しかった**と言える。

## Unit 5 では密に戻す

計画どおり戻す。エントロピー評価で検証の不確実性とリスクが HIGH になる。

Unit 3・4 で疎にできたのは「人が見ていた判断を機械に移せていたから」だ。**Unit 5 で新しく現れる判断は、まだ機械に移せていない。** 減らしたまま突っ込まない。
